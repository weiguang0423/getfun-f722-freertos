# 从关键点得到可靠手势：几何分类与状态机

> **当前学习位置：** `摄像头已经输出手框和关键点` → **把不稳定的单帧结果变成可靠的手势事件** → `虚拟 RC 候选帧`
>
> 本篇对应 S7.5。它解决“为什么模型看到了手，还不能直接让飞控动作”。它不打开串口、不产生 RC，也不改变飞控。

## 真实问题：一帧看到手，不等于一次可靠意图

S7.4 的输出中，一帧可以是 `valid:true`，但它只说明该帧的检测器和关键点模型认为“这里像一只手”。无手的长期运行记录里仍出现过少量 `valid:true`。如果把这种单帧结果直接翻译成飞行指令，光线变化、手部遮挡或一个偶然误检都可能成为动作。

因此 S7.5 在 S7.4 与虚拟 RC 之间新增两层：

```text
21 个关键点 + presence_score
    -> 几何分类：这一帧最像哪种手势，置信度多少
    -> 时序状态机：它是否已经持续足够久，能成为 ACTIVE
    -> 只把 ACTIVE 手势交给 S7.6
```

这里的“状态机”不是神秘算法。它就是一个明确记录当前阶段的变量：没有手、未知、正在候选、已经生效，还是刚释放后需要等待。它的目的不是提高模型分数，而是规定任何不确定情况都不能保留旧动作。

## 冻结的四种手势是怎样定义的

S7.5 读取 21 个手部关键点的二维坐标，计算手指关节是否接近伸直、指尖距离是否足够大，再组合成四种单手静态手势：

| ID | 名称 | 几何含义 | 后续 RC 含义 |
|---:|---|---|---|
| 1 | `OPEN_PALM` | 拇指和四指均伸展 | 一次向前 Pitch 脉冲 |
| 2 | `FIST` | 拇指和四指均弯曲 | 立即释放虚拟源 |
| 3 | `POINT` | 只有食指伸展 | 一次向后 Pitch 脉冲 |
| 4 | `V_SIGN` | 食指、中指伸展且分开；无名指、小指弯曲 | 一次向左 Roll 脉冲 |

`OPEN_PALM` 等英文名称只是稳定的机器 ID。显示给人看的文字可以另行翻译，但线上协议和测试不能因为改显示文案而改变 ID。

### 分类置信度从哪里来

每根手指先得到一个 0 到 1 的“伸展程度”：关节越接近直线、指尖到掌根的距离越接近完整手指长度，分数越高。四种手势各自把相关手指的伸展程度组合为一个得分，再取最高分和第二高分做比较。

本项目当前门槛是：

- 分类置信度必须至少 `0.58`。
- 第一名与第二名的差值必须至少 `0.08`，否则两种手势太像，输出 `UNKNOWN`。
- 进入下一层状态机时，置信度还必须至少 `0.75`。

这些阈值不是模型训练参数，而是部署后的安全决策参数。它们记录在 [`s7_5_gesture.cpp`](../../s7_5/s7_5_gesture.cpp) 中；改变它们就改变了手势语义，应重新做 S7.5 验收，而不是只改数字后继续使用旧结论。

## 五态状态机怎样防止误触发

> **当前学习位置：** `单帧分类` → **连续帧确认和释放** → `只有 ACTIVE 可交给虚拟 RC`

状态机中的五个状态如下：

| 状态 | 日常含义 | 是否允许交付活动手势 |
|---|---|---|
| `NO_HAND` | 画面中没有可用手部 | 否 |
| `UNKNOWN` | 有手，但不满足某个已定义手势或置信度不足 | 否 |
| `CANDIDATE` | 同一个高置信度手势正在连续出现 | 否 |
| `ACTIVE` | 已经连续确认，可以作为一次动作事件 | 是 |
| `RELEASED` | 刚刚失效/切换/释放，处于冷却期 | 否 |

真实转换规则可以压缩成这张图：

```text
NO_HAND / UNKNOWN
      |
      | 同一手势 >= 0.75，开始出现
      v
CANDIDATE -- 连续至少 5 帧且跨越至少 150 ms --> ACTIVE
      ^                                          |
      | 同一手势继续                              | 低置信度、无手、改手势、超时
      |                                          v
      +------------------------------------- RELEASED
                                                    |
                                                    | 冷却 300 ms 后等待新候选
                                                    v
                                             NO_HAND / UNKNOWN
```

除此之外，相邻有效输入相隔超过 `250 ms` 也会释放。这个时间间隔保护的是“程序卡住后，旧 `ACTIVE` 还挂着”的情况。无手、未知、低置信度、推理失败、采集失败、延迟超限和手势切换，都在当前结果清空 `active_id`；系统不保留“上一秒的张掌”当作现在仍有效。

## 先运行纯逻辑自检，再跑摄像头

S7.5 的分类器和状态机刻意写成纯 C++ 模块，不依赖 RKNN、OpenCV 或摄像头。这样你可以在 WSL 先验证最核心的安全规则。

**运行地点：WSL。**

```sh
cd /mnt/e/getfun-f722-freertos/GETFUN_F722_FreeRTOS
g++ -std=c++17 -O2 -Wall -Wextra \
  Linux/RK3568/s7_5/s7_5_gesture.cpp \
  Linux/RK3568/s7_5/s7_5_gesture_test.cpp \
  -o /tmp/s7_5_gesture_test
/tmp/s7_5_gesture_test
```

`g++` 是 C++ 编译器；`-std=c++17` 固定 C++ 语言版本；`-Wall -Wextra` 要求编译器报告更多常见错误；`-o` 指定生成文件的位置。成功时预期输出：

```text
s7.5 gesture self-test ok
```

这个测试自行构造四种几何手形，并验证：4 帧仍是 `CANDIDATE`、第 5 帧并达到 150 ms 才是 `ACTIVE`；置信度降到 0.70 时立即 `RELEASED`；输入间隔超过 250 ms 时也释放。它证明规则实现一致，但不能代替真人手势验收。

然后才进入真实板端链。构建在 **WSL**，运行在 **RK3568 板端**：

```sh
# WSL：生成 ARM64 程序
cd /mnt/e/getfun-f722-freertos/GETFUN_F722_FreeRTOS
sh Linux/RK3568/s7_5/build_board.sh

# RK3568：先检查可执行文件的内部自检
cd /userdata/gesture_rc_demo
./s7_5_live --self-test
```

实时摄像头运行方式沿用上一章的参数，只是可执行文件变为 `s7_5_live`。屏显打开时，会额外显示“本帧观察到的手势/置信度”和“状态/活动手势/候选帧数”。绿色代表 `ACTIVE`；其余颜色代表安全的非活动状态。

## 怎样验证手势，而不是只看一次屏幕

S7.5 需要把每个真实手势所在的序号范围写进标签文件，再让评估脚本计算混淆矩阵和进入延迟。仓库提供了 [`labels.example.csv`](../../s7_5/labels.example.csv) 作为格式例子，以及 [`evaluate_results.py`](../../s7_5/evaluate_results.py)。

**运行地点：WSL 或能运行 Python 3 的 PC。**

```sh
python3 Linux/RK3568/s7_5/evaluate_results.py labels.csv results.jsonl > summary.json
```

此处 `labels.csv` 不是模型训练集，而是你手工记录“第几帧到第几帧，我实际做的是哪一个手势”的验收标签。脚本输出：

- `expected x active` 混淆矩阵：真实手势和最终 ACTIVE 手势是否一致。
- 每个标签区间首次进入 `ACTIVE` 的延迟。
- 无标签、`UNKNOWN` 区间内仍出现 ACTIVE 的误触发。

当前项目的验收方法要求四类手势分别重复至少 10 次，并额外覆盖无手、半握拳、遮挡、边缘和快速切换。项目状态记录为 S7.5 已验收；如果你改变摄像头安装、光线、手势定义或阈值，应把这些场景重新跑一遍，不应把旧验收结果直接套用。

## 本篇完成判据与故障定位

完成本篇时，你应能解释并观察到：

1. 一帧 `OPEN_PALM` 先是 `CANDIDATE`，不是立刻 ACTIVE。
2. 满足 5 帧和 150 ms 后才会出现 `ACTIVE`。
3. 移开手、低置信度、推理失败或间隔超过 250 ms 时，`active_gesture_name` 会清空。
4. 一次手势切换会先释放，而不是直接把 A 手势换成 B 手势。

| 现象 | 第一检查点 | 正确理解 |
|---|---|---|
| 一直显示 `UNKNOWN` | 关键点骨架是否贴合；`presence_score`；0.75 门槛 | 这是保护，不应先把门槛调低 |
| 经常一出现就释放 | JSONL 帧间隔、是否超过 250 ms、摄像头延迟 | 先修实时链，不是先改状态机 |
| 手势切换时没有动作 | 300 ms 冷却和 5 帧/150 ms 确认 | 这是防抖的预期行为 |
| 一帧误识别导致 ACTIVE | 检查是否真的已连续达到确认条件；保存 JSONL | 单帧结果不应直接成为动作 |
