# 关键点怎样变成可靠手势

上一章得到的是一帧里的 21 个手部关键点。这些点只能说明“这一瞬间，模型认为关节在这些位置”。

它还不能直接触发控制。原因很实际：

- 手正在进入画面时，手指可能只显示一半；
- 两个手势切换时，中间形状可能短暂像第三种手势；
- 关键点会在真实位置附近小幅抖动；
- 置信度可能一帧高、一帧低；
- 某一帧可能完全识别错。

所以这一章要解决两个不同问题：

1. 单帧的 21 个点更像哪一种手势？
2. 这个结果是否已经连续稳定，足以变成一次“确认事件”？

## 本项目识别哪四种手势

当前冻结手势集合是：

| 名称 | 直观形状 | 后续用途 |
|---|---|---|
| `OPEN_PALM` | 五指张开 | 触发一次 Pitch 负向动作 |
| `FIST` | 五指弯曲成拳 | 立即释放 Linux 候选 |
| `POINT` | 食指伸展，其他主要手指弯曲 | 触发一次 Pitch 正向动作 |
| `V_SIGN` | 食指和中指伸展并分开 | 触发一次 Roll 负向动作 |

这里先只关心“怎样确认手势”。具体怎样映射成 RC，在下一章讲。

## 为什么不用关键点的绝对坐标

如果直接规定“食指尖的 y 小于 100 就算伸直”，同一个手势离摄像头远一点、近一点或换一个画面位置，结果就会改变。

所以项目主要使用相对几何关系：

- 相邻关节形成的角度；
- 从指根到指尖的直线距离；
- 沿手指各段长度相加得到的总长度；
- 食指和中指之间的距离，相对于手掌宽度有多大。

这些比例不会完全消除视角影响，但比固定像素坐标更稳定。

## 一根手指怎样判断是否伸展

先以食指为例。食指有四个连续关键点：指根、两个中间关节和指尖。

项目同时看两个方面。

### 关节是不是接近一条直线

如果手指伸直，连续三点形成的夹角会比较大。弯曲时，夹角变小。

程序把两个关节的直线程度都算出来，并取较差的那个。这样可以防止“第一节看起来直、第二节明显弯”仍被当成完全伸展。

### 指尖离指根是不是足够远

程序还会比较：

```text
指根到指尖的直线距离
÷
三段指骨路径长度之和
```

手指伸直时，这个比例接近 1。手指弯曲时，沿关节走的总长度没变太多，但指尖会靠近指根，比例下降。

最后把“关节直线程度”和“指尖伸出程度”组合成 0～1 的伸展度。

拇指的方向和其他四指不同，所以它使用类似思路，但还会参考拇指尖与食指根的距离，以及手掌宽度。

## 五根手指怎样形成四类分数

得到五个伸展度后，程序不是立即写一堆硬判断，而是给四种手势分别打分。

### 张掌

五根手指都越伸展，张掌分数越高。

### 握拳

五根手指都越弯曲，握拳分数越高。

### 单指

食指伸展、其他主要手指弯曲时，单指分数高。

### V 字

食指和中指伸展，无名指和小指弯曲，并且两根伸展手指有明显分离时，V 字分数高。

这里使用分数而不是只有 true/false，是因为真实关键点很少刚好落在理想位置。分数能表达“像到什么程度”。

## 为什么要比较第一名和第二名

假设一帧结果是：

| 手势 | 分数 |
|---|---:|
| 张掌 | 0.81 |
| V 字 | 0.79 |
| 单指 | 0.32 |
| 握拳 | 0.10 |

张掌虽然是第一名，但只比 V 字高 0.02。这说明当前形状很模糊。

项目要求第一名与第二名至少拉开 0.08。没有拉开时，单帧结果记为 `UNKNOWN`，也就是“现在不能可靠归类”。

另外，单帧分类本身还要达到最低可信度。项目把手存在置信度和几何最高分一起考虑：任何一边太低，最终置信度都不会高。

这一步解决的是“不要被勉强的第一名骗到”。

## 单帧结果为什么还不能变成动作

即使一帧张掌分数很高，也可能是切换过程中的偶然结果。

项目要求一个手势进入 `ACTIVE` 前，同时满足：

- 置信度至少 0.75；
- 连续确认至少 5 帧；
- 从第一帧候选到当前至少经过 150 ms；
- 中间不能换成其他手势；
- 相邻输入不能中断太久。

“5 帧”和“150 ms”同时存在，是为了防止两种极端情况：

- 帧率异常高时，5 帧可能挤在很短时间内；
- 帧率异常低时，只看时间又可能只有很少样本。

## 五个状态分别表示什么

状态机保存的不是一帧分类，而是这段时间内的确认过程。

| 状态 | 含义 |
|---|---|
| `NO_HAND` | 当前没有可靠的手部输入 |
| `UNKNOWN` | 看到了手，但不能可靠归为四类之一 |
| `CANDIDATE` | 某种手势正在连续确认，还不能触发 |
| `ACTIVE` | 同一手势已经通过帧数、时间和置信度要求 |
| `RELEASED` | 刚刚因为失效或切换而释放，处于短暂冷却期 |

状态变化的核心思路是：

```text
没有手 → NO_HAND

有手但不明确 → UNKNOWN

明确识别到一个手势
  ↓
CANDIDATE
  ↓ 同一手势连续5帧且跨度至少150ms
ACTIVE

ACTIVE期间出现低置信度、换手势或输入超时
  ↓
RELEASED
  ↓ 冷却300ms
重新允许确认
```

## 为什么切换手势时要先释放

假设当前张掌已经 `ACTIVE`，下一帧突然变成 V 字。

程序不会在同一帧直接把活动手势改成 V 字。它先释放张掌，清空活动手势，再进入 300 ms 冷却。冷却结束后，V 字还要重新完成连续确认。

这样做会增加一点切换时间，但能避免两个动作在切换边缘连续触发。

## 250 ms 输入间隔限制解决什么

状态机还记录上一次更新时刻。

如果相邻输入间隔超过 250 ms，说明实时链可能卡住、摄像头可能停止，或者进程长时间没有拿到新结果。

即使间隔前的手势是 `ACTIVE`，也不能继续相信。状态机会立即释放活动手势。

这里检查的是“输入是否持续到达”，不是“这一帧手势分数高不高”。它们是两种不同的健康条件。

## 用一段时间线看懂确认过程

假设每 50 ms 处理一帧，张掌置信度一直是 0.90：

| 时间 | 单帧结果 | 状态 | 能否触发 |
|---:|---|---|---|
| 1000 ms | 张掌 0.90 | `CANDIDATE`，第1帧 | 不能 |
| 1050 ms | 张掌 0.90 | `CANDIDATE`，第2帧 | 不能 |
| 1100 ms | 张掌 0.90 | `CANDIDATE`，第3帧 | 不能 |
| 1150 ms | 张掌 0.90 | `CANDIDATE`，第4帧 | 不能 |
| 1200 ms | 张掌 0.90 | 5帧且经过200ms，进入 `ACTIVE` | 可以触发一次 |

如果 1250 ms 的张掌置信度掉到 0.70，因为低于 0.75，状态立即进入 `RELEASED`，活动手势清空。

即使 1300 ms 又出现高置信张掌，也还在 300 ms 冷却期内，不能马上再次触发。

## `ACTIVE` 是事件，不是持续遥控杆

这是理解下一章的关键。

`ACTIVE` 表示“这个手势刚刚完成了可靠确认”。项目不会因为手一直保持张掌，就在每一帧重复创建新动作。

后面的映射器只关注一次新的 `ACTIVE` 边沿，也就是从“还没活动”变成“已经活动”的那个时刻。它由此启动一个固定 1 秒的姿态目标。

这样可以避免使用者一直保持同一手势时，命令被无限延长或重复触发。

## 怎样判断这一层工作正常

观察时不要只看最后的手势名字，要同时看：

- 当前单帧识别结果；
- 当前置信度；
- 状态机状态；
- 候选已经连续多少帧；
- 当前活动手势是什么。

典型现象应该是：

| 场景 | 正常表现 |
|---|---|
| 手刚进入画面 | 先是 `UNKNOWN` 或 `CANDIDATE`，不会立即 ACTIVE |
| 稳定保持合法手势 | 满足帧数和时间后只进入一次 ACTIVE |
| 模糊手形 | 保持 UNKNOWN，不勉强选第一名 |
| ACTIVE 后置信度下降 | 立即清空活动手势并进入 RELEASED |
| 从张掌切到 V 字 | 先释放，再冷却，再重新确认 V 字 |
| 输入停顿超过 250 ms | 即使上一结果很好，也释放 |

## 参数应该怎样理解，而不是怎样乱调

这些参数是在准确率、响应速度和误触发之间做取舍：

- 提高 0.75 门槛：更难触发，但可能漏掉角度不佳的真实手势；
- 增加确认帧数或确认时间：更稳，但响应更慢；
- 缩短 250 ms 输入间隔：更快发现卡顿，但容易把偶发慢帧当故障；
- 增加 300 ms 冷却：减少连续误触发，但手势切换更慢。

调整时一次只改一个参数，并使用同一批真实场景比较。否则即使结果变好，也不知道是哪项变化起作用。

## 这一章交给下一章什么

现在已经不再是抖动的一帧结果，而是一个有明确状态的手势事件：

```text
GestureSnapshot
  当前状态
  当前看到的手势
  当前置信度
  已确认的活动手势
  连续候选帧数
```
