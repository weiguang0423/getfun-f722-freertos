# 拆桨端到端验收与故障定位

> **当前学习位置：** `Linux 和飞控各自可验证` → **用同一源序号证明整条链路、验证每一种退出** → `S7.9 之前停止`
>
> 本篇对应 S7.8。它的终点是拆桨条件下的端到端证据，不是装桨或飞行。完成后，你可以判断故障卡在摄像头、推理、手势、串口、飞控仲裁还是后续控制链。

## 为什么“Linux 有日志”和“飞控有日志”还不够

如果 Linux 记录说自己发过 `sequence=318`，飞控记录也说自己正常，两者不一定是同一次动作。S7.8 用同一个源序号把它们接起来：

```text
摄像头帧 sequence=318
    -> Linux virtual_rc_source_sequence=318
    -> UART 帧 source_sequence=318
    -> 飞控 e2e rc_seq=318（或随后更新的更大序号）
```

这样才能追问：这次手势对应的候选是否真的被飞控采用？采用后 setpoint、PID、Mixer、ARM/Failsafe 和 DShot 状态是否完整？

## 开始前的绝对前提

1. 拆掉螺旋桨。可断开电机动力时优先断开；不要因为“只是看日志”就装桨。
2. 保存两类日志：RK3568 标准输出保存为 `linux.jsonl`，飞控 UART4 保存为 `flight.log`。
3. 物理遥控器：AUX1=ARM、AUX2=ANGLE、AUX3=视觉授权；上电时三者低位，油门最低。
4. Linux 只能向已实物确认的 USART6 接线发送。确认 UART2 仍只连接 CRSF。
5. 先保持无手。Linux 应持续发送 `virtual_rc_valid:true`、`virtual_rc_gesture_name:"UNKNOWN"` 和五通道全 0 的健康中立帧。

以下流程依赖硬件连接，不能在没有电气核对时直接执行。未接飞控或只想检查 Linux 链时，明确设置 `S7_6_RC_OUTPUT=/dev/null`；它只验证视觉/软件链，不能验证端到端通信。

## 先检查两套日志工具本身

仓库提供两个 Node.js 脚本。先运行内置样例，验证你的 PC 上的检查器可工作：

**运行地点：Windows PowerShell 或 WSL，均在仓库根目录。**

```powershell
node Tools/verify_s7_8_trace.mjs --self-test
node Tools/verify_s7_8_e2e.mjs --self-test
```

预期分别输出：

```text
S7.8 Linux trace: self-test PASS
S7.8 端到端检查：内置样例通过
```

第一个工具检查 Linux JSONL：摄像头序号不能倒退、心跳必须递增、有效候选的源序号必须等于当前摄像头 `sequence`、Throttle/AUX 必须为 0、无效帧必须全通道释放。

第二个工具读取 Linux JSONL 和飞控 UART4 日志中的 `e2e` 行。它要求至少出现一次 `rc_source=1`，并检查每一个被选中的样本前面都能找到有效 Linux 源序号，而且 `rc_valid`、setpoint、PID、Mixer、飞控准备、DShot 准备和 Failsafe 字段符合安全合同。

## 采集真实端到端日志

> **当前学习位置：** `检查工具本身` → **保存两端原始日志** → `从中立、动作到故障退出逐级观察`

在 RK3568 上启动 `s7_6_live --camera ...` 时，标准输出是 Linux JSONL。用 `>` 保存它；不要把错误输出混入这个文件。UART4 的终端会话另存为 `flight.log`。

完成一轮拆桨测试后，在 PC 上执行：

```powershell
node Tools/verify_s7_8_trace.mjs C:\路径\linux.jsonl
node Tools/verify_s7_8_e2e.mjs C:\路径\linux.jsonl C:\路径\flight.log
```

`PASS` 的含义是这些日志没有违反脚本内的合同。它不能替代检查真实手势、实际电机接线、电气波形和物理安全状态；日志检查是证据链的一环，不是全部证据。

## 从中立到动作的最小拆桨流程

每一步都应保留两端日志，不要只在最后看一次：

| 阶段 | 操作 | Linux 应看到什么 | 飞控应看到什么 |
|---|---|---|---|
| 默认 | 上电，AUX1/2/3 低，无手 | 有效 UNKNOWN 中立帧 | `rc_source=0`，物理源 |
| ARM 但未授权 | 仅 AUX1 ARM | 仍是健康中立 | 仍 `rc_source=0` |
| 进入虚拟源 | RPY 回中，AUX3 从低拉到高 | `virtual_rc_valid:true` | `rc_source=1`；控制链有效 |
| 张掌 | 进入 ACTIVE 后保持到自动回中 | 一次 Pitch 负向脉冲，约 1 秒后回中 | `rc_seq` 与 Linux 对齐，姿态通道有对应变化 |
| 单指 | 重新进入 ACTIVE | 一次 Pitch 正向脉冲 | 同上，不能影响 Roll/Yaw/Throttle/AUX |
| V 字 | 重新进入 ACTIVE | 一次 Roll 负向脉冲 | 同上，不能影响 Pitch/Yaw/Throttle/AUX |
| 正常无手/切换 | 手移开或候选期间 | 健康 UNKNOWN 中立；尚未结束的脉冲不被截断 | `rc_source` 仍为 1，不要求重新授权 |
| 握拳 | 做 FIST | 当前帧无效释放 | `rc_source=0`，恢复物理源 |

在 `rc_source=1` 期间，安全范围内改变物理油门是专门要验证的一项：`rc_source` 不应退出，Linux 的 Throttle/AUX 候选仍为 0，飞控有效油门和四电机基础值应继续跟随物理遥控器。它证明 Linux 没有取得油门所有权。

## 每一种故障都必须有明确的退出证据

正常动作正确只是半个验收。下面的故障注入每次都从“已 ARM、已 AUX3 低高授权、`rc_source=1`”开始；完成一项后再次进入时，都必须先做 AUX3 低到高授权。

| 故障/操作 | 预期飞控结果 | 首先查看的证据 |
|---|---|---|
| AUX3 拉低 | 立即物理源，原因 AUTH_REVOKED | `rc source` 日志的退出原因 |
| 物理 R/P/Y 任一偏移超过 150 us | 立即物理源，原因 PHYSICAL_TAKEOVER | 物理 RC 与 `source` 变化 |
| 握拳或视觉故障 | 当前帧候选无效，立即物理源 | Linux `valid:false` 与飞控原因 VIRTUAL_INVALID |
| 杀死 Linux 发送进程/拔 TX | 最多约 150 ms 后退出 | 最后有效帧时间、飞控 `source=0` 时间 |
| Linux/RK3568 重启 | 即使流量恢复也不自动重入 | 接收会话代数、AUX3 仍高时保持物理源 |
| CRC、版本、长度、序号或时间错误 | 当前候选拒绝、进入物理源 | `linux_rc` 的 CRC/格式/序号/时间错误计数 |
| 飞控 inhibit 或物理 RC 失效 | 退出虚拟源，既有 Failsafe 接管 | `armed`、`failsafe`、退出原因 |

不要为了方便制造故障而短接电源、带电移动未知跳线或绕过 ARM/Failsafe。要使用项目已有的安全故障注入方法，例如杀 Linux 进程、拔已确认的 TX、或触发现有 RC Failsafe 条件。

## 用现象倒推故障在哪一层

```text
摄像头无帧
  -> 看 /dev/video0 与 V4L2 短采集
有帧但 JSONL 无有效手
  -> 看模型路径、关键点标注图、延迟与 NPU Runtime
有手但永远 UNKNOWN/CANDIDATE
  -> 看 S7.5 置信度、5 帧/150 ms、250 ms 间隔
Linux 有 virtual_rc 但飞控无候选
  -> 看 UART 电平/接线、44 字节、CRC、USART6 计数
候选有效但 rc_source 始终为 0
  -> 看 ARM、AUX3 低高、RPY 中立、inhibit、候选年龄和通道配置
rc_source=1 但 e2e 不完整
  -> 看 rc_setpoint/PID/Mixer/Failsafe/DShot 的实际诊断字段
```

这种从“离物理输入最近的一层”往后检查的方法比一次性重装 SDK 或改阈值可靠。每一次检查都缩小故障范围，并保留能复现的日志。

## 当前项目结论和你完成后的停止点

项目主计划记录 S7.1～S7.8 已验收并冻结为 `v1.6.0-s7.8-gesture-rc-baseline`。这说明本教程描述的链路在记录的硬件、版本和验收条件下完成过平台、模型、实时、手势、串口、仲裁和拆桨端到端验证。

它不意味着以下事情已经完成：

- 没有因此获得装桨权限。
- 没有因此获得离地、受控飞行或自动飞行权限。
- 没有因为换了模型、SDK、系统、摄像头、线序或飞控固件后仍然自动有效。

S7.9 是独立的受控飞行阶段，必须在 S5 基础飞行和额外安全前置条件都关闭后另行开始。本课程到 S7.8 停止，正是为了让 Linux 伴随计算机始终处于飞控安全链之内。

## 完成课程后的复盘

请用下面的结构复述整个项目：

```text
WSL 用交叉编译器生成 ARM64 副本
  -> RK3568 用 V4L2 读摄像头、用 RKNN 得到关键点
  -> S7.5 用连续帧状态机确认手势
  -> S7.6 只发送限幅、带 CRC、可失效的虚拟 RC 候选
  -> STM32 USART6 验证候选
  -> RcTask 只在物理 ARM/AUX3 授权等条件下选择它
  -> 物理 RC 始终保留油门、AUX 和接管能力
  -> 原有 Failsafe、PID、Mixer、DShot 决定最终安全输出
```

如果其中任何一箭头无法用日志、图像、串口波形或源码责任点证明，就把它当成待验证项，而不是“应该没问题”。
