# 拆桨端到端验收与故障定位

> **文档进度：`Linux链已建立 → 飞控仲裁已理解 → [本篇：同一源序号贯穿两端证据与故障退出] → 课程停止`**
>
> **真实数据流位置：`摄像头sequence → Linux候选source_sequence → 飞控rc_seq → setpoint/PID/Mixer/DShot诊断`**
>
> 本篇对应 S7.8，终点是**拆桨台架证据**。不安装螺旋桨，不离地，不进行 S7.9 受控飞行。

## 这次真正要证明什么

前六篇已经分别解释各模块，但“每个模块看起来正常”不等于整条链正常。端到端验收必须让同一件事在上下游留下可关联证据：

```text
摄像头帧 sequence=318
  ↓
单帧关键点 valid=true
  ↓
手势状态 ACTIVE
  ↓
Linux virtual_rc_source_sequence=318，heartbeat=901
  ↓ 44字节UART帧
飞控 linux_rc last seq=318 hb=901
  ↓ 仲裁器采用
飞控 e2e rc_source=1 rc_seq=318 rc_hb=901
  ↓
setpoint_valid=1 → pid_valid=1 → mixer_valid=1 → DShot诊断
```

如果只看到 Linux 的 318，没有飞控 318，故障在发送、导线、接收或验证层。如果飞控能看到 318，但 `rc_source=0`，故障在授权/门禁/接管层。如果 `rc_source=1` 而 `pid_valid=0`，故障已经越过仲裁，位于后级控制链。

本篇使用：

| 文件 | 作用 |
|---|---|
| `Tools/verify_s7_8_trace.mjs` | 检查 Linux JSONL 内部序号、心跳、通道所有权和释放合同 |
| `Tools/verify_s7_8_e2e.mjs` | 把 Linux 有效候选与飞控 `e2e` 行按源序号关联 |
| `Docs/43_S7.8_拆桨端到端联合验收.md` | 项目历史验收范围和结论 |

仓库记录 S7.1～S7.8 已验收并冻结为 `v1.6.0-s7.8-gesture-rc-baseline`。本轮只是重写教程并执行主机侧检查器自检，没有重新做板端 30 分钟或飞控实物动作，因此历史通过只绑定当时硬件、模型、线序、固件和参数。

## 开始前先把人和硬件置于安全状态

> **当前位置：`准备验收 → [建立不可跳过的安全边界] → 定义两端日志`**

以下任一项不满足，就停止，不用“手扶电机”或“只试几秒”代替：

1. **四个螺旋桨全部拆除**，并拍照或在记录中写明。能断开电机动力时优先断开。
2. 飞控固定在绝缘台面，线材不会碰到相邻焊盘；准备可立即断电的电源开关。
3. RK3568 UART 是 3.3 V TTL；两板共地；RK3568 TX 只接 PC7/USART6_RX；UART2 仍只接 CRSF。
4. 逻辑分析仪地夹接系统 GND，不能夹信号脚；禁止带电试探未知针脚或短接电源。
5. 物理遥控器已绑定：AUX1=ARM、AUX2=ANGLE、AUX3=视觉授权；上电前三者低、Throttle 最低、RPY 回中。
6. UART4 诊断口以 115200 8N1 持续保存原始文本。
7. 记录实际 Linux ELF、模型和飞控 BIN/ELF 的 SHA-256；以后换任何一个产物都要视为新组合。

本篇会出现 ARM 和 DShot 字段，是为了观察既有安全链，不是授权装桨。若默认上电就 `rc_source=1`、无物理 RC 仍活动、Linux 改变 Throttle/AUX，立即断电并判失败。

## 两端原始日志必须分开保存

> **当前位置：`安全前置已满足 → [规定Linux JSONL与UART4文本证据] → 检查工具设计`**

### Linux JSONL 记录一帧的完整来源

启动实时程序时：

- 标准输出 stdout 只保存逐帧 JSONL；
- 标准错误 stderr 保存模型、摄像头和串口诊断；
- 两者不能合并，否则 JSON 解析器会把普通诊断文字当坏 JSON。

端到端关键字段：

| 字段 | 当前含义 |
|---|---|
| `frame_index` / `sequence` | 当前摄像头帧序号 |
| `valid` / `reject_reason` | 单帧手部是否可用，若否为什么 |
| `gesture_name/confidence/state` | 当前观察和状态机状态 |
| `active_gesture_name` | 状态机真正批准的手势 |
| `virtual_rc_valid` | 当前发送的是健康候选还是无效释放 |
| `virtual_rc_source_sequence` | 线上帧引用的摄像头序号，正常必须等于当前 `sequence` |
| `virtual_rc_heartbeat` | 每发一帧递增 |
| `virtual_rc_gesture_name` | 当前候选脉冲来源；回中后 UNKNOWN |
| `virtual_rc_channels` | `[Roll,Pitch,Yaw,Throttle,AUX]`，后两项必须永远为0 |

健康无手应是 `virtual_rc_valid:true`、手势 UNKNOWN、五通道全零。摄像头/推理/时间故障或 FIST 应是 `virtual_rc_valid:false`、五通道全零。`valid:false` 绝不能携带旧姿态值。

### 飞控 UART4 有三层文本

`linux_rc` 回答“字节和帧通过了吗”：

```text
linux_rc rx=... frame=... valid=... crc=... fmt=... seqerr=...
timeerr=... restart=... uart=... last=[v... g... c... seq=... hb=... ch=...]
```

`rc source` 回答“候选为什么被采用或没被采用”：

```text
rc source=1(virtual) auth=1 reauth=0 virtual=1 age_ms=20
seq=318 hb=901 gen=0 enter=1 exit=0 reason=0(none)
aux3_us=2000 armed=1 inhibit=0x00000000 cfg=1
```

`e2e` 回答“采用后下游是否完整”：

```text
e2e rc_source=1 rc_valid=1 rc_seq=318 rc_hb=901
setpoint_valid=1 setpoint_mode=0 pid_valid=1 mixer_valid=1
flight_ready=1 armed=1 failsafe=0 dshot_ready=1 dshot_busy=0 motors=[...]
```

`e2e` 每秒采样一次，而 Linux 约每 50 ms 一帧，所以飞控日志不可能列出每个 Linux 序号。检查器采用“飞控 rc_seq 前面最近的有效 Linux 源序号”做关联；这能证明时间顺序和存在性，不能证明每个中间帧都被 UART4 逐条打印。

## 第一份检查器先检查 Linux 自己是否前后一致

> **当前位置：`日志字段已定义 → [理解verify_s7_8_trace.mjs] → 先自测工具`**

### 为什么先检查单端

若 Linux 日志内部就出现心跳倒退、Throttle 非零或无效帧带旧通道，没必要先怀疑飞控。第一份脚本只读一个 JSONL 文件，不修改文件。

### Node 脚本依赖顺序

```text
fail(message) → 统一抛错误
assert(condition,message) → 条件不满足时调用fail
readRecords(path) → 文件每行解析JSON
checkLinuxTrace(records) → 逐条检查合同
命令行入口 → --self-test或真实路径
```

首次出现的 JavaScript/Node 概念：

- `.mjs` 表示 ES module，使用 `import`。
- `node:fs` 是 Node 自带文件系统模块，不需安装第三方包。
- `throw new Error` 立即中止当前检查，并保留具体原因。
- `process.argv.slice(2)` 取得用户在脚本名后输入的参数。
- `process.exit(2)` 表示用法错误；未捕获检查错误通常以非 0 退出。
- `Number.isInteger` 防止序号是字符串或小数。
- `Array.isArray` 验证通道确实是数组。
- `.every(...)` 要求数组每个元素都满足条件。

### 完整 `Tools/verify_s7_8_trace.mjs`

```javascript
import fs from "node:fs";

function fail(message) {
  throw new Error(message);
}

function assert(condition, message) {
  if (!condition) fail(message);
}

function readRecords(path) {
  const text = fs.readFileSync(path, "utf8");
  return text.split(/\r?\n/).filter(Boolean).map((line, index) => {
    try {
      return JSON.parse(line);
    } catch (error) {
      fail(`${path}:${index + 1}: invalid JSON (${error.message})`);
    }
  });
}

function checkLinuxTrace(records) {
  assert(records.length > 0, "Linux trace is empty");
  let previousSequence = -1;
  let previousHeartbeat = -1;
  let sawActive = false;
  let sawRelease = false;

  for (const [index, record] of records.entries()) {
    assert(Number.isInteger(record.frame_index),
           `record ${index}: frame_index missing`);
    if (record.sequence !== undefined) {
      assert(record.sequence >= previousSequence,
             `record ${index}: camera sequence went backwards`);
      previousSequence = record.sequence;
    }
    if (record.virtual_rc_heartbeat !== undefined) {
      assert(record.virtual_rc_heartbeat > previousHeartbeat,
             `record ${index}: virtual RC heartbeat did not advance`);
      previousHeartbeat = record.virtual_rc_heartbeat;
    }
    if (record.virtual_rc_valid === true) {
      sawActive = true;
      assert(record.virtual_rc_source_sequence === record.sequence,
             `record ${index}: RC source sequence does not match camera sequence`);
      assert(Array.isArray(record.virtual_rc_channels) &&
             record.virtual_rc_channels.length === 5,
             `record ${index}: active RC channels are missing`);
      const [roll, pitch, yaw, throttle, aux] = record.virtual_rc_channels;
      assert(throttle === 0 && aux === 0,
             `record ${index}: active frame changed throttle/AUX`);
      assert(["UNKNOWN", "OPEN_PALM", "POINT", "V_SIGN"].includes(
               record.virtual_rc_gesture_name),
             `record ${index}: active frame has an invalid command gesture`);
      const matchesGesture =
        (record.virtual_rc_gesture_name === "UNKNOWN" &&
         roll === 0 && pitch === 0 && yaw === 0) ||
        (record.virtual_rc_gesture_name === "OPEN_PALM" &&
         roll === 0 && yaw === 0 && pitch >= -300 && pitch <= 0) ||
        (record.virtual_rc_gesture_name === "POINT" &&
         roll === 0 && yaw === 0 && pitch >= 0 && pitch <= 300) ||
        (record.virtual_rc_gesture_name === "V_SIGN" &&
         pitch === 0 && yaw === 0 && roll >= -300 && roll <= 0);
      assert(matchesGesture,
             `record ${index}: channels do not match event gesture`);
    } else if (record.virtual_rc_channels) {
      sawRelease = true;
      assert(record.virtual_rc_channels.every((value) => value === 0),
             `record ${index}: invalid frame did not release all channels`);
    }
  }
  assert(sawActive, "trace contains no valid virtual RC frame");
  assert(sawRelease, "trace contains no invalid/release virtual RC frame");
}

const paths = process.argv.slice(2);
if (paths.length === 1 && paths[0] === "--self-test") {
  checkLinuxTrace([
    { frame_index: 1, sequence: 1, virtual_rc_heartbeat: 1,
      virtual_rc_valid: true, virtual_rc_source_sequence: 1,
      virtual_rc_gesture_name: "OPEN_PALM",
      virtual_rc_channels: [0, -30, 0, 0, 0] },
    { frame_index: 2, sequence: 2, virtual_rc_heartbeat: 2,
      virtual_rc_valid: true, virtual_rc_source_sequence: 2,
      virtual_rc_gesture_name: "UNKNOWN",
      virtual_rc_channels: [0, 0, 0, 0, 0] },
    { frame_index: 3, sequence: 3, virtual_rc_heartbeat: 3,
      virtual_rc_valid: true, virtual_rc_source_sequence: 3,
      virtual_rc_gesture_name: "V_SIGN",
      virtual_rc_channels: [-30, 0, 0, 0, 0] },
    { frame_index: 4, sequence: 4, virtual_rc_heartbeat: 4,
      virtual_rc_valid: false,
      virtual_rc_channels: [0, 0, 0, 0, 0] },
  ]);
  console.log("S7.8 Linux trace: self-test PASS");
  process.exit(0);
}
if (paths.length === 0) {
  console.error("usage: node Tools/verify_s7_8_trace.mjs LINUX_TRACE.jsonl");
  process.exit(2);
}

for (const path of paths) checkLinuxTrace(readRecords(path));
console.log(`S7.8 Linux trace: PASS (${paths.length} file${
  paths.length === 1 ? "" : "s"})`);
```

具体走读内置第 1 条：序号 1 不倒退，心跳 1 大于 -1，source_sequence=sequence=1；通道长度 5，Throttle/AUX 为 0；OPEN_PALM 要求 Roll/Yaw=0、Pitch 在 -300～0，`-30` 合法。第 4 条无效且全零，使 `sawRelease=true`。若删掉第 4 条，自测最后会报没有无效/释放帧，因为验收日志必须覆盖失效路径。

所有函数已经定义和走读后，第一次运行位置：**Windows PowerShell 或 WSL，仓库根目录**。

```powershell
node Tools/verify_s7_8_trace.mjs --self-test
```

正常输出 `S7.8 Linux trace: self-test PASS`，退出码 0。它只证明检查器和内置样例匹配，不证明你的真实日志通过。

## 第二份检查器把 Linux 与飞控 `e2e` 关联

> **当前位置：`Linux单端合同可检查 → [理解verify_s7_8_e2e.mjs] → 自测关联逻辑`**

### 先规定它能证明和不能证明什么

输入 1 是 Linux JSONL；输入 2 是 UART4 原始文本。输出摘要包含 Linux 有效候选数、飞控选中虚拟源的 e2e 样本数和关联的源序号范围。

它要求每个 `rc_source=1` 样本同时满足：

```text
rc_valid=1
setpoint_valid=1
pid_valid=1
mixer_valid=1
flight_ready=1
failsafe=0
dshot_ready=1
```

它读取 `armed` 和 `dshot_busy` 并验证是数字，但当前 `badFields` 没要求 `armed=1` 或 `dshot_busy=0`。这是检查器当前边界：实物验收仍要人工核对 armed 和 busy，不能因为脚本 PASS 就省略。

### 函数依赖顺序

```text
fail/assert
  ↓
readLinuxRecords(path)：解析JSONL
parseE2eLines(path)：只提取e2e并校验必需数字字段
  ↓
latestLinuxSourceAtOrBefore(records,sequence)：找不晚于rc_seq的最近有效源
  ↓
verify(linuxRecords,flightRecords,...)：检查选中样本和后级字段
  ↓
selfTest()：构造最小两端样例
  ↓
命令行入口
```

`Object.fromEntries` 把键值对列表变成对象；正则 `/([a-z_]+)=([^\s\r\n]+)/g` 从 e2e 行提取 `字段=值`；`/^\d+$/` 要求值全是十进制数字；`.filter` 选择 `rc_source===1` 的样本。

### 完整 `Tools/verify_s7_8_e2e.mjs`

```javascript
import fs from "node:fs";

function fail(message) {
  throw new Error(message);
}

function assert(condition, message) {
  if (!condition) fail(message);
}

function readLinuxRecords(path) {
  const text = fs.readFileSync(path, "utf8");
  return text.split(/\r?\n/).filter(Boolean).map((line, index) => {
    try {
      return JSON.parse(line);
    } catch (error) {
      fail(`${path}:${index + 1}: Linux JSON 格式错误 (${error.message})`);
    }
  });
}

function parseE2eLines(path) {
  const text = fs.readFileSync(path, "utf8");
  const records = [];
  for (const [index, line] of text.split(/\r?\n/).entries()) {
    if (!line.startsWith("e2e ")) continue;
    const values = Object.fromEntries(
      [...line.matchAll(/([a-z_]+)=([^\s\r\n]+)/g)]
        .map((match) => [match[1], match[2]]),
    );
    const required = [
      "rc_source", "rc_valid", "rc_seq", "rc_hb", "setpoint_valid",
      "pid_valid", "mixer_valid", "flight_ready", "armed", "failsafe",
      "dshot_ready", "dshot_busy",
    ];
    for (const field of required) {
      assert(values[field] !== undefined,
             `${path}:${index + 1}: e2e 缺少字段 ${field}`);
      assert(/^\d+$/.test(values[field]),
             `${path}:${index + 1}: e2e 字段 ${field} 不是数字`);
    }
    records.push({
      line: index + 1,
      ...Object.fromEntries(
        required.map((field) => [field, Number(values[field])])),
    });
  }
  assert(records.length > 0, `${path}: 没有找到 e2e 汇总行`);
  return records;
}

function latestLinuxSourceAtOrBefore(records, sequence) {
  let latest;
  for (const record of records) {
    if (record.virtual_rc_valid === true &&
        Number.isInteger(record.virtual_rc_source_sequence) &&
        record.virtual_rc_source_sequence <= sequence) {
      latest = record;
    }
  }
  return latest;
}

function verify(linuxRecords, flightRecords, linuxPath, flightPath) {
  const linuxActive = linuxRecords.filter(
    (record) => record.virtual_rc_valid === true);
  assert(linuxActive.length > 0,
         `${linuxPath}: 没有找到有效的 Linux 虚拟 RC 帧`);

  const selected = flightRecords.filter((record) => record.rc_source === 1);
  assert(selected.length > 0,
         `${flightPath}: 飞控没有选中 Linux RC（rc_source=1）`);

  let firstSequence;
  let lastSequence;
  for (const record of selected) {
    const badFields = [
      ["rc_valid", 1], ["setpoint_valid", 1], ["pid_valid", 1],
      ["mixer_valid", 1], ["flight_ready", 1], ["failsafe", 0],
      ["dshot_ready", 1],
    ].filter(([field, expected]) => record[field] !== expected);
    assert(badFields.length === 0,
           `${flightPath}:${record.line}: 已选中 Linux RC，但控制链不完整：` +
           badFields.map(([field, expected]) =>
             `${field} 应为 ${expected}`).join("，"));

    const matched = latestLinuxSourceAtOrBefore(linuxActive, record.rc_seq);
    assert(matched !== undefined,
           `${flightPath}:${record.line}: rc_seq=${record.rc_seq} 前没有有效的 Linux 源序号`);
    if (firstSequence === undefined)
      firstSequence = matched.virtual_rc_source_sequence;
    lastSequence = matched.virtual_rc_source_sequence;
  }

  return {
    linuxActive: linuxActive.length,
    selected: selected.length,
    firstSequence,
    lastSequence,
  };
}

function selfTest() {
  const linux = [
    { virtual_rc_valid: false, virtual_rc_channels: [0, 0, 0, 0, 0] },
    { virtual_rc_valid: true, virtual_rc_source_sequence: 42 },
    { virtual_rc_valid: true, virtual_rc_source_sequence: 43 },
  ];
  const flight = [{
    line: 1, rc_source: 1, rc_valid: 1, rc_seq: 43, rc_hb: 8,
    setpoint_valid: 1, pid_valid: 1, mixer_valid: 1, flight_ready: 1,
    armed: 1, failsafe: 0, dshot_ready: 1, dshot_busy: 0,
  }];
  const result = verify(linux, flight,
                        "self-test Linux", "self-test flight");
  assert(result.lastSequence === 43, "内置样例的序号关联失败");
}

const paths = process.argv.slice(2);
if (paths.length === 1 && paths[0] === "--self-test") {
  selfTest();
  console.log("S7.8 端到端检查：内置样例通过");
} else {
  if (paths.length !== 2) {
    console.error(
      "用法：node Tools/verify_s7_8_e2e.mjs Linux日志.jsonl 飞控日志.log");
    process.exit(2);
  }
  try {
    const result = verify(
      readLinuxRecords(paths[0]), parseE2eLines(paths[1]),
      paths[0], paths[1]);
    console.log("S7.8 端到端日志检查：通过");
    console.log(`Linux 有效虚拟 RC 帧：${result.linuxActive}`);
    console.log(`飞控选中 Linux RC 的 e2e 样本：${result.selected}`);
    console.log(`已关联的源序号范围：${result.firstSequence} 到 ${result.lastSequence}`);
  } catch (error) {
    console.error(`S7.8 端到端日志检查：不通过 - ${error.message}`);
    process.exit(1);
  }
}
```

内置走读：Linux 有效源 42、43；飞控选中时 `rc_seq=43`，后级所有必查字段合格；关联函数依次看到 42 和 43，最后保存 43。若飞控 `rc_seq=41`，找不到不晚于 41 的有效 Linux 源，检查失败。

第一次自测位置：**仓库根目录**。

```powershell
node Tools/verify_s7_8_e2e.mjs --self-test
```

正常输出 `S7.8 端到端检查：内置样例通过`。同样只证明工具自身最小路径。

## 真实日志怎样采集，且不覆盖旧证据

> **当前位置：`两份检查器已先自测 → [保存本次两端原始日志] → 中立和动作验收`**

每轮创建新的带日期目录，例如：

```text
evidence/s7_8_course_20260828_001/
├── linux.jsonl
├── linux.stderr.log
├── flight.log
├── hashes.txt
├── wiring.jpg
└── test_record.md
```

在 RK3568 板端启动时，分别重定向 stdout/stderr：

```sh
S7_6_RC_OUTPUT=/已确认的串口设备 \
./s7_6_live --camera \
  ./models/hand_detector_fp16.rknn \
  ./models/hand_landmarks_detector_fp16.rknn \
  /dev/video0 800 600 20 0 200 4776 \
  > ./evidence/s7_8_course_20260828_001/linux.jsonl \
  2> ./evidence/s7_8_course_20260828_001/linux.stderr.log
```

命令会占据当前 Shell，便于 Ctrl+C 安全结束。UART4 使用独立串口工具保存到 `flight.log`。不要用复制终端可见几行替代完整原始日志。

纯视觉练习可以把输出设备明确设 `/dev/null`，但那只验证 Linux 单端，不能生成飞控端到端证据。

## 从中立到三个动作的最小正确路径

> **当前位置：`两端正在记录 → [正常授权、动作和回中] → 故障注入`**

每一阶段都先记录开始状态，再操作，再记第一条结果：

| 阶段 | 只做的操作 | Linux 第一证据 | 飞控第一证据 | 通过标准 |
|---|---|---|---|---|
| 上电默认 | AUX1/2/3低、无手 | 有效UNKNOWN全零 | source=0、enter=0 | 绝不能默认虚拟源 |
| 未ARM授权尝试 | AUX3低→高，AUX1仍低 | 候选仍健康 | armed=0、source=0 | 未ARM不能进入 |
| 建立低位记忆 | AUX3回低，RPY回中 | 候选持续 | reauth=1 | 已见低位 |
| ARM未授权 | AUX1高，AUX3低 | 候选持续 | armed=1、source=0 | ARM不等于视觉授权 |
| 首次进入 | AUX3低→高 | source seq/hb前进 | source=1、enter+1 | 全门禁满足才进入 |
| 张掌 | 等ACTIVE并保持 | Pitch 0→负，1秒后回中 | rc_seq对齐，后级valid=1 | 只影响Pitch，不重复续期 |
| 单指 | 释放/冷却后重新ACTIVE | Pitch 0→正→0 | rc_seq对齐 | Roll/Yaw/Throttle/AUX不变 |
| V字 | 重新ACTIVE | Roll 0→负→0 | rc_seq对齐 | Pitch/Yaw/Throttle/AUX不变 |
| 健康无手 | 移开手 | valid=true UNKNOWN全零 | source仍1 | 不把健康空档当断线 |
| 物理油门 | 拆桨安全范围改变Throttle | Linux throttle仍0 | source仍1，实际油门/基础电机值跟物理 | 证明油门所有权 |

为什么每个动作都要等“重新 ACTIVE”？持续保持同一手势只触发一次。若为了方便快速摆动，状态机可能仍在 300 ms 冷却期；这不是丢命令，而是设计的防抖。

## 每一种失败都要只改变一个条件

> **当前位置：`正常链已经可关联 → [逐项故障退出和重授权] → 30分钟稳定性`**

每个退出测试都从同一基线开始：拆桨、物理 RC 有效、已 ARM、AUX3 已低高授权、RPY 居中、Linux 候选健康、`rc_source=1`。一项结束后，不沿用状态；恢复基线并再次 AUX3 低→高。

| 故障/操作 | Linux 第一证据 | 飞控第一证据 | 安全结果 | 失败时第一检查点 |
|---|---|---|---|---|
| AUX3 拉低 | Linux仍可能健康 | reason=1 AUTH_REVOKED | 当前周期回物理 | `aux3_us` 是否真的低于1700 |
| 物理 Roll 偏>150us | Linux仍健康 | reason=2 TAKEOVER | 回物理，输出当前物理值 | Receiver实际Roll与1500差值 |
| 物理 Pitch 偏>150us | 同上 | reason=2 | 同上 | Pitch校准和中心值 |
| 物理 Yaw 偏>150us | 同上 | reason=2 | 同上 | Yaw校准和中心值 |
| FIST | virtual_rc_valid=false、全零 | reason=3 VIRTUAL_INVALID | 立即回物理 | FIST是否真正ACTIVE、飞控last[v0] |
| 摄像头拔出/故障 | capture_failure/valid=false，进程可能退出 | reason=3或随后reason=4 | 不保留旧RPY | Linux stderr和最后JSONL |
| NPU推理失败 | inference_failure、无效释放 | reason=3 | 回物理 | 模型/Runtime错误，不先改仲裁 |
| deadline miss | reject_reason=deadline_miss、源无效 | reason=3 | 回物理 | 分段耗时和端到端ms |
| 杀Linux进程 | 心跳/JSONL停止 | age增至150ms，reason=4 | 约150ms+一个RcTask周期内退出 | 最后一帧时间和UART4时间基准 |
| 拔已确认TX线 | Linux本机仍写 | rx/frame停止，reason=4 | 超时回物理 | 线、共地、PC7，不改代码 |
| Linux进程重启 | heartbeat重新从小值开始 | restart/gen增加，活动时reason=5 | 流量恢复也不自动重入 | 会话代数与AUX3仍高 |
| CRC翻一位 | Linux正常日志不足以代表注入器 | crc计数+1 | 候选失效、回物理 | 抓到44字节并重算CRC |
| 版本/长度/保留位错 | 注入器记录 | fmt+1 | 回物理 | 偏移2/3/7 |
| 通道越界/手势轴不匹配 | 注入器记录 | fmt+1 | 回物理 | 偏移32～41和手势ID |
| 心跳重复/倒退 | 注入器记录 | seqerr+1 | 回物理 | 上一hb与当前hb |
| 有效源序号重复/倒退 | 注入器记录 | seqerr+1 | 回物理 | source_sequence和新会话边界 |
| 源时间>发送时间或年龄>250ms | 注入器记录 | timeerr+1 | 回物理 | 偏移16/24的单位与小端 |
| 无效帧带非零通道 | 注入器记录 | fmt+1 | 回物理 | valid位与五通道清零 |
| AUX3配置给ARM/ANGLE | Linux仍健康 | cfg=0，reason=9 | 禁止进入/立即退出 | 参数配置，不绕过检查 |
| arming inhibit非0 | Linux仍健康 | inhibit非0，reason=6 | 回物理并服从既有安全链 | 真实inhibit来源 |
| 物理RC失效 | Linux可能健康 | reason=8、failsafe相应变化 | 回物理安全/Failsafe | CRSF接收和既有Failsafe |
| DISARM | Linux仍健康 | reason=7、armed=0 | 电机安全，Linux不能重ARM | AUX1和飞行状态 |

非法帧必须用已验证的串口帧注入器或逻辑分析仪发送功能，一次只改一个字段。禁止短接电源、带电移动未知线、关闭 ARM/Failsafe 来“方便测试”。

每次退出后保持 AUX3 高并恢复合法流量 3 秒，必须仍是物理源。再 AUX3 拉低，看到 `reauth=1`，再拉高才可进入。这个复位流程本身也是验收内容。

## 真实日志检查只能在采集完成后第一次运行

> **当前位置：`正常与故障原始日志已完整保存 → [离线检查两端一致性] → 判读边界`**

把两端文件复制到 PC 的新证据目录，先算 SHA-256，保证后续分析针对同一文件。然后在仓库根目录运行：

```powershell
node Tools/verify_s7_8_trace.mjs `
  C:\实际证据目录\linux.jsonl

node Tools/verify_s7_8_e2e.mjs `
  C:\实际证据目录\linux.jsonl `
  C:\实际证据目录\flight.log
```

PowerShell 反引号表示命令换行，反引号后不能再有空格。请替换成真实路径。

第一份 PASS 证明该 Linux 文件至少包含有效和无效路径，且未发现序号/心跳/通道合同违规。第二份 PASS 证明日志中至少有一次飞控选中虚拟源，选中样本前能关联有效 Linux 源，且指定后级字段完整。

它们**不能证明**：

- 关键点肉眼贴合；
- 逻辑分析仪电压一定是 3.3 V；
- `armed` 一定为 1（当前脚本只解析，不纳入 badFields）；
- 电机顺序和旋向正确；
- 30 分钟没有复位；
- 可以装桨或飞行。

这些要由标注图、波形、人工日志检查、完整稳定性记录和独立飞行阶段证明。

## 出现问题时从最前面的断点开始查

> **当前位置：`自动检查给出结果 → [按证据链定位第一处断裂] → 稳定性边界`**

```text
没有摄像头sequence
  → /dev/video0、V4L2格式、MMAP、camera stderr

sequence增长但手部valid长期false
  → 模型SHA、RKNN Runtime、标注骨架、presence、deadline

手部valid但手势长期UNKNOWN/CANDIDATE
  → 五指几何分数、0.58/0.08、0.75、5帧/150ms、帧间隔

Linux virtual_rc正常但飞控rx不涨
  → 3.3V、共地、TX→PC7、115200 8N1、USART6中断

rx涨但frame不涨
  → GR魔数、丢字节、帧长、起始位置

frame涨但valid不涨
  → 先看crc/fmt/seqerr/timeerr中第一个增长的计数

virtual=1但source=0
  → armed、inhibit、cfg、reauth、AUX3、RPY中心

source=1但setpoint/PID/Mixer某层无效
  → 从第一处valid=0的后级模块查，不回头重装模型

e2e全通过但实物动作方向不对
  → RC方向、轴语义、电机顺序/旋向和物理验收；日志结构PASS不证明机械方向
```

不要一次更换 SDK、模型、阈值、串口和固件。那会消灭可比较性。每次只改一个已被证据指向的条件，使用新目录复验。

## 30 分钟稳定性到底证明什么

> **当前位置：`单次功能和故障均正确 → [长时观察资源、错误和源切换] → S7.8停止`**

拆桨条件下运行 30 分钟：前 10 分钟物理源；中间 10 分钟虚拟中立和三种动作；后 10 分钟重复授权、撤销、接管和安全故障。每分钟保存：

- Linux RSS、FD、温度、NPU 负载、帧数、丢帧和延迟；
- 飞控 `linux_rc` 四类错误、restart/uart；
- `rc source` 的 enter/exit/reason/age/gen；
- `e2e`、任务栈高水位、堆最低水位、复位/故障码。

正常判据：无复位、无栈溢出、无旧动作残留、无自动 ARM、无未经低高授权的自动重入；没有主动注入时错误计数不应无故增长；每次 enter 能对应一次授权，每次 exit 能对应唯一操作或故障。

30 分钟只能证明“这组硬件、产物、参数和环境在这 30 分钟内未观察到所列问题”。它不能证明未来永不故障、温度极限环境可靠、换线后仍可靠或已经获得装桨许可。

## 迁移练习：故意制造一条可定位的日志错误

不要碰真实 UART。复制一份 Linux JSONL 到实验目录，只把其中一条有效 UNKNOWN 中立记录的 Throttle 从 0 改为 1，原文件保持不动。先预测第一份脚本会在该记录报告 `active frame changed throttle/AUX`，再运行检查器确认。第二次实验把一条飞控 `e2e` 的 `pid_valid=1` 改为 0，预测端到端脚本指出该文件行和期望值。

这个练习只编辑副本，目的是学会把“检查失败”映射到具体合同；不能把伪造文件混入真实验收附件。

## 最终文字复盘和整系统图

从零开始，你现在应能说明：Windows 仓库保存源文件；WSL 用与板端 ABI 匹配的工具把模型转换成 RKNN、把 C++ 交叉编译成 AArch64 ELF；RK3568 动态加载程序和私有库，用 V4L2 从设备文件取得最新 NV12 帧，用两级 RKNN 得到 21 点；几何分类和状态机把单帧测量变成可靠 ACTIVE 手势；Mapper 只生成有界、限速、可过期、Throttle/AUX为0的候选；固定 44 字节用 CRC、序号、心跳和时间戳提供验证证据。

F722 从 PC7 的第一个字节开始找 GR、验完整帧，只产生候选快照。RcTask 同时读取物理 CRSF，仲裁器默认物理源；只有已 ARM、无 inhibit、AUX3 合法且先低后高、RPY居中、候选新鲜时才只替换 RPY。任何撤销、接管、无效、超时、重启、DISARM、物理 RC 失效或配置冲突都回物理源，并要求重新授权。原有 Failsafe、Setpoint、PID、Mixer、DShot 仍决定最终安全输出。
