# 拆桨完成端到端验收和故障定位

前面几章把每一层分别讲开了。这一章要做的事情很朴素：把这些层重新连起来，确认数据确实从摄像头一路走到了飞控原有控制链，而且任何异常都能让系统退出到安全状态。

这里不是教你写日志检查脚本。仓库里的检查脚本是开发阶段用于核对结果的工具，不是你理解 Linux 和飞控链路的前置知识。本章只讲人应该怎样观察、怎样判断，以及为什么按这个顺序判断。

## 1. 先说清楚这次验收能证明什么

这次验收是在**拆掉全部螺旋桨**的条件下进行的。

它要证明：

- RK3568 能连续取得摄像头画面；
- 两个 RKNN 模型能得到手部关键点；
- 关键点能稳定形成手势事件；
- 手势事件能形成正确、受限、够新的虚拟 RC 候选；
- F722 能正确收帧并拒绝坏帧；
- 只有满足授权条件时，飞控才采用虚拟 Roll、Pitch、Yaw；
- Throttle、ARM 和全部 AUX 始终属于物理遥控器；
- 物理接管、断线、超时、程序重启、DISARM 等情况能让系统退出；
- 最终 RC 变化能继续传到 setpoint、PID、Mixer 和 DShot 这一条原有链路。

它不能证明：

- 装桨后飞行一定稳定；
- 当前 PID 参数适合实际机体；
- 视觉控制在室外、远距离、逆光和振动中都可靠；
- 所有手势、速度和方向都适合真实飞行；
- S7.9 已经开始或已经获得飞行许可。

仓库的统一进度文档记录，S7.1～S7.8 已经在 2026 年 8 月完成，并冻结为 `v1.6.0-s7.8-gesture-rc-baseline`。这是当时那套硬件、接线、模型、程序、固件和参数的历史验收结果。

本教程的重写没有重新完成实物 30 分钟运行，也没有重新做电机动作验收。因此，历史通过不能自动等同于你现在手里的设备也已经通过。你仍要按本章重新核对当前实物。

## 2. 为什么端到端验收不能只看最后电机动没动

假设电机没有出现预期差动，原因可能在任何一层：

```text
摄像头没有新画面
→ 没检测到手
→ 关键点不对
→ 手势没有稳定
→ 没形成候选
→ 串口没有收到
→ 帧被 CRC 或时间检查拒绝
→ AUX3 没授权
→ 仲裁器仍在物理源
→ 最终 RC 没变化
→ setpoint 没变化
→ PID 或 Mixer 没形成差动
→ DShot 没输出预期命令
```

只盯着最后一级，会把十几个可能原因混在一起。

正确思路是：**从数据的起点往后看，找到第一个不符合预期的位置。**

一旦找到第一个断点，后面没有变化通常只是它的结果，不是新的故障。

## 3. 通电前的安全准备

这部分不是形式要求。飞控软件、接线或手势方向任何一项有误，都可能让电机突然转动。

通电前逐项确认：

1. 四个电机的螺旋桨全部拆下，不是只拆一部分；
2. 机架固定，不会因电机转动从桌面滑落；
3. 电机、电调和人员周围没有松散导线或其他会被卷入的物品；
4. 物理遥控器已经绑定，失控保护已确认；
5. Throttle 在最低位；
6. Roll、Pitch、Yaw 摇杆回中；
7. ARM、ANGLE、视觉授权 AUX3 在上电前都处于低位；
8. RK3568 UART 使用 3.3 V TTL 电平；
9. RK3568 与 F722 共地；
10. RK3568 TX 接 F722 PC7，也就是 USART6 RX；
11. 没有把 5 V 串口电平直接接到 3.3 V 接收脚；
12. 物理 CRSF 仍使用它原来的串口，没有被这根 Linux 串口线占用。

测试时，手要能随时拨低 AUX3、DISARM 或切断动力电源。不要把“程序应该会退出”当作唯一保护。

## 4. 先认识要观察的三组信息

验收时需要同时看 Linux 端和 F722 端。两边记录的不是同一件事。

### Linux 端：这份候选是怎么产生的

Linux 每一帧的输出通常包含这些信息：

| 信息 | 它回答的问题 |
|---|---|
| 画面序号和时间 | 摄像头画面是否一直向前更新 |
| 是否检测到手 | 第一阶段有没有找到手 |
| 关键点和推理状态 | 第二阶段是否真的得到可用结果 |
| 手势名称、置信度和状态 | 当前只是单帧判断，还是已经稳定成为事件 |
| `active_gesture` | 状态机这一次真正批准了什么手势 |
| `virtual_rc_valid` | 当前发出的是健康候选还是无效释放 |
| 源序号和心跳 | 数据来源和发送循环是否都在向前走 |
| 五个候选通道 | Roll、Pitch、Yaw 是否匹配手势，Throttle/AUX 是否保持 0 |

Linux 端能说明“我准备发送什么”。它不能单独证明 F722 真的收到了，也不能证明飞控采用了这些值。

健康无手时，应当看到有效的中立候选：手势为 `UNKNOWN`，五个候选通道全为 0。

摄像头失败、推理失败、数据过期或握拳释放时，应当看到无效候选，而且通道全为 0。无效候选绝不能继续带着上一条姿态值。

### F722 的 `linux_rc`：串口和协议是否通过

这组信息回答：

- 字节有没有进入 USART6；
- 有没有收满 44 字节；
- 有多少帧通过检查；
- CRC、格式、序号、时间或 UART 错误是否增加；
- F722 最后看到的心跳、源序号、手势和通道是什么。

它能证明候选已经到达并通过协议检查，但仍不能证明仲裁器采用了候选。

### F722 的 `rc source` 和 `e2e`：是否采用并继续向后传

`rc source` 用于判断当前是物理源还是虚拟源，以及为什么没有进入或为什么退出。重点是：

- 当前来源；
- AUX3 当前高低；
- 是否已经见过 AUX3 低位；
- 是否 ARM；
- 是否有 inhibit；
- AUX3 配置是否可用；
- 候选是否有效、年龄多大；
- 最近一次退出原因。

`e2e` 用于继续观察最终 RC、setpoint、PID、Mixer、DShot 是否跟着变化。

所以三组信息的关系是：

```text
Linux 输出：我打算发送什么
linux_rc：飞控是否完整、正确地收到了
rc source：飞控现在是否允许采用
e2e：采用后是否沿原控制链传下去
```

## 5. 第一次通电不要马上做手势

先建立一个“什么都不控制”的正常起点。

上电后保持：

- 物理遥控器有效；
- Throttle 最低；
- R/P/Y 居中；
- ARM 低；
- AUX3 低；
- 摄像头前没有用于触发的手势。

这时应该看到：

1. Linux 画面序号持续增加；
2. 没有手时，Linux 发送健康中立帧，而不是旧动作；
3. Linux 心跳持续增加；
4. F722 的 USART6 接收字节数、完整帧数和有效帧数持续增加；
5. CRC、格式、序号和时间错误不应持续增加；
6. `rc source` 仍是物理源；
7. 最终 RC 与物理遥控器一致。

这一阶段证明的是“链路健康但没有获得控制权”。这是后面所有动作测试的基础。

如果连这个起点都不正常，不要继续 ARM，也不要做手势。先找到前面哪一层断了。

## 6. 正常进入虚拟源的完整顺序

在保持拆桨的前提下，按下面顺序进行。

### 第一步：确认物理遥控器仍是唯一来源

轻微移动物理 Roll、Pitch、Yaw，确认最终 RC 会跟随；然后全部回中。

这样可以证明物理链路、通道映射和中心值正常。若物理 RC 本身无效，虚拟源本来就不允许进入。

### 第二步：由物理遥控器完成 ARM

Linux 没有 ARM 权限。ARM 状态必须来自物理 AUX。

如果无法 ARM，先处理原有的 arming inhibit，不要把它当成 Linux 问题。只有 ARM 成功且 inhibit 为 0，才继续。

### 第三步：让 AUX3 从低拨到高

低到高是一次人工授权。与此同时，物理 R/P/Y 必须在中心附近，Linux 候选必须有效且新鲜。

满足后，`rc source` 应从物理变为虚拟。进入时最终三轴从当前物理中心开始，不应突然跳到目标值。

### 第四步：先保持无手

无手时，Linux 应继续发送有效中立候选。飞控可以保持虚拟源，但 R/P/Y 目标为中立。

这一步很重要，因为“没有动作”不等于“链路断了”。健康无手和故障释放是两个不同状态：

- 健康无手：链路活着，候选有效，通道为 0；
- 故障释放：候选无效，飞控应退出虚拟源。

## 7. 三种动作分别应该看到什么

每种手势都先从中立开始，稳定保持到状态机产生一次新的 `ACTIVE`，然后观察 1 秒动作脉冲和回中。

### 张掌 `OPEN_PALM`

正确链路是：

```text
张掌稳定
→ active gesture = OPEN_PALM
→ Linux 候选 Pitch = -300
→ F722 收到相同手势和通道
→ 最终 Pitch 从 1500 向 1200 平滑变化
→ setpoint、PID、Mixer、DShot 出现对应变化
→ 1 秒后候选回中
```

### 单指 `POINT`

正确结果是 Pitch = `+300`，最终 Pitch 从 1500 向 1800 平滑变化。其他姿态轴保持中立。

### V 字 `V_SIGN`

正确结果是 Roll = `-300`，最终 Roll 从 1500 向 1200 平滑变化。Pitch 和 Yaw 保持中立。

当前 Yaw 候选始终为 0。若你看到 Yaw 随这三种手势变化，不要解释成“正常算法差异”，而应当检查手势和通道映射是否与当前基线一致。

每个新 `ACTIVE` 只触发一次约 1 秒的命令，不是手一直摆着就永久压住摇杆。同一个手势要经过释放和冷却，再重新稳定，才会形成下一次事件。

## 8. 验收物理 Throttle 一直归物理遥控器

虚拟源已经启用时，在拆桨条件下缓慢改变物理 Throttle。

应该看到：

- 最终 Throttle 跟随物理遥控器；
- Linux 候选里的 Throttle 仍是 0；
- 改变 Throttle 不会因为“Linux 没给油门”而把实际油门拉回 0；
- 仅改变 Throttle 不会触发三轴物理接管，因为 Throttle 本来就没有交给 Linux。

这一步证明的不是电机推力是否正确，而是控制权边界是否正确：Linux 只替换 R/P/Y，物理 Throttle 一直在线。

## 9. 验收物理三轴可以立即接管

重新完成 AUX3 低到高授权并进入虚拟源，然后把任一物理 R/P/Y 摇杆推离中心超过约 150 μs。

应该看到：

1. `rc source` 立即回到物理；
2. 退出原因是物理接管；
3. 最终 R/P/Y 立即使用物理遥控器；
4. 摇杆回中后，只要 AUX3 还保持高位，就不会自动重进；
5. 必须把 AUX3 拨低，再拨高，才能重新授权。

这一步验证的是人在任何时候都能主动拿回三轴控制。

## 10. 验收握拳是主动释放，不是另一个动作

重新进入虚拟源后，稳定做出 `FIST`。

应该看到：

- Linux 将候选变为无效；
- 五个候选通道全部为 0；
- F722 退出虚拟源；
- 退出原因是候选无效；
- 物理遥控器重新成为来源；
- AUX3 即使还在高位也不会自动重进；
- 需要新的 AUX3 低到高授权。

握拳的作用是“我不要 Linux 继续提供候选”，不是要求某个姿态方向。

## 11. 故障测试为什么一次只能改一个条件

如果你同时拔摄像头、断串口并停止 Linux 进程，系统也许会退出，但你不知道究竟是哪条保护先起作用，更不知道另外两条是否真的有效。

每次只改变一个条件，观察预期的第一处变化，然后恢复正常、重新授权，再测下一项。

下面每项都在拆桨条件下进行。

### 摄像头断开

预期过程：

```text
画面序号停止或采集失败
→ Linux 候选变为无效
→ F722 收到无效候选或随后超时
→ 退出虚拟源
→ 必须重新授权
```

如果 Linux 仍持续发送旧的有效动作值，问题在 Linux 的失效处理，而不是飞控后级。

### 停止 Linux 主程序

串口数据会停止。F722 最近候选的年龄达到 150 ms 后，应退出虚拟源。Linux 程序重新启动后，也不能自动恢复控制；需要新的 AUX3 低到高授权。

### 断开 UART 线

Linux 自己可能仍显示识别和候选正常，但 F722 的接收字节不再增加，随后候选超时并退出。

这正好说明为什么不能只看 Linux 屏幕：发送端“准备好了”不等于接收端“收到了”。

### 让一帧 CRC 错误

错误帧应使 CRC 错误计数增加，不能更新为有效候选。旧候选也不能因为错误新帧而无限续命。

这里的目标是证明飞控会拒绝损坏数据，不是学习怎样写一个制造坏帧的工具。若项目已有测试工具，可直接使用它；不需要把工具本身当作本课程内容。

### 发送过期时间

如果 Linux 的源时间到发送时间超过 250 ms，F722 应记为时间错误并拒绝。这模拟的是摄像头或推理队列严重积压，虽然串口仍有数据，但那些数据已经太旧。

### 重复心跳或源序号

重复值应被识别为数据没有向前走。它用于区分“程序真的产生新结果”和“旧结果被反复发送”。

### 重启 Linux 程序

F722 应识别新会话。如果重启发生在虚拟源期间，应退出并要求重新授权。新程序恢复正常发送不应自动取得控制权。

### DISARM

由物理遥控器 DISARM 后，虚拟源必须立即退出。再次 ARM 后仍要重新完成 AUX3 低到高。

### 制造 arming inhibit

只要飞控认为当前存在禁止条件，就不能进入或继续虚拟源。先通过飞控诊断明确 inhibit 的真实原因，不要为测试随意绕过安全检查。

### 物理 RC 进入 failsafe

物理 RC 失效时，虚拟源必须退出，而且原有 failsafe 继续负责安全输出。Linux 不能因为自己还活着就替代物理 RC 的基础安全地位。

## 12. 根据“第一个异常”定位故障

| 第一个不正常的现象 | 故障大概率在哪一层 | 先检查什么 |
|---|---|---|
| Linux 画面序号不动 | 摄像头采集 | `/dev/video*`、设备占用、格式、供电和连接 |
| 有画面但始终检测不到手 | 检测模型或输入画面 | 光照、手的大小、预处理、检测结果 |
| 有手框但关键点明显错误 | 关键点模型或 ROI | 裁剪区域、缩放、坐标还原、模型输入输出 |
| 单帧手势会变化，但始终不 `ACTIVE` | 几何分类或时间状态机 | 最高分、分差、0.75、5帧、150 ms |
| 已 `ACTIVE`，但候选通道不对 | 手势到 RC 映射 | 手势名称、方向、1秒脉冲、限速 |
| Linux 正常，F722 `rx` 不增加 | 串口电气层 | 共地、3.3 V、TX→PC7、115200 8N1 |
| `rx` 增加，完整帧很少 | 帧同步或丢字节 | `G R`、固定 44 字节、连续发送 |
| 完整帧增加，`valid` 不增加 | 协议检查 | CRC、版本、范围、手势匹配、时间、序号 |
| 有效帧增加，来源仍是物理 | 仲裁进入条件 | ARM、inhibit、AUX3配置、低→高、RPY居中、150 ms |
| 已进入但很快退出 | 某个安全条件触发 | 最近退出原因、物理接管、超时、重启、无效候选 |
| 最终 RC 变化，setpoint 不变 | 模式或目标生成 | 当前飞行模式、RC 到 setpoint 映射 |
| setpoint 变化，PID 不变 | 控制器输入或状态 | 姿态反馈、控制器是否运行、限制条件 |
| PID 变化，Mixer/DShot 不对 | 输出分配或电机链 | Mixer方向、电机编号、DShot状态，继续保持拆桨 |

不要跳过前面的层直接改 PID。视觉链路的故障如果发生在摄像头或串口，改 PID 不会解决它，反而会引入新的变量。

## 13. 怎样判断一次正常动作确实走完了整条链

以张掌为例，理想证据应该前后对应：

1. Linux 的画面序号向前；
2. 检测器找到手；
3. 关键点结果有效；
4. 单帧分类连续稳定为 `OPEN_PALM`；
5. 状态机从候选变成新的 `ACTIVE`；
6. Linux 建立 Pitch = `-300` 的一次动作；
7. 心跳和源序号继续递增；
8. F722 的有效帧计数增加，看到相同手势和通道；
9. `rc source` 已经是虚拟源；
10. 最终 Pitch 从中点向 1200 μs 平滑移动；
11. setpoint 发生对应方向变化；
12. PID、Mixer、DShot 出现符合当前机体定义的差动；
13. 约 1 秒后候选回中，最终 Pitch 平滑回中。

如果第 1～8 项正确，第 9 项不正确，就查授权条件；不要回头修改模型。

如果第 9～10 项正确，第 11 项不正确，就查 RC 到 setpoint 的已有映射；不要修改串口协议。

这就是“从第一个断点查”的实际用法。

## 14. 30 分钟稳定运行到底要看什么

短时间成功只能说明链路在某个时刻能工作。30 分钟运行是为了观察随着时间累积才容易出现的问题，例如：

- 摄像头帧是否停止更新；
- 推理是否越来越慢；
- 画面是否积压，源时间越来越旧；
- Linux 进程是否崩溃；
- 内存占用是否持续增长；
- 心跳和源序号是否停止；
- UART 错误、CRC 错误是否持续增加；
- F722 是否出现错误退出或意外重进；
- 无手时是否一直保持健康中立；
- 物理接管和重新授权在长时间后是否仍然有效。

30 分钟稳定并不证明以后永远不会出错，也不证明装桨飞行安全。它只是为“在当前桌面条件下，没有明显的短期资源泄漏、积压或链路失活”提供证据。

## 15. 验收结果应该怎样记录

记录的目的不是堆很多文件，而是以后能回答四个问题：

1. 当时使用的是哪一版 Linux 程序、模型和飞控固件？
2. 当时怎样接线，串口设备和参数是什么？
3. 正常动作和每个故障条件实际出现了什么？
4. 哪些是在实物上看到的，哪些只是从源码或主机检查得到的？

建议至少保存：

- 固件版本或 Git 提交号；
- RK3568 程序和模型文件的哈希；
- 摄像头节点、串口节点和串口参数；
- Linux 端原始输出；
- F722 UART4 原始输出；
- 接线照片；
- 每个测试项的条件、预期、实际结果和结论；
- 明确写出“已拆桨”。

不要只写“测试通过”。没有版本、条件和原始现象的“通过”，以后很难复现，也无法判断换了硬件或程序后是否仍然成立。

## 16. 本教程到哪里结束

本教程的目标是让 Linux 基础为 0 的学习者理解并能搭建下面这条链：

```text
Windows / WSL 准备板端文件
→ RK3568 Linux 运行程序
→ IMX335 / V4L2 取得画面
→ RKNN 检测手并得到 21 个关键点
→ 几何规则判断单帧手势
→ 时间状态机确认一次手势事件
→ 生成受限的虚拟 RC 候选
→ 44 字节串口帧到 F722 USART6
→ 飞控检查并保存候选
→ 物理 / 虚拟 RC 仲裁
→ 原有 setpoint / PID / Mixer / DShot 链
```

更重要的是，你应该已经知道每条箭头为什么存在：

- V4L2 把具体摄像头变成 Linux 可以统一使用的视频设备；
- 两阶段 RKNN 先找手，再找关节，减少无关区域干扰；
- 几何分类把关键点变成手势，但单帧结果还不够可靠；
- 时间状态机把稳定手势变成一次事件，避免抖动和重复触发；
- 虚拟 RC 层限制 Linux 的数值和权限；
- 串口帧用长度、时间、序号、心跳和 CRC 让飞控能判断数据是否可信；
- 飞控仲裁器保留物理遥控器的最终安全权；
- 原有控制链继续负责真正的姿态和电机控制。

课程在拆桨端到端验收这里结束。S7.9、装桨和受控飞行需要另外的安全条件、场地、人员、参数确认和实物验收，不能因为 S7.8 历史上通过就自动开始。
