# 从摄像头画面到 21 个手部关键点

> **文档进度：`课程地图 → Linux基本操作 → 构建与部署 → [本篇：实时摄像头与两级NPU推理] → 手势判断`**
>
> **真实数据流位置：`IMX335光学图像 → /dev/video0 → NV12帧 → 手框 → 手部ROI → 21个关键点 → JSONL`**
>

上一篇已经得到：两个面向 RK3568 的 FP16 `.rknn` 模型、一个 AArch64 程序以及板端所需动态库。现在仍缺的是“实时输入”。离线图片能推理，不代表摄像头能持续送帧，也不代表处理速度跟得上摄像头。


## 程序为什么能在自己的目录找到动态库

> **当前位置：`程序和库已经复制到板端 → [理解启动时怎样找到.so] → 打开摄像头设备`**
>
> 本节只解决程序启动阶段。完成后，Linux 才有机会执行摄像头代码。

程序运行前，Linux 的**动态加载器**会读取 ELF 中记录的依赖，例如 `libopencv_core.so` 和 `librknnrt.so`。动态加载器可以理解为“程序开门前的库管理员”：缺少任意必需 `.so`，`main()` 还没开始就会退出。

构建脚本里的：

```sh
-Wl,-rpath,'$ORIGIN/lib'
```

在第一次使用它前，先拆开：

- `-Wl,内容`：让 `g++` 把后面的内容交给链接器；链接器负责把程序和库的引用连起来。
- `-rpath`：把运行时搜索路径写进 ELF。
- `$ORIGIN`：动态加载器认识的特殊名字，表示“当前 ELF 自己所在的目录”，不是 Shell 的普通变量。
- `'$ORIGIN/lib'` 外面的单引号：阻止构建时的 Shell 提前把 `$ORIGIN` 当变量展开。

假设板端目录是：

```text
/userdata/linux_course/s7_4/
├── s7_4_live
└── lib/
    ├── libopencv_core.so.4.5
    ├── libopencv_imgproc.so.4.5
    └── librknnrt.so
```

那么程序中的 `$ORIGIN/lib` 实际指向 `/userdata/linux_course/s7_4/lib`。这使部署目录可以整体移动，不必把私有 OpenCV 覆盖到板子的 `/usr/lib`。

第一次检查依赖时，在 **RK3568 板端 Shell**、部署目录中运行：

```sh
readelf -d ./s7_4_live | grep -E 'NEEDED|RPATH|RUNPATH'
```

`readelf -d` 只读取 ELF 的动态段；`grep -E` 只保留依赖库和搜索路径。正常应看到需要的 `.so` 以及 `$ORIGIN/lib`。若运行时报 `not found`，第一检查点不是摄像头，而是 `lib/` 中的库名和符号链接是否完整。

## `/dev/video0` 为什么看起来像文件

> **当前位置：`程序已经能启动 → [理解摄像头在Linux中的入口] → 请求画面格式`**
>
> 本节只建立设备文件和文件描述符。还不开始取帧。

Linux 把很多硬件入口放在 `/dev` 目录。`/dev/video0` 不是保存视频内容的普通文件，而是一个**设备文件**：程序对它执行打开、查询和读取动作时，Linux 把这些动作转交给摄像头驱动。

```text
路径 /dev/video0
   ↓ open()
文件描述符 fd，例如3
   ↓ ioctl(fd, 请求, 参数)
摄像头驱动
```

首次出现的名字：

- `open()`：POSIX 系统调用，用路径打开对象；成功返回非负整数，失败返回 `-1` 并设置 `errno`。
- `fd`：file descriptor，文件描述符。它只是当前进程里的一个小整数，代表已经打开的对象。
- `ioctl()`：input/output control，向设备发送“普通读写表达不了”的控制请求，例如设置分辨率。
- `errno`：最近一次失败的系统调用留下的错误编号。
- `O_RDWR`：以可读、可写方式打开；写权限用于给驱动发配置。
- `O_NONBLOCK`：没有现成帧时立即返回，不让线程永远卡死。

对应的 C++ 定义位于 `Camera` 构造函数开头：

```cpp
fd_ = open(device, O_RDWR | O_NONBLOCK);
if (fd_ < 0) fail("open camera");
```

具体走读：若 `device` 是 `/dev/video0`，打开成功并返回 `3`，则 `fd_=3`。后面的所有 V4L2 请求都发给 3 所代表的摄像头。若设备不存在，`open()` 返回 `-1`，程序立即形成 `open camera: No such file or directory`，不会伪造空画面继续运行。

第一次只读确认使用两个已经能解释的动作：`ls -l` 查看设备文件；`v4l2-ctl` 是 Video4Linux2 的检查程序，`-d` 指定设备，`--all` 查询驱动、格式和控件。它们都不启动项目模型。

在 **RK3568 板端 Shell** 运行：

```sh
ls -l /dev/video0
v4l2-ctl -d /dev/video0 --all
```

正常输出能证明驱动提供了这个入口，不能证明项目模型已经推理成功。

## V4L2 怎样把一帧送进进程

> **当前位置：`已打开设备文件 → [设置格式并建立缓冲队列] → 等待最新帧`**
>
> **真实数据流：`RKISP驱动 → MMAP缓冲 → Camera::latest()`**

### 为什么不能把摄像头当成一张 JPEG

摄像头持续产生原始像素。项目使用 **V4L2**，全称 Video4Linux2，它是 Linux 用户程序和视频驱动之间的标准接口。当前板子的图像信号处理器叫 **RKISP**；它把 IMX335 的传感器数据处理后暴露为 V4L2 捕获节点。

当前驱动报告 `Video Capture Multiplanar`。这里的“multiplanar”表示接口结构允许一帧由多个内存平面组成；但本项目要求 `num_planes=1`，即 NV12 的 Y 与 UV 数据在同一块连续内存里。接口类型是多平面，不等于实际一定分配多个内存块。

**NV12** 是一种 YUV 像素格式：前 `width × height` 字节保存亮度 Y，后面交错保存 U、V 色度。800×600 一帧需要 `800 × 600 × 3 / 2 = 720000` 字节。它不是 RGB，所以不能直接按红、绿、蓝三字节读取。

### 设置格式的输入、输出和失败出口

这段代码位于 `Camera::Camera()`。输入是期望宽、高、NV12；输出是驱动最终接受的格式。驱动允许调整请求，所以设置后必须读回，而不是假设请求值一定生效。

```cpp
v4l2_format format{};
format.type = V4L2_BUF_TYPE_VIDEO_CAPTURE_MPLANE;
format.fmt.pix_mp.width = width;
format.fmt.pix_mp.height = height;
format.fmt.pix_mp.pixelformat = V4L2_PIX_FMT_NV12;
format.fmt.pix_mp.num_planes = 1;
call(VIDIOC_S_FMT, &format, "VIDIOC_S_FMT");
if (format.fmt.pix_mp.pixelformat != V4L2_PIX_FMT_NV12 ||
    format.fmt.pix_mp.num_planes != 1) {
    throw std::runtime_error("camera did not accept NV12");
}
```

首次出现的符号：

- `VIDIOC_S_FMT`：set format，让驱动设置并回填格式。
- `V4L2_BUF_TYPE_VIDEO_CAPTURE_MPLANE`：选择多平面捕获接口。
- `V4L2_PIX_FMT_NV12`：请求 NV12。
- `format{}`：把结构体先清零，避免未初始化字段进入内核。
- `call()`：项目内辅助函数；它调用 `ioctl()`，被信号打断时重试，其他失败转成异常。

具体走读：输入 800×600，驱动若仍回填 NV12、单内存平面，`width_` 和 `height_` 保存实际值。若驱动改成其他格式，程序立即退出；否则后面的 NV12 转换会把错误字节布局解释成颜色，产生花屏或错误推理。

### 为什么使用 MMAP 缓冲

`MMAP` 是 memory map 的缩写，意思是把驱动管理的缓冲区映射到进程地址空间。程序不必每帧额外复制整块数据。

```text
VIDIOC_REQBUFS：请求4个缓冲
   ↓
VIDIOC_QUERYBUF：逐个取得大小和映射偏移
   ↓
mmap：映射到进程地址
   ↓
VIDIOC_QBUF：把空缓冲交给驱动
   ↓
VIDIOC_STREAMON：开始采集
```

- `QBUF` 是 queue buffer，把可写缓冲排入驱动队列。
- `DQBUF` 是 dequeue buffer，从完成队列取出一帧。
- 4 个缓冲允许驱动写下一帧时，程序处理当前帧。
- 析构时先 `STREAMOFF`，恢复改过的 `VBLANK`，再 `munmap` 和 `close`，避免驱动仍写入已经解除映射的地址。

`VBLANK` 是 vertical blanking，垂直消隐行数。它会影响传感器一帧的总时长，项目把它保留为板端实测调节项。`4776` 是历史验收值，不是所有摄像头都适用的通用常数；另换传感器必须重新测。

## 为什么必须丢旧帧，只处理最新一帧

> **当前位置：`驱动缓冲已经流动 → [取得最新画面并统计丢帧] → 颜色转换`**
>
> 本节解决实时性，不解决识别准确率。

假设摄像头每 50 ms 产生一帧，但程序一度花了 150 ms。如果按顺序处理积压帧，屏幕显示的是越来越旧的动作；即使每帧都识别正确，控制链也会因为延迟而危险。

```text
poll 最多等待1000 ms
   ├─ 超时 → 返回false，输出capture_timeout
   ├─ 断开 → 抛异常，输出capture_failure后退出
   ↓ 有帧
反复 DQBUF
   ├─ 还有更晚帧 → 旧帧立即QBUF归还
   └─ EAGAIN → 已经排空
只把最后一帧交给推理
```

首次出现的符号：

- `poll()`：等待某个文件描述符出现事件，可设置超时，所以摄像头卡住时程序仍能留下失效记录。
- `POLLIN`：有数据可取。
- `POLLERR/POLLHUP/POLLNVAL`：设备错误、断开或描述符无效。
- `EAGAIN`：非阻塞模式下“现在暂时没有更多数据”，不是致命错误。
- `sequence`：驱动给帧的递增序号。
- `dropped_frames`：通过序号间隙和主动丢弃累计出来的旧帧数。

具体走读：完成队列里依次有序号 100、101、102。程序先取 100；又取到 101，就把 100 重新排回；又取到 102，就把 101 排回；下一次返回 `EAGAIN`，于是只处理 102。这样损失两帧覆盖率，却阻止延迟无限累积。

推理完成或发现坏帧后，必须调用 `Camera::release(frame)` 把当前缓冲 `QBUF` 回驱动。漏掉它会让可用缓冲越来越少，最终采集停住。

## 一帧为什么要经过两个模型

> **当前位置：`拿到最新NV12 → [颜色转换、检测、ROI、关键点] → 输出记录`**
>
> **真实数据流：`NV12 → BGR → RGB → 192×192检测 → 224×224关键点`**

一个模型若直接在整张 800×600 图上精确找 21 个点，会同时承担“手在哪里”和“手指细节是什么”两个问题。当前开源方案把任务拆成两级：

1. **检测模型**看缩放后的整幅图，找手框和 7 个方向参考点。
2. **ROI** 是 region of interest，感兴趣区域。程序依据手框和参考点裁剪、放大并旋正手部区域。
3. **关键点模型**只看 224×224 的手部 ROI，输出 21×3=63 个数、存在分数和左右手分数。

```text
800×600 NV12
  │ cvtColor(YUV2BGR_NV12)
800×600 BGR
  │ cvtColor(BGR2RGB) + 保持比例缩放/黑边
192×192 RGB
  │ detector.run()
2016个候选 → 分数阈值0.75 → 加权NMS(IoU 0.3)
  │
最高优先手框 + 7参考点
  │ 仿射变换：平移、缩放、旋转
224×224 RGB ROI
  │ landmark.run()
21个ROI坐标 + presence + handedness
  │ 逆仿射变换
21个整图归一化坐标
```

### `Model` 怎样调用 RKNN Runtime

`Model` 对象的输入是 `.rknn` 文件路径，长期保存模型字节、RKNN 上下文和输出信息。构造失败就抛异常，不会留下“半初始化模型”。

- `rknn_init`：从模型字节创建 NPU 上下文。
- `rknn_query`：查询输入/输出张量数量和属性。
- `rknn_inputs_set`：把本帧 RGB uint8 缓冲交给输入 0。
- `rknn_run`：启动一次 NPU 推理。
- `rknn_outputs_get`：取回输出；项目要求转换成 float，方便后处理。
- `rknn_outputs_release`：归还 Runtime 管理的输出资源。
- `rknn_destroy`：对象销毁时释放上下文。

`Model::run()` 只有在确认 `rgb` 是连续的三通道 8 位图像后才设置输入。调用顺序必须是“设置输入 → 运行 → 取得输出 → 复制结果 → 释放 Runtime 输出”。先释放再复制会读到无效内存。

### 具体一帧走读

假设驱动给出序号 102、720000 字节：

1. `cv::cvtColor` 把 800×900 的单通道 NV12 内存视图转换成 800×600 BGR。
2. `print_record()` 再把 BGR 转成 RGB，因为模型冻结合同是 RGB。
3. 检测输入保持比例缩到 192×144，上下各补 24 像素黑边。
4. 检测输出 2016 个候选；低于 0.75 的候选被拒绝，重叠候选按 IoU 0.3 合并。
5. 最优手框经反缩放回到 800×600 坐标，依据参考点计算旋转角。
6. 仿射变换得到 224×224 手部 ROI。
7. 关键点模型输出 63 个坐标；逆仿射把每个点送回整图坐标并除以宽高。
8. `presence_score >= 0.5` 才令该帧 `valid:true`；超出最大端到端延迟时，即使看见手也强制 `valid:false` 和 `deadline_miss`。

这证明 `valid` 表示“本帧手部观测可用”，不是“某个手势已经可靠成立”。可靠手势要由下一篇跨帧状态机完成。

## JSONL 为什么适合逐帧留证

> **当前位置：`21个关键点已经得到 → [把一帧写成一条可检查记录] → 稳定性运行`**

JSON 是带字段名的文本对象。**JSONL** 是 JSON Lines 的缩写：每一行都是一个独立 JSON 对象。程序崩在第 1000 帧时，前 999 行仍可单独读取。

| 字段 | 含义 |
|---|---|
| `sequence`、`capture_timestamp_us` | 驱动帧号和采集时间，`us` 表示微秒 |
| `complete_timestamp_us`、`end_to_end_ms` | 完成时间和从采集到完成的延迟，`ms` 表示毫秒 |
| `detector_score`、`presence_score`、`landmarks_21x3_image` | 单帧模型结果 |
| `dropped_frames`、`valid`、`reject_reason` | 实时性、是否可用和拒绝原因 |

无手、低存在分数、坏帧、超时、推理异常不能复用上一帧的坐标。它们要产生新的 `valid:false` 记录。典型拒绝原因是 `no_hand`、`low_presence`、`bad_frame`、`capture_timeout`、`capture_failure`、`inference_failure` 和 `deadline_miss`。

```json
{"sequence":102,"capture_timestamp_us":123400000,"complete_timestamp_us":123465000,"end_to_end_ms":65.0,"dropped_frames":2,"presence_score":0.93,"valid":true,"reject_reason":""}
```

具体走读：`123465000-123400000=65000 us=65 ms`，低于 200 ms；`presence_score=0.93` 高于 0.5，所以保持有效。若同一帧耗时为 230 ms，最终必须改为 `valid:false` 和 `deadline_miss`，不能因为模型置信度高就放行陈旧结果。

## 先读懂板端显示预检查脚本，再决定要不要直显

> **当前位置：`推理和JSONL主链已完整 → [可选屏显旁路] → 构建`**
>
> 屏显不是识别必需项。没有屏幕也能通过 JSONL 和保存的标注帧验收。

**DRM** 是 Direct Rendering Manager，Linux 内核管理显示硬件的接口。**KMS** 是 Kernel Mode Setting，负责连接器、分辨率、扫描输出等显示模式。`/dev/dri/card0` 是显示设备文件。connector 是物理输出连接；CRTC 可先理解为“按固定节奏把帧缓冲扫描到连接器的显示通道”；framebuffer 是一张准备显示的像素缓冲。

板端可能已有 Weston 图形合成器占用 DRM master。项目直显若拿不到控制权会失败。因此先读取事实，不能直接杀进程。

下面是现有 `Linux/RK3568/s7_4/precheck_board.sh` 的完整内容。输入是板端状态；输出是设备节点、连接状态、模式和占用进程；它不修改显示状态。

脚本首次出现的新符号要先解释：

- `$(命令)`：先运行括号里的命令，再把输出放进当前文字。
- `tr '\n' ' '`：把多行模式列表改成一行。
- `< 文件`：把文件内容作为命令标准输入。
- `2>&1`：把标准错误合并到标准输出。
- `tail -30`：只保留最后 30 行。
- `grep -v grep`：排除查询命令自身。

```sh
#!/bin/sh
set -u
echo "== 1. DRM 设备节点 =="
ls -l /dev/dri/ 2>&1 || echo "MISSING /dev/dri（内核显示被禁用或未配置）"

echo "== 2. 各 card 状态与可用模式 =="
for d in /sys/class/drm/card*/; do
  [ -d "$d" ] || continue
  echo "--- $d"
  echo "status: $(cat "$d/status" 2>&1)"
  echo "modes:  $(tr '\n' ' ' < "$d/modes" 2>&1)"
done

[ -r /sys/class/graphics/fb0/name ] && echo "fb0 name: $(cat /sys/class/graphics/fb0/name 2>&1)"

echo "== 4. 内核 cmdline =="
cat /proc/cmdline; echo

echo "== 5. 显示相关内核日志（drm/dsi/panel/hdmi/vop）=="
dmesg 2>/dev/null | grep -iE "drm|dsi|panel|hdmi|vop" | tail -30 || echo "dmesg 不可用"

echo "== 6. 已运行的显示/合成进程 =="

  echo "无（干净环境，DRM 直显可直接用）"

echo "== 7. 屏的物理信息（需人工确认）=="
```

## 完整理解构建脚本后再第一次构建

> **当前位置：`源码、模型、显示边界都已理解 → [生成AArch64程序] → 板端300秒运行`**

构建输入是 C++、RKNN/OpenCV/DRM 头和目标库；输出是 `s7_4_live` 与 `s7_4_drm_smoke`。文件是 `Linux/RK3568/s7_4/build_board.sh`，在 WSL 执行。

脚本首次出现的构建写法要先建立：

- `dirname "$0"` 取得脚本父目录；`CDPATH=` 防止某些 Shell 的 `cd` 输出额外文字。
- `-std=c++17` 选择 C++17；`-O2` 优化；`-Wall -Wextra` 打开常见警告。
- `-D__user=` 让旧内核 UAPI 头里的内核标记可被用户态编译器解析。
- `-I` 增加头文件目录，`-L` 增加库目录，`-l名字` 链接 `lib名字.so`。
- `-o` 指定输出；`file` 只检查架构，不运行 ARM 程序。

```sh
#!/bin/sh
set -eu

SCRIPT_DIR=$(CDPATH= cd -- "$(dirname -- "$0")" && pwd)
SDK=${SDK:-/home/user123/rk3568_sdk}
HOST="$SDK/buildroot/output/rockchip_rk3568/host"
RKNN="$SDK/external/rknpu2/runtime/RK356X/Linux/librknn_api"
OPENCV=${OPENCV:-/home/user123/s7_3_opencv/install}
DRMHDR=${DRMHDR:-/home/user123/s7_4_drm_headers}

"$HOST/bin/aarch64-buildroot-linux-gnu-g++" -std=c++17 -O2 -Wall -Wextra -D__user= \
  "$SCRIPT_DIR/../s7_3/s7_3_board_infer.cpp" "$SCRIPT_DIR/s7_4_display.cpp" \
  -I"$OPENCV/include/opencv4" -I"$RKNN/include" -I"$DRMHDR" -I"$SCRIPT_DIR" \
  -L"$OPENCV/lib" -L"$RKNN/aarch64" \
  -Wl,-rpath,'$ORIGIN/lib' -lopencv_imgcodecs -lopencv_imgproc -lopencv_core -lrknnrt \
  -o "$SCRIPT_DIR/s7_4_live"

"$HOST/bin/aarch64-buildroot-linux-gnu-g++" -std=c++17 -O2 -Wall -Wextra -D__user= \
  "$SCRIPT_DIR/s7_4_drm_smoke.cpp" \
  -I"$DRMHDR" \
  -o "$SCRIPT_DIR/s7_4_drm_smoke"

file "$SCRIPT_DIR/s7_4_live" "$SCRIPT_DIR/s7_4_drm_smoke"
```

具体走读：若 `SCRIPT_DIR=/repo/Linux/RK3568/s7_4`，第一条编译会读取相邻 S7.3 主体和本目录显示实现，最后写入 `s7_4_live`。正常 `file` 应报告 ARM aarch64。若报告 x86-64，说明编译器选错；编译通过也不能证明板端摄像头和 NPU 已运行。

## 先读懂资源监控脚本，再运行 300 秒

> **当前位置：`AArch64程序已部署 → [实时运行并留证] → 把关键点交给手势分类`**

程序跑着不退出，只能说明“进程还活着”。还要知道帧是否持续更新、延迟是否增长、内存和文件描述符是否泄漏、温度是否异常、退出码是否为 0。

- 命令末尾 `&`：让进程在后台运行。
- `$!`：最近一个后台进程的 PID；PID 是进程编号。
- `trap`：脚本退出或收到信号时执行清理。
- `kill -0 PID`：不终止进程，只查询它是否仍存在。
- `/proc/PID/status` 的 `VmRSS`：当前驻留物理内存，单位 KiB。
- `/proc/PID/fd`：进程打开的文件描述符目录；数量持续上涨可能是泄漏。
- `wait PID`：等待后台进程结束并取得退出码。
- `set +e`：暂时允许非 0 返回，使脚本来得及保存真实退出码。

完整文件 `Linux/RK3568/s7_4/run_stability.sh`：

```sh
#!/bin/sh
set -eu

if [ "$#" -lt 4 ] || [ "$#" -gt 10 ]; then
  echo "usage: run_stability.sh APP DETECTOR LANDMARK OUTPUT_DIR [DEVICE] [WIDTH] [HEIGHT] [FPS] [MAX_LATENCY_MS] [VBLANK]" >&2
  exit 2
fi

APP=$1
DETECTOR=$2
LANDMARK=$3
OUTPUT=$4
DEVICE=${5:-/dev/video0}
WIDTH=${6:-800}
HEIGHT=${7:-600}
FPS=${8:-20}
MAX_LATENCY_MS=${9:-200}
VBLANK=${10:-4776}
mkdir -p "$OUTPUT"

v4l2-ctl -d "$DEVICE" --all >"$OUTPUT/camera.txt" 2>&1 || true
"$APP" --camera "$DETECTOR" "$LANDMARK" "$DEVICE" "$WIDTH" "$HEIGHT" "$FPS" \
  300 "$MAX_LATENCY_MS" "$VBLANK" >"$OUTPUT/results.jsonl" 2>"$OUTPUT/runtime.log" &
PID=$!
trap 'kill "$PID" 2>/dev/null || true' EXIT INT TERM

echo 'epoch_s,rss_kb,fd_count,temp_mC,npu_load' >"$OUTPUT/resources.csv"
while kill -0 "$PID" 2>/dev/null; do
  RSS=$(awk '/VmRSS:/ {print $2}' "/proc/$PID/status")
  FDS=$(ls -1 "/proc/$PID/fd" | wc -l)
  TEMP=$(cat /sys/class/thermal/thermal_zone0/temp 2>/dev/null || echo unavailable)
  NPU=unavailable
  for PATHNAME in /sys/class/devfreq/*npu*/load /sys/class/devfreq/fde40000.npu/load; do
    [ -r "$PATHNAME" ] && NPU=$(cat "$PATHNAME") && break
  done
  echo "$(date +%s),${RSS:-0},$FDS,$TEMP,$NPU" >>"$OUTPUT/resources.csv"
  sleep 10
done

set +e
wait "$PID"
STATUS=$?
set -e
trap - EXIT INT TERM
echo "$STATUS" >"$OUTPUT/exit_code.txt"
exit "$STATUS"
```

- `>文件` 新建或覆盖本次输出；`>>文件` 追加一行；`2>文件` 只保存标准错误。
- CSV 是逗号分隔表格；第一行是列名。
- `epoch_s` 是从 1970-01-01 UTC 起的秒数。
- `temp_mC` 是毫摄氏度；`40000` 表示 40°C。

假设部署目录有程序和两个模型，脚本会把相机事实写入 `camera.txt`，后台运行 300 秒，把逐帧记录写入 `results.jsonl`，诊断写入 `runtime.log`，每 10 秒记录资源，最后把退出码写入 `exit_code.txt`。

## 文字复盘和下一篇起点

你现在知道 `/dev/video0` 是驱动入口；`open()` 得到 fd，V4L2 用 `ioctl()` 配格式，用 MMAP 建缓冲，用 QBUF/DQBUF 交换帧。程序通过 `poll()` 有超时地等帧，并主动丢旧帧，避免结果越来越陈旧。

两个模型分工明确：检测模型解决“手在哪里”，关键点模型解决“手部细节在哪里”。只有采集、存在分数和端到端时限同时满足，一帧才 `valid:true`；失败必须输出新的失效记录，不能沿用上次成功结果。

```text
4个MMAP缓冲
  ↓ poll + 排空DQBUF

  ↓ NV12→BGR→RGB
```
