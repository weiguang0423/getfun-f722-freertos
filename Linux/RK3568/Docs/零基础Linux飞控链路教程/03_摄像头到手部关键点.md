# 摄像头到手部关键点：V4L2 与 RKNN 实时链

> **当前学习位置：** `ARM64 程序和 FP16 模型已部署` → **摄像头画面变成手框和 21 个关键点** → `连续帧手势确认`
>
> 本篇解释 S7.4 的 Linux 实时链。完成后，你能运行和读取“摄像头 → 手部观测”的结果；它仍不判断手势、不发送 RC，也不接管飞控。

## 先看真实的数据是怎样流动的

摄像头不是把 JPEG 文件一张张交给程序。IMX335 的原始图像先经过 RKISP，Linux 再通过 `/dev/video0` 提供一帧帧 NV12 数据。S7.4 在这条数据上调用 S7.3 已验收的两级 FP16 模型：

```text
IMX335
  -> RKISP
  -> /dev/video0：800 x 600 NV12 帧
  -> 手掌检测模型：有没有手、手在哪里
  -> 旋转 ROI：从原图裁出并校正手部区域
  -> 关键点模型：21 个手部关键点、存在分数、左右手分数
  -> JSONL：本帧的时间、序号、有效性、关键点和耗时
```

**ROI** 是 Region Of Interest 的缩写，中文是“感兴趣区域”。这里它不是随便裁一块图，而是使用检测到的手框，把手旋转、缩放到关键点模型期待的输入大小。这样手即使斜着放，关键点模型仍能看到较标准的手部区域。

**JSONL** 是“每一行一个 JSON 对象”的日志格式。例如一行记录一帧，方便后续统计，不会因为一行太长让整份文件难以流式处理。

## V4L2 的“最新帧”策略为什么重要

> **当前学习位置：** `摄像头可输出帧` → **避免积压旧画面** → `把可信的当前观测交给手势层`

如果摄像头以 20 fps 产生画面，而推理偶尔变慢，最危险的做法是把每一帧都排队等待处理。这样程序最后仍然会输出结果，但结果可能是几秒前的手势。

本项目 S7.4 使用 V4L2 多平面 MMAP 缓冲，并在每一轮把已完成的缓冲排空、只处理最新帧：

```text
驱动已经完成的帧：100, 101, 102
程序落后时：丢弃 100、101，处理 102
```

这里的 **MMAP**（内存映射）可以先理解为：摄像头驱动分配缓冲，程序映射后直接读取同一块内存，不再额外复制整帧图像。它降低复制成本，但更重要的安全语义来自“旧帧宁可丢弃，也不能作为新动作发送”。

每条实时结果会携带 `sequence`、采集时间、完成时间、累计丢帧数和端到端延迟。坏帧、采集超时、推理异常或延迟超过门槛时，程序输出 `valid:false`，不会沿用上一帧的手部结果。

## 在板端先运行不接飞控的自检

假设你已把 `s7_4_live` 和两份 FP16 模型放在 `/userdata/gesture_rc_demo`。下面都在 **RK3568 板端** 运行：

```sh
cd /userdata/gesture_rc_demo
./s7_4_live --self-test
```

`--self-test` 只检查程序内部的确定性逻辑，不打开摄像头，也不代表实际图像识别已经通过。退出码为 `0` 才表示自检成功；可以紧接着执行 `echo $?` 查看上一条命令的退出码。

接下来定义运行参数，再执行真实摄像头入口：

```sh
./s7_4_live --camera \
  hand_detector_fp16.rknn hand_landmarks_detector_fp16.rknn \
  /dev/video0 800 600 20 180 200 4776 \
  /userdata/gesture_rc_demo/annot 5 \
  > /userdata/gesture_rc_demo/results.jsonl \
  2> /userdata/gesture_rc_demo/runtime.log
```

命令中的每个首次出现参数含义如下：

| 位置 | 参数 | 含义 |
|---:|---|---|
| 1、2 | 两个 `.rknn` | 手掌检测模型、手部关键点模型 |
| 3 | `/dev/video0` | 已由 S7.1 确认的摄像头设备节点 |
| 4、5 | `800 600` | 请求的图像宽和高 |
| 6 | `20` | 请求输入帧率；这里使用冻结验收的 20 fps |
| 7 | `180` | 运行秒数；本例运行 3 分钟，省略则持续运行到手动退出 |
| 8 | `200` | 最大端到端延迟毫秒数；超过它的帧必须无效 |
| 9 | `4776` | IMX335 的 `vertical_blanking` 调节值；退出时程序恢复原值 |
| 10 | `annot` | 保存带框和关键点骨架的 JPEG 目录 |
| 11 | `5` | 每处理 5 帧保存一张标注图 |

`>` 和 `2>` 分别很重要：`>` 把正常 JSONL 输出保存到 `results.jsonl`；`2>` 把错误信息和运行日志保存到 `runtime.log`。两者分开，后续工具才能把 JSONL 当作严格的数据文件读取。

不要随意把 `4776` 当作通用参数。它是项目在当前 IMX335 安装和测试条件下为约 20 fps 使用的实测值；换摄像头、分辨率或安装环境时，它需要重新测量。程序退出时恢复启动前值，是为了不把一次测试悄悄变成永久传感器配置。

## 怎样观察“识别到手”而不是只相信数字

只看 `valid:true` 不足以证明 21 个点落在正确手指上。S7.4 会把检测框、21 点骨架和置信度画到 JPEG 标注图上。运行中或运行后，在板端查看保存数量：

```sh
ls /userdata/gesture_rc_demo/annot | wc -l
tail -n 3 /userdata/gesture_rc_demo/results.jsonl
```

`wc -l` 的意思是统计行数；`tail -n 3` 只显示日志最后 3 行。把标注图复制回 PC 后，用图片浏览器检查：

- 手张开和移动时，绿色检测框跟随手，骨架的 21 点贴近手指。
- 手移出画面时，框和有效手结果消失，而不是保留上一次骨架。
- 遮挡或半握拳时，可以低置信度或无效；不能“凭空补成”一个完整稳定手。

项目的 S7.4 实物记录中，屏显 180 秒运行得到 2832 条记录、773 条有效手部观测；5 分钟稳定性关口实际运行 438.656 秒，处理约 20.011 fps，端到端延迟均值约 65.156 ms、P95 约 76.585 ms，累计丢 8 帧且退出码为 0。这些是当时板卡上的实测证据，不是换环境后的自动保证。

## 可选：在 RK3568 屏幕上直接看结果

S7.4 使用 DRM/KMS 做最小屏显，不依赖 Qt、GStreamer 或额外 GUI 框架。DRM/KMS 可以先理解为 Linux 内核提供的“直接向显示硬件送画面”的接口。

板端桌面合成器 Weston 通常占用显示控制权。只有确认要做屏显时，才在 **RK3568 板端** 执行：

```sh
killall weston
./s7_4_drm_smoke /dev/dri/card0 10
```

第一条命令会停止 Weston，释放 DRM master；屏幕桌面会消失，这是预期的。第二条是显示链路冒烟程序，成功时屏幕应出现随时间变化的渐变色块，程序应输出 `smoke: ok, display link usable`。重启板子后 Weston 会恢复。

只有冒烟通过后，才在 `--camera` 命令最后附加显示设备 `/dev/dri/card0`。显示失败被设计为只告警，不改变推理 JSONL 的安全失效语义。

## S7.4 的边界和本篇完成判据

S7.4 只能回答：当前一帧是否看到了几何上合理的一只手。它不能回答“这是不是你定义的张掌手势”。项目实际 5 分钟无手稳定性运行中仍出现过 2 条 `valid:true`，这正是下一篇还要加手势分类、连续帧确认和释放状态的原因。

完成本篇时，请留存：

1. `results.jsonl`、`runtime.log` 和退出码。
2. 至少几张能证明关键点位置正确的标注图，以及无手时的 JSONL 记录。
3. 摄像头实际格式/帧率、延迟统计和资源统计；长时间运行请复用 `s7_4/run_stability.sh`。

| 现象 | 第一检查点 | 结论边界 |
|---|---|---|
| `capture_failure` | `/dev/video0`、摄像头接线、`v4l2-ctl` 短采集 | 先修摄像头，不是手势算法问题 |
| `valid:false` / `deadline_miss` | JSONL 的延迟字段、请求 fps、NPU 负载 | 这正是程序拒绝陈旧帧的保护，不应强行改成有效 |
| 模型加载失败 | 模型路径、SHA-256、板端 Runtime 版本 | 不要先覆盖 `librknnrt.so` |
| 屏幕不显示 | `/dev/dri`、Weston 是否释放、DRM 冒烟结果 | 不影响无屏的推理和 JSONL 验证 |
