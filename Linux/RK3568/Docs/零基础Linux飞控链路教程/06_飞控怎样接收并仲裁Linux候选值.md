# 飞控怎样接收并决定是否采用 Linux 候选值

上一章结束时，RK3568 已经把一个 44 字节的候选帧从串口发了出去。

现在不要急着想 PID、电机或者“无人机怎么动”。飞控刚开始看到的只是一串接连到来的字节。它还不知道这些字节是否完整、是否来自当前运行的 Linux 程序，也不知道操作者是否允许使用它们。

因此，飞控端要连续回答三个问题：

1. 我有没有收到一整帧？
2. 这一帧有没有损坏，内容是否合理，时间是否够新？
3. 即使这一帧可信，现在是否允许用它替换物理遥控器的 Roll、Pitch、Yaw？

这三个问题对应三层处理：

```text
USART6 收字节
    ↓
找帧头、收满 44 字节、检查整帧
    ↓
得到一个“可信的 Linux 候选值”
    ↓
结合物理遥控器和飞行状态决定采用哪一边
    ↓
唯一的有效 RC 数据继续进入原有控制链
```

这里最重要的边界是：**收到候选值，不等于采用候选值。**

## 1. 一个串口字节是怎样进入飞控的

RK3568 的 TX 接到 F722 的 PC7。PC7 在本项目中是 `USART6_RX`，也就是 USART6 的接收脚。

串口参数是 115200、8N1：

- 115200 表示每秒传输约 115200 个比特；
- 8 表示一个数据单位有 8 个数据位；
- N 表示没有奇偶校验位；
- 1 表示使用 1 个停止位。

两端这些参数必须相同。参数不同并不会让数据“慢一点”或“少一点”，而是会把同一段电平读成错误的字节。

F722 每收到一个字节，底层串口接收逻辑就把这个字节交给 Linux RC 接收模块。这个动作发生在中断回调里。初学时可以把“中断”理解为：

> 串口硬件告诉 CPU：“新字节到了，先来取一下。”

中断里只做很短的工作：取走字节、推进收帧状态、重新等待下一个字节。它不会在这里做飞行控制计算，因为中断占用太久会影响系统里其他实时任务。

## 2. 为什么不能每收到 44 个字节就当成一帧

串口只负责按顺序传字节，它不会额外告诉接收方“这里是第 1 个字节”“这里是第 44 个字节”。

假设飞控在 Linux 已经发送到第 17 个字节时才上电，那么它最先收到的是旧帧的中间部分。若接收方直接从这里数 44 个字节，后面每一帧都会错位。

所以协议在每帧开头放了两个固定字节：`G` 和 `R`。接收方一直寻找这两个连续字节：

```text
杂乱字节 → 找到 G → 下一个是 R → 认为这里可能是一帧的开头
```

找到开头后，接收方继续收，直到凑满 44 字节。注意这里说的是“可能是一帧”，不是“已经确认正确”。`G R` 也可能碰巧出现在杂乱数据里，真正的确认要靠后面的完整检查。

如果收满以后检查失败，接收方会重新寻找下一组 `G R`，而不是继续相信这个错误位置。这样，即使中途丢了一个字节，后面也有机会重新对齐。

## 3. 为什么检查新帧前要先让旧候选失效

这是一个很关键、但容易被忽略的安全思路。

假设上一帧是有效的 Pitch 命令，下一帧已经收满，但 CRC 错了。如果程序只是“忽略错误新帧”，旧的有效命令可能还会被继续使用，看起来就像 Linux 仍然健康。

本项目选择更保守的做法：

> 一旦准备处理一帧新的完整数据，先撤销旧候选；只有新帧通过全部检查，才重新发布有效候选。

这样做的结果是，错误数据不会延长上一条命令的寿命。控制链遇到不确定情况时，优先回到物理遥控器。

## 4. 一帧为什么要按这个顺序检查

检查顺序不是为了好看，而是为了让便宜、基础的错误先被挡住，再解释更复杂的字段。

### 第一步：检查 CRC

CRC 是根据前 42 字节算出的 16 位结果，帧尾也带着发送端算好的结果。接收端重新计算一次，两边相同才继续。

它主要发现传输中的比特翻转、丢字节、错位等问题。CRC 不能证明发送者“有权限”，也不能证明字段含义合理；它只说明这 44 字节大概率没有在传输中损坏。

### 第二步：检查版本、长度、标志位和保留字段

这一步回答：“发送端和接收端说的是不是同一种协议？”

例如：

- 版本必须是飞控当前支持的版本 1；
- 长度必须明确写成 44；
- 标志位只能使用已经定义的位；
- 手势编号和置信度必须落在允许范围；
- 尚未使用的保留字节必须保持约定值。

如果未来协议改了字段，但 Linux 和飞控只升级了一边，这一步会拒绝它，而不是把新格式误读成旧格式。

### 第三步：检查数值范围

当前 Linux 只允许给出有限的姿态偏移。Roll、Pitch、Yaw 的候选值都必须在 `-300` 到 `+300` 之间。

虽然帧里还保留了 Throttle 和 AUX 字段，但 Linux 没有这两类控制权，因此当前发送值必须为 0。这里不是把油门真的设为 0，而是明确表示“Linux 不提供油门和 AUX”。最终油门和 AUX 始终从物理遥控器复制。

范围检查可以挡住内存错误、字段错位或异常程序给出的极端值。

### 第四步：检查手势名称和通道是否互相匹配

仅仅“每个数字都在范围内”仍然不够。例如一帧声称自己来自张掌，却同时要求 Roll 和 Yaw 改变，这不符合当前项目的手势映射。

所以飞控还会检查含义是否匹配：

| 手势 | 当前允许出现的候选变化 |
|---|---|
| `UNKNOWN` | Roll、Pitch、Yaw 全为 0 |
| `OPEN_PALM` | 只允许 Pitch 负向 |
| `POINT` | 只允许 Pitch 正向 |
| `V_SIGN` | 只允许 Roll 负向 |
| `FIST` 或无效帧 | 不能携带有效动作值 |

这一层能发现“手势编号写对了，但通道内容不属于这个手势”的问题。

### 第五步：检查 Linux 内部时间关系

帧里有源时间和发送时间：

- 源时间表示这份识别结果对应的摄像头画面是什么时候产生的；
- 发送时间表示 Linux 什么时候把它装进串口帧。

发送时间不能早于源时间，而且二者相差不能超过 250 ms。否则，Linux 可能正在发送一份已经在相机、推理或队列里积压太久的旧结果。

这里比较的是同一台 Linux 机器上的两个时间，所以不需要让 RK3568 和 F722 的时钟完全同步。

### 第六步：检查心跳和源序号是否向前走

`heartbeat` 每发送一帧就递增，用来证明发送循环仍在运行。

`source_sequence` 对应摄像头或识别结果的序号，用来证明数据来源也在向前更新。

如果串口还在不断收到相同心跳，可能是旧帧在被重复发送；如果心跳前进但源序号长时间不动，可能是发送线程活着，但摄像头或推理结果卡住了。两者一起检查，比只看“串口有没有数据”更可靠。

### 第七步：识别 Linux 进程重启

Linux 程序重启后，心跳和序号通常会从较小的数重新开始。这不能简单当成普通递增帧，也不能继续沿用重启前的授权状态。

接收模块会把它识别为新会话，并增加一个会话代数。新的帧可以重新成为候选，但如果飞控当时正在使用虚拟源，仲裁器会先退出。操作者必须再次把 AUX3 从低拨到高，才能重新进入。

这避免了 Linux 意外重启后自动恢复控制。

## 5. 通过检查以后得到的仍然只是候选值

一帧通过全部检查后，接收模块会保存一份候选快照，包括：

- 是否有效；
- F722 在什么时候收到它；
- 源序号和心跳；
- Linux 会话代数；
- 五个候选通道值。

这里的“快照”就是某一时刻的一整份数据副本。

为什么要强调“一整份”？因为串口中断可能正在更新候选，而 `RcTask` 同时在读取。如果读取一半时中断又写入新数据，就可能得到“上一帧的序号加下一帧的通道”这种拼接结果。

项目在复制这份小数据时，会短暂阻止中断改写。复制完成后马上恢复。这样 `RcTask` 读到的字段一定来自同一帧。这个过程很短，不会把耗时工作塞进中断。

候选快照仍然没有决定最终控制权。它只回答：

> “最近收到过一份通过协议检查的 Linux 候选值。”

它没有回答：

- 物理遥控器是否有效；
- 飞机是否已 ARM；
- 当前是否存在禁止解锁或禁止控制的原因；
- AUX3 是否被专门留给视觉授权；
- 操作者是否真的做过一次低到高授权；
- 物理摇杆是否正在要求接管。

这些问题由下一层仲裁器处理。

## 6. 仲裁器到底在“仲裁”什么

“仲裁”可以直接理解为：两种来源同时存在时，决定最终使用哪一种。

两种来源是：

- 物理来源：遥控器通过 CRSF 进入飞控；
- 虚拟来源：RK3568 通过 USART6 提供候选 Roll、Pitch、Yaw。

仲裁器每次运行都会收到：

- 当前物理 RC 的全部通道；
- 物理 RC 是否有效；
- 是否已经 ARM；
- 是否存在 arming inhibit；
- AUX3 是否能安全地用作视觉授权开关；
- 最新 Linux 候选及其接收时间；
- 当前 F722 时间。

它输出一份唯一的有效 RC 通道。后面的姿态目标、PID、Mixer、DShot 只看这份结果，不分别认识“Linux”和“物理遥控器”。这样控制权的选择只发生在一个位置，不会在后续各层重复判断。

## 7. 为什么第一步永远是完整复制物理遥控器

仲裁器开始处理时，先把物理遥控器的全部通道复制到输出。

如果后面任何条件不满足，什么都不用额外做，输出自然就是物理遥控器。这就是安全默认值。

只有虚拟源已经被允许使用时，程序才覆盖前三个通道：Roll、Pitch、Yaw。Throttle 和全部 AUX 从头到尾都没有被 Linux 覆盖。

```text
最终 RC = 先完整复制物理 RC

若虚拟源已获准：
    只替换 Roll / Pitch / Yaw

始终不替换：
    Throttle / ARM / ANGLE / AUX3 / 其他 AUX
```

这也是为什么上一章串口帧里的 Throttle 和 AUX 为 0，不会让真实油门突然归零：仲裁器根本不用 Linux 的这两个字段替换物理通道。

## 8. 什么时候允许从物理源进入虚拟源

进入虚拟源必须同时满足下面全部条件：

1. 物理遥控器当前有效；
2. AUX3 没有和 ARM、ANGLE 等功能发生配置冲突；
3. 飞机已经由物理遥控器完成 ARM；
4. 当前没有 arming inhibit；
5. 操作者已经让 AUX3 出现过低位，然后又拨到高位；
6. 物理 Roll、Pitch、Yaw 都在中心附近；
7. Linux 候选有效；
8. 这份候选在 F722 端的接收年龄严格小于 150 ms。

这里的 150 ms 与前面的 250 ms 检查不是一回事：

- 250 ms 检查 Linux 内部从画面产生到发送之间是否积压；
- 150 ms 检查 F722 最近一次收到候选以后，链路是否还活着。

为什么要求 AUX3 先低再高？因为上电时开关可能本来就在高位。如果只检查“现在是不是高”，系统可能在操作者没有做出新动作时自动进入。低到高表示一次明确的新授权。

为什么要求物理三轴居中？因为进入的瞬间如果操作者正推着摇杆，系统无法判断他是在准备交出控制，还是正在主动飞行。

## 9. 进入以后候选值怎样成为 RC 通道

物理 RC 常用 1500 μs 表示姿态轴中点。Linux 给的是以中点为 0 的偏移量。

例如：

```text
Linux Pitch 候选 = -300
目标 Pitch = 1500 - 300 = 1200 μs
```

仲裁器不会从 1500 一次跳到 1200。它把变化速度限制在每秒 600 个单位。这样可以减少突然跳变。

如果任务每 20 ms 更新一次，每次最多变化约 12 个单位：

```text
1500 → 1488 → 1476 → 1464 → …… → 1200
```

这个限制只让变化更平滑，不会替代后面的姿态控制和 PID。它也不是安全授权；授权仍由上一节的条件决定。

## 10. 哪些情况会立即退出虚拟源

一旦已经处于虚拟源，仲裁器按以下顺序检查退出条件：

1. 物理遥控器失效；
2. AUX3 配置变得不可用；
3. 飞机 DISARM；
4. 出现 arming inhibit；
5. AUX3 被拨低，操作者撤销授权；
6. 物理 Roll、Pitch、Yaw 任一轴偏离中心超过 150 μs，表示人工接管；
7. Linux 候选变成无效；
8. Linux 会话发生重启；
9. 最近候选的接收年龄达到或超过 150 ms。

退出时，输出马上回到物理遥控器，并清除“已经见过 AUX3 低位”的记录。即使 Linux 下一帧立刻恢复正常，也不会自动重新进入。必须再次完成一次 AUX3 低到高。

这里有两个容易误解的地方。

第一，物理遥控器失效时回到“物理来源”，不表示失效的遥控数据会被当成正常控制。原有 RC failsafe 仍会处理物理链路失效。虚拟链路不能绕开这套安全机制。

第二，当前协议中，改变物理 Throttle 不会触发三轴接管。原因是 Throttle 从未交给 Linux，它在虚拟源期间也一直直接来自物理遥控器。只有物理 R/P/Y 明显离中才表示要取回三轴控制。

## 11. 用一次真实时序把进入和退出串起来

假设物理三轴都在 1500 μs，Throttle 在最低位，Linux 正常发送候选：

| 时间 | 发生的事 | 飞控的决定 |
|---|---|---|
| 1000 ms | AUX3 低，物理 RC 有效，尚未 ARM | 使用物理源，并记住“见过 AUX3 低位” |
| 1200 ms | 操作者用物理 AUX1 ARM，AUX3 仍低 | 仍使用物理源 |
| 1300 ms | AUX3 拨高；三轴居中；候选刚收到 | 条件全部满足，进入虚拟源 |
| 1350 ms | 收到张掌产生的 Pitch = -300 | Pitch 目标朝 1200 μs 平滑变化 |
| 1500 ms | 操作者把物理 Roll 推离中心 200 μs | 立即退出，最终三轴恢复物理值 |
| 1520 ms | 物理 Roll 回中，AUX3 仍高 | 不会自动重进，因为还没有新的低到高授权 |
| 1600 ms | AUX3 拨低 | 再次记住“见过低位” |
| 1700 ms | AUX3 再拨高，其余条件正常 | 可以再次进入虚拟源 |

这段时序体现了项目的核心思路：进入要满足一组条件，退出只需要出现一个不安全条件；退出之后不能靠数据自己恢复，必须由人重新授权。

## 12. 后面的飞控链没有被 Linux 重写

仲裁器产出的唯一 RC 快照仍沿用项目原来的飞控路线：

```text
有效 RC
  ↓
生成姿态或角速度目标
  ↓
PID 根据目标和实际姿态计算修正量
  ↓
Mixer 把修正量分配给各个电机
  ↓
DShot 把电机命令发给电调
```

Linux 没有直接写 PID 输出，没有直接控制 Mixer，也没有直接发 DShot。它只在获得授权时，替换了唯一 RC 快照里的三个姿态输入。

这使原有的 ARM、failsafe、姿态控制和电机输出限制仍然有效。

## 13. 出问题时按数据经过的顺序看

飞控通过 UART4 输出三组不同层次的信息。它们不是三个重复日志，而是在回答三个不同问题。

### `linux_rc`：字节和帧有没有通过

重点看：

- `rx` 是否持续增加：USART6 有没有收到字节；
- `frame` 是否增加：有没有反复收满 44 字节；
- `valid` 是否增加：完整帧有没有通过全部检查；
- `crc`、`fmt`、`seqerr`、`timeerr` 哪一项增加：失败发生在哪类检查；
- 最后一次序号、心跳、手势和通道是否合理。

如果 `rx` 完全不涨，先查接线、共地、电平、PC7 和 115200 8N1，不要先查 PID。

如果 `rx` 涨但 `frame` 不涨，先查是否丢字节或无法找到稳定帧头。

如果 `frame` 涨但 `valid` 不涨，就根据错误计数查 CRC、格式、时间或序号。

### `rc source`：可信候选为什么没有被采用

这里看当前来源、AUX3 状态、是否已见过低位、候选是否新鲜、退出原因、ARM、inhibit 和配置状态。

如果 `linux_rc valid` 持续增加，但来源始终是物理源，问题通常不在串口，而在进入条件：未 ARM、AUX3 没有低到高、三轴没回中、配置冲突、存在 inhibit，或者候选已经超过 150 ms。

### `e2e`：采用以后是否进入原有控制链

这里用于观察最终 RC、setpoint、PID、Mixer 和 DShot 相关状态。只有前两层都正常，才有必要继续向后查。

## 14. 一张故障定位表

| 最先出现异常的位置 | 最可能的问题层 | 第一批检查项 |
|---|---|---|
| USART6 `rx` 不增加 | 电气连接或串口配置 | 3.3 V、共地、TX→PC7、115200 8N1 |
| `rx` 增加，完整帧不增加 | 收帧同步 | 丢字节、帧头、Linux 是否连续写完整帧 |
| 完整帧增加，CRC 错误增加 | 传输内容损坏 | 波特率、电平、线材、帧长度和 CRC 实现是否一致 |
| 格式错误增加 | 两端协议理解不一致 | 版本、长度、标志、手势和通道范围 |
| 时间或序号错误增加 | Linux 数据不再向前更新 | 摄像头、推理、发送循环、进程是否重启 |
| 有效候选增加，但来源不切换 | 进入条件不满足 | ARM、inhibit、AUX3低→高、三轴居中、候选年龄 |
| 已进入后突然退出 | 安全条件被触发 | 退出原因、物理三轴、AUX3、候选有效性和超时 |
| 来源已是虚拟，但后级不变化 | 原有控制链 | 最终RC、setpoint、PID、Mixer、DShot，保持拆桨 |

这张表的用法是：找到数据第一次不符合预期的位置。第一次断掉的地方通常比最后看到的症状更接近原因。

## 15. 本章真正需要记住什么

你不需要先会写接收器或仲裁器代码，才能理解这一章。先抓住下面这条逻辑：

```text
收到字节
≠ 收到完整帧
≠ 收到可信候选
≠ 允许采用候选
≠ 已经形成电机命令
```

飞控先在 USART6 上重新找齐 44 字节，再检查 CRC、格式、范围、手势含义、时间、心跳、源序号和 Linux 会话。通过以后只得到候选快照。

`RcTask` 再把候选与物理遥控器、ARM、inhibit、AUX3 授权和人工接管条件一起交给仲裁器。默认完整保留物理通道；条件全部满足时才覆盖 Roll、Pitch、Yaw。任何不安全条件出现，都回到物理源并要求重新低到高授权。

下一章不再讲程序内部结构，而是讲怎样在拆桨条件下，从摄像头开始沿着这条链逐层确认实际结果。
