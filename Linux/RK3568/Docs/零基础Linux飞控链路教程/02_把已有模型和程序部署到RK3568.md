# 已有模型和程序怎样部署到 RK3568

上一章建立了最少的 Linux 基础。现在开始处理真正的部署问题。

你手里已经有开源模型和项目源码，但它们不能原样复制到 RK3568 后直接运行。中间至少要完成两种“翻译”：

- 把模型翻译成 RK3568 NPU 能接受的 RKNN 格式；
- 把 C++ 源码翻译成 RK3568 CPU 能执行的 ARM64 程序。

这就是本章的主线。我们只讲为什么需要这些环节、每个环节交出什么，以及怎样判断结果是否可靠，不讲项目中自动化工具的内部写法。

## 先分清四类文件

部署过程中最容易混淆的是：看起来都是“项目文件”，但用途完全不同。

### 模型文件

模型文件保存神经网络的结构和参数。原始开源项目提供的是 TFLite 模型。

模型不是普通程序。CPU 不会把它当作指令直接执行。需要有一个推理运行库读取模型，再把输入送进去，得到输出。

### C++ 源码

源码描述程序逻辑，例如怎样打开摄像头、怎样处理一帧图像、怎样调用两个模型。

RK3568 的 CPU 不能直接执行 `.cpp` 文字。源码必须先经过编译器，变成 CPU 指令。

### 动态库

项目没有把图像处理和 NPU 调用全部重新实现，而是使用现成的 OpenCV 和 RKNN Runtime。

这些现成功能通常放在 `.so` 文件里。`.so` 可以先理解为 Linux 的共享功能包。程序启动时会加载它们。

### 可执行文件

编译后的 ARM64 ELF 才是 RK3568 真正启动的程序。

ELF 是 Linux 常见的可执行文件格式。ARM64 ELF 只能在兼容的 ARM64 Linux 环境运行，不能因为它是“Linux 程序”就在 x86-64 WSL 中直接运行。

## 整个部署过程在解决什么

```text
原始 TFLite 模型
  ↓ 目标芯片转换
RK3568 可用的 RKNN 模型

C++ 源码 + 头文件
  ↓ ARM64 交叉编译
ARM64 ELF

ARM64 ELF + RKNN 模型 + OpenCV/RKNN 动态库
  ↓ 复制到开发板
板端部署目录
  ↓ 实际启动
摄像头实时推理程序
```

模型转换和程序编译是两条平行的准备工作。最后在 RK3568 上运行时，它们才会合在一起。

## 为什么模型要转换成 RKNN

TFLite 描述的是一种通用模型格式。RK3568 的 NPU 有自己的运算方式、支持范围和数据布局。

RKNN Toolkit2 的工作可以理解成：

1. 读取原始模型；
2. 检查其中的运算是否能在目标芯片上实现；
3. 按 RK3568 的要求重新组织模型；
4. 导出 `.rknn` 文件。

这里没有重新训练模型。模型原本学到的参数仍然来自开源模型。转换只是为了让目标硬件能够执行它。

### 为什么要明确写目标芯片是 RK3568

RKNN 文件不是对所有 Rockchip 芯片通用。不同芯片的 NPU 能力和运行时可能不同。

所以“这是官方 RKNN 模型”也不代表它一定适合当前板子。必须确认它是为 RK3568 或兼容的 RK356X 目标生成，并在当前 Runtime 上实际运行。

### 为什么最终选择 FP16

本项目比较过 FP16 和 INT8 两种转换结果。

- FP16 使用 16 位浮点数表示许多中间数据；
- INT8 使用 8 位整数，通常更省空间、速度也可能更快，但需要量化，误差可能更大。

实际板端对比中，FP16 通过了冻结的输出误差要求，INT8 的有效性一致率和多项误差超限，所以项目选择 FP16。

这个决定说明一个重要思路：**部署模型不能只看速度，还要确认输出是否仍然符合原模型的行为。**

## 为什么要在 WSL 里交叉编译

开发电脑通常是 x86-64，RK3568 是 ARM64。

普通电脑编译器默认生成给本机使用的 x86-64 指令。交叉编译器则运行在电脑上，却生成 ARM64 指令。

因此“交叉”指的是：

```text
编译器运行的位置：x86-64 WSL
程序最终运行的位置：ARM64 RK3568
```

### 编译器还需要知道哪些内容

编译器不能只看一份 `.cpp` 文件。它还要知道：

- RKNN API 的函数声明在哪里；
- OpenCV 的头文件在哪里；
- 目标系统使用哪些 ARM64 动态库；
- 最终程序启动时去哪里找这些库。

“头文件”告诉编译器某个函数怎样调用。“动态库”提供这个函数真正编译好的实现。缺少头文件时通常在编译阶段失败；缺少库时可能在链接阶段或板端启动阶段失败。

## 为什么不能随便换一个更新的编译器

开发板用户空间使用的 glibc 版本较旧。glibc 是 Linux 程序经常依赖的一组基础运行功能。

如果用更新编译器生成的程序要求 `GLIBC_2.36`，而板端只有 glibc 2.35，程序会在启动时报告所需版本不存在。

所以项目最终选择能生成兼容产物的 GCC 10，并把部分 C++/GCC 运行支持静态带入程序。

这里的思路不是“编译器越旧越好”，而是：**程序所要求的运行环境不能比目标板实际拥有的环境更新。**

## 动态库为什么放在程序旁边

板端可能没有完整安装项目所需的 OpenCV。直接修改系统 `/usr/lib` 又容易影响其他程序。

因此项目把自己的动态库放进部署目录下的 `lib`：

```text
/userdata/gesture_rc/
  s7_6_live
  detector.rknn
  landmark.rknn
  lib/
    libopencv_core.so...
    libopencv_imgproc.so...
    libopencv_imgcodecs.so...
    librknnrt.so 或由系统提供的兼容版本
```

程序的运行路径配置使用 `$ORIGIN/lib`。这里的 `$ORIGIN` 不是 Shell 变量，而是动态加载器理解的特殊位置，表示“当前可执行文件所在目录”。

这样无论整个部署目录移动到哪里，程序都能优先在自己旁边的 `lib` 中寻找依赖。

## 一次完整构建应该留下哪些产物

对本项目而言，最少需要：

- 手部检测模型的 RKNN FP16 文件；
- 手部关键点模型的 RKNN FP16 文件；
- ARM64 实时程序；
- 程序需要、但板端系统没有提供的动态库；
- 能说明这些文件来自哪个源码版本的记录；
- 每个正式产物的 SHA-256。

SHA-256 是根据文件内容计算出的长字符串。只要文件任何一个字节改变，结果通常就会改变。

它解决的是“传到板上的文件是不是原来那一份”这个问题，而不是“文件功能一定正确”。

## 怎样把产物部署到板上

部署本质上是一次有边界的复制：

```text
WSL 构建产物
  ↓ 检查架构和哈希
通过网络复制
  ↓
RK3568 新部署目录
  ↓ 再检查大小、架构、哈希和动态库
允许启动
```

为什么建议使用一个新的部署目录，而不是覆盖正在运行的旧目录？

因为覆盖一半时可能出现“程序是新版、模型还是旧版”或者“库只复制了一部分”的混合状态。使用新目录可以先完整检查，再决定是否切换。

## 板端启动前按什么顺序确认

### 确认 CPU 架构

使用 `file` 查看可执行文件。结果应包含 ARM aarch64。

这个检查只证明程序是给 ARM64 生成的，不能证明它一定兼容板端动态库。

### 确认动态库

使用 `ldd` 查看程序需要的库。任何关键库显示 `not found`，都说明启动条件还不完整。

### 确认模型文件

检查两个 RKNN 文件是否存在、大小是否合理、SHA-256 是否与构建记录一致。

模型存在不代表它能被当前 RKNN Runtime 加载。真正的兼容性仍要在板端初始化模型时确认。

### 确认设备

最终程序还依赖 `/dev/video0` 和实际 UART 设备。软件文件都齐全，但硬件设备不存在时，程序仍然不能完成整条链路。

## 最常见的失败怎样理解

| 现象 | 说明哪一层有问题 | 先检查什么 |
|---|---|---|
| `Exec format error` | CPU 架构不对 | `file` 是否为 ARM aarch64 |
| `GLIBC_x.x not found` | 程序要求的系统运行库太新 | 编译器和目标系统版本 |
| 某个 `.so` not found | 动态库搜索路径不完整 | `ldd`、部署目录 `lib` |
| RKNN 初始化失败 | 模型、Runtime 或目标芯片不匹配 | 模型目标、Runtime 版本、模型哈希 |
| 两个模型只加载了一个 | 部署内容不完整或路径错误 | 两个模型的实际路径和文件名 |
| 程序能启动但没有图像 | 构建部署已过，问题走到摄像头层 | `/dev/video0`、格式和占用状态 |

## 这一章真正要理解的思路

部署不是“把几个文件复制过去”。它是在建立一组兼容关系：

```text
原始模型 ↔ RKNN转换目标 ↔ RK3568 NPU与Runtime
C++源码 ↔ ARM64编译器 ↔ 板端glibc
程序 ↔ OpenCV/RKNN动态库
部署目录 ↔ 模型路径和设备路径
```

只要其中一组不匹配，程序就可能在不同阶段失败。
