# 从已有模型到 RK3568 程序：转换、交叉编译与部署

> **文档进度：`课程地图 → Linux文件/命令/进程 → [本篇：模型转换、交叉编译和部署] → 摄像头实时链`**
>
> **真实数据流位置：`两个已有 TFLite 模型 + C++ 源码 → WSL 构建产物 → RK3568 文件系统`**
>
> 本篇不运行摄像头，也不连接飞控。完成后，你会得到两份 RKNN FP16 模型、一个 AArch64 可执行程序和它需要的 OpenCV 动态库，并能解释真实脚本每一段为什么存在。

## 当前已经有什么，还缺什么

上一篇确认了三件事：

- Windows 仓库保存项目原件；
- WSL 是 x86-64 Linux 构建环境；
- RK3568 是 AArch64 Linux 运行环境。

当前项目已经有两个开源 TFLite 模型、RK3568 SDK、RKNN Toolkit2、C++ 源码和构建脚本。但“文件都在”不等于“板端能运行”，中间还缺一条构建链：

```text
TFLite 模型
   ↓ 使用与板端 Runtime 匹配的 RKNN Toolkit2
RKNN 模型

C++ 源码
   ↓ 使用 AArch64 交叉编译器、头文件和库
AArch64 ELF 程序

模型 + ELF + 运行库
   ↓ 复制并核对 SHA-256
RK3568 部署目录
```

本篇引用并解释以下现有文件，不创建新的源码或脚本：

| 文件 | 为什么存在 |
|---|---|
| `Linux/RK3568/s7_4/precheck_wsl.sh` | 在构建前确认 SDK、工具链、头文件和库是否真的存在 |
| `Linux/RK3568/s7_3/convert_models.py` | 把已有 TFLite 模型转换为面向 RK3568 的 FP16/INT8 RKNN 文件 |
| `Linux/RK3568/s7_3/build_opencv.sh` | 为板端程序构建最小 OpenCV 动态库 |
| `Linux/RK3568/s7_3/build_board.sh` | 把板端推理源码交叉编译为 AArch64 ELF |
| `Linux/RK3568/s7_3/s7_3_board_infer.cpp` | 实现模型加载、图像前后处理和离线推理 |

## 源码、头文件、库和可执行程序是什么关系

> **当前位置：`会操作 Linux 文件 → [理解构建输入和输出] → 检查 SDK`**
>
> 本节不执行编译。完成后，你能解释编译器为什么同时需要 `.cpp`、`.h`、`-I`、`-L` 和 `-l`。

### 源文件描述“程序怎样工作”

`.cpp` 是 C++ 源文件。它包含人能够阅读的类型、函数和控制流程。例如 `s7_3_board_infer.cpp` 描述怎样加载模型、处理图片并输出 JSON。

CPU 不能直接执行 C++ 文本。编译器要把它翻译成目标 CPU 指令。

### 头文件描述“可以怎样调用”

`.h` 或 `.hpp` 头文件通常提供类型和函数声明。例如 RKNN 的 `rknn_api.h` 告诉编译器：

- `rknn_init` 这个函数存在；
- 它接收哪些参数；
- 它返回什么类型；
- RKNN 张量结构体有哪些字段。

头文件本身不包含板端 NPU Runtime 的全部实现。它解决“编译时知道接口”的问题。

### 库文件提供已经编译好的实现

Linux 动态库常以 `.so` 结尾，SO 是 Shared Object 的缩写。当前程序需要：

- `libopencv_core.so`：OpenCV 基本矩阵与数据结构；
- `libopencv_imgproc.so`：颜色转换、缩放和几何处理；
- `libopencv_imgcodecs.so`：读取 JPEG 等图片；
- `librknnrt.so`：在 RK3568 上调用 NPU 的 Runtime。

编译时，链接器把“源码中的函数调用”与“库提供的实现”对应起来。运行时，Linux 动态加载器再找到这些 `.so`。

### ELF 是 Linux 可执行文件格式

编译和链接完成后得到 ELF。ELF 是 Executable and Linkable Format 的缩写，中文可理解为“可执行与可链接文件格式”。

ELF 内部记录了目标 CPU 架构和依赖库。AArch64 ELF 只能交给兼容的 ARM64 Linux 运行；WSL 的 x86-64 CPU不能直接执行它。

### 模型不是程序

`.tflite` 和 `.rknn` 保存神经网络结构与参数，它们不能自己执行。程序通过 Runtime API 加载模型，再把输入张量交给 NPU。

当前构建关系是：

```text
s7_3_board_infer.cpp ──编译/链接──> s7_3_board_infer（程序）
hand_detector.tflite ──转换──> hand_detector_fp16.rknn（模型）
hand_landmarks_detector.tflite ──转换──> hand_landmarks_detector_fp16.rknn（模型）
```

程序与模型必须同时部署，且模型格式要与板端 RKNN Runtime 兼容。

## 为什么要用交叉编译器

> **当前位置：`构建输入已经分清 → [选择能生成 AArch64 指令的工具] → 检查工具链文件`**
>
> 本节解释“交叉”发生在哪里，不立即调用编译器。

普通 WSL `g++` 默认生成 x86-64 指令，因为它面向当前 PC。RK3568 需要 AArch64 指令。因此 SDK 提供：

```text
aarch64-buildroot-linux-gnu-g++
```

名字可以拆开理解：

| 片段 | 当前含义 |
|---|---|
| `aarch64` | 输出目标 CPU 架构 |
| `buildroot` | 与板端 Buildroot 工具链和系统环境配套 |
| `linux-gnu` | 目标是使用 GNU 用户空间接口的 Linux |
| `g++` | C++ 编译驱动 |

交叉编译器在 x86-64 WSL 中运行，但输出 AArch64 ELF。它还必须使用目标系统对应的头文件和库；如果误用 WSL 自己的 x86-64 OpenCV 库，链接会失败，或生成无法在板端使用的混合产物。

## Shell 脚本里的变量和默认值

> **当前位置：`知道要找哪些工具 → [学会把本机实际路径交给脚本] → 阅读预检查脚本`**
>
> 本节只建立后面四个脚本共同使用的 Shell 语法。

### 变量保存一段文字

Shell 中：

```sh
SDK=/home/user123/rk3568_sdk
```

等号左边 `SDK` 是变量名，右边是文字值。等号两边不能有空格。赋值本身不会访问这个目录。

使用变量时写：

```sh
"$SDK"
```

`$` 表示取变量值。双引号保证路径中即使有空格，也仍作为一个参数。

### 环境变量把值交给子进程

在命令前写一次性赋值：

```sh
SDK=/实际路径 sh 某个脚本.sh
```

表示只为这次启动的 `sh` 提供 `SDK`。它不会永久修改 WSL 配置。

### `${变量:-默认值}` 提供缺省路径

真实脚本中：

```sh
SDK=${SDK:-/home/user123/rk3568_sdk}
```

含义是：

```text
如果外部已经提供 SDK
    使用外部值
否则
    使用 /home/user123/rk3568_sdk
```

因此默认路径只是历史验收环境的方便值，不是所有电脑都必须相同。

### `set -e`、`set -u` 控制失败策略

- `set -e`：某条未处理命令失败时，脚本停止，避免拿错误中间结果继续构建。
- `set -u`：读取未定义变量时停止，避免空路径悄悄变成别的目录。

`set -eu` 同时启用二者。

预检查脚本只使用 `set -u`，因为它希望把所有缺失项都列出来，而不是遇到第一个缺失就停。真正构建脚本使用 `set -eu`，因为编译依赖缺失后继续没有意义。

## 预检查脚本为什么先于构建

> **当前位置：`懂得变量和失败策略 → [完整理解 precheck_wsl.sh] → 第一次执行预检查`**
>
> 本节先给出脚本构思和完整定义，最后才执行。脚本只读取文件，不安装、删除或修改 SDK。

### 当前问题和脚本构思

构建需要多个分散在 SDK 和外部目录中的文件。如果直接编译，错误可能只说“找不到头文件”或“找不到库”，初学者很难判断是哪一层缺失。

脚本的输入是 `SDK` 环境变量或默认路径。输出是逐项 `OK`、`MISSING` 或可选的 `absent`。

流程是：

```text
取得 SDK 路径
    ↓
检查 SDK 根目录
    ↓
检查 DRM 内核头
    ↓
检查可选 libdrm / modetest
    ↓
检查 AArch64 g++
    ↓
检查 OpenCV 头和库
    ↓
检查可选部署包
```

### 首次出现的 Shell 符号

- `[ -d 路径 ]`：测试路径是否为目录。
- `[ -f 路径 ]`：测试是否为普通文件。
- `[ -e 路径 ]`：测试任何类型的路径是否存在。
- `[ -x 路径 ]`：测试文件是否存在且可执行。
- `&&`：左边成功才执行右边。
- `||`：左边失败才执行右边。
- `for 名字 in 列表; do ... done`：依次把列表中的每一项放入变量并执行循环体。
- `2>/dev/null`：把标准错误丢弃；这里用于让可选查询失败时不刷出无关错误。
- `grep -E`：从文本中筛选匹配扩展正则表达式的行。

### 完整脚本

现有文件：`Linux/RK3568/s7_4/precheck_wsl.sh`

```sh
#!/bin/sh
# 在 WSL 中检查 SDK、工具链、DRM 头和 OpenCV 是否存在。
set -u

SDK=${SDK:-/home/user123/rk3568_sdk}
HOST="$SDK/buildroot/output/rockchip_rk3568/host"
STAGING="$SDK/buildroot/output/rockchip_rk3568/staging"
TARGET="$SDK/buildroot/output/rockchip_rk3568/target"

echo "== 1. SDK 根目录 =="
[ -d "$SDK" ] && echo "OK   $SDK" || echo "MISSING $SDK"

echo "== 2. 内核 uapi DRM 头（DRM/KMS 直显必需）=="
for h in "$SDK/kernel/include/uapi/drm/drm.h" \
         "$SDK/kernel/include/uapi/drm/drm_mode.h"; do
  [ -f "$h" ] && echo "OK   $h" || echo "MISSING $h"
done
grep -E "^(VERSION|PATCHLEVEL|SUBLEVEL) =" \
  "$SDK/kernel/Makefile" 2>/dev/null || echo "MISSING kernel Makefile version"

echo "== 3. libdrm 库（可选；缺失则用内核 uapi 头裸 ioctl）=="
for f in "$STAGING/usr/include/libdrm/drm.h" \
         "$STAGING/usr/lib/libdrm.so" \
         "$TARGET/usr/lib/libdrm.so.2"; do
  [ -e "$f" ] && echo "OK   $f" || echo "absent $f (可选)"
done

echo "== 4. modetest 工具（可选，板端调试用）=="
for f in "$HOST/bin/modetest" "$HOST/usr/bin/modetest" \
         "$STAGING/usr/bin/modetest" "$TARGET/usr/bin/modetest"; do
  [ -e "$f" ] && echo "OK   $f" || echo "absent $f (可选)"
done

echo "== 5. 交叉工具链 =="
[ -x "$HOST/bin/aarch64-buildroot-linux-gnu-g++" ] \
  && echo "OK   toolchain g++" || echo "MISSING toolchain g++"

echo "== 6. OpenCV 4.5.5 构建产物（S7.3 已用）=="
for f in /home/user123/s7_3_opencv/install/include/opencv4/opencv2/imgproc.hpp \
         /home/user123/s7_3_opencv/install/lib/libopencv_core.so; do
  [ -e "$f" ] && echo "OK   $f" || echo "MISSING $f"
done

echo "== 7. 板端部署包（模型/二进制所在）=="
for f in "$SDK/../s7_3_deploy_20260813.tar.gz"; do
  [ -e "$f" ] && echo "OK   $f" || echo "absent $f (部署包可留在板端，主机不必有)"
done

echo "核验完成"
```

### 用具体输入走读

假设 `SDK=/home/user123/rk3568_sdk`：

1. `HOST` 变成 `/home/user123/rk3568_sdk/buildroot/output/rockchip_rk3568/host`。
2. 工具链测试检查 `$HOST/bin/aarch64-buildroot-linux-gnu-g++` 是否可执行。
3. 若 OpenCV 头存在，循环输出 `OK`；不存在则输出 `MISSING`，脚本仍继续。
4. 部署包不存在只输出 `absent ... (可选)`，因为主机本次构建不一定需要旧包。

### 第一次执行

**运行地点：WSL。当前目录：仓库根目录。作用：只读检查。**

```sh
sh Linux/RK3568/s7_4/precheck_wsl.sh
printf '预检查脚本退出码：%s\n' "$?"
```

因为脚本对缺失项主要使用 `echo MISSING`，它可能仍返回 0。判断构建就绪不能只看退出码，还要逐项阅读输出。关键 `MISSING` 是工具链、RKNN/OpenCV 头或库；可选 libdrm/modetest 缺失不一定阻止当前裸 DRM 实现。

若 SDK 不在默认路径：

```sh
SDK=/你的实际SDK绝对路径 sh Linux/RK3568/s7_4/precheck_wsl.sh
```

这里的中文路径只是说明位置，执行时必须替换为真实绝对路径。

## 模型转换不是模型训练

> **当前位置：`构建依赖已检查 → [把两个已有 TFLite 文件转换为 RK3568 格式] → 构建 OpenCV`**
>
> 本节先解释转换程序的输入、函数和失败出口，再展示完整 Python 文件，最后才调用。

### 转换要解决什么问题

TFLite 文件面向 TensorFlow Lite 运行时。RK3568 NPU 使用 RKNN Runtime，因此需要 Toolkit2 把模型图编译成 RKNN 格式。

这个过程会：

- 读取已有模型结构和参数；
- 固定输入预处理为 RGB 且除以 255；
- 针对 `rk3568` 编译算子；
- 可选执行 INT8 量化；
- 导出 `.rknn`；
- 保存输入输出 SHA-256、字节数和转换日志。

它不会重新训练模型，也不会改变训练数据。

### Python 文件的依赖顺序

程序按下面顺序组织：

```text
sha256(path)
    ↓ 提供文件指纹
convert(source, output, ...)
    ↓ 完成一个模型的转换
main()
    ↓ 解析两个模型参数，依次调用 convert，并写 manifest
if __name__ == "__main__"
    ↓ 只有直接运行脚本时才调用 main
```

### 首次出现的 Python 名字

- `Path`：把路径作为对象处理，提供 `open`、`resolve`、`stat` 等操作。
- `argparse.ArgumentParser`：定义命令行参数和自动错误提示。
- `RKNN`：RKNN Toolkit2 提供的转换器类。
- `ret`：return value 的缩写，保存每次 RKNN API 的整数返回值；0 表示成功。
- `try/finally`：无论转换成功或抛出异常，`finally` 都会执行 `rknn.release()` 释放资源。
- `manifest`：清单对象，记录工具版本、输入指纹、输出指纹和参数。
- `if __name__ == "__main__"`：区分“直接运行脚本”和“被其他 Python 文件导入”。

### 一个模型的转换流程

`convert(source, output, quantize, dataset, log_file)` 接收：

- `source`：输入 TFLite 路径；
- `output`：输出 RKNN 路径；
- `quantize`：是否做 INT8 量化；
- `dataset`：量化时使用的校准图片清单；FP16 时不用；
- `log_file`：Toolkit2 详细日志路径。

它不返回模型对象；成功时输出文件出现在 `output`，失败时抛出异常并终止。

关键 API 按顺序是：

```text
RKNN(...)
  ↓ config：规定输入预处理和目标平台
load_tflite：读取源模型
  ↓
build：编译模型，可选量化
  ↓
export_rknn：写出模型文件
  ↓
release：释放转换器资源
```

顺序不能交换：模型尚未加载时不能 build，build 尚未完成时不能导出。

### 完整转换脚本

现有文件：`Linux/RK3568/s7_3/convert_models.py`

```python
#!/usr/bin/env python3
"""把已经冻结的两个 TFLite 手部模型转换为 RK3568 RKNN 模型。"""

import argparse
import hashlib
import json
from pathlib import Path

from rknn.api import RKNN


def sha256(path):
    """分块读取文件并返回 SHA-256；分块避免一次把大模型全部读入内存。"""
    digest = hashlib.sha256()
    with path.open("rb") as stream:
        for chunk in iter(lambda: stream.read(1024 * 1024), b""):
            digest.update(chunk)
    return digest.hexdigest()


def convert(source, output, quantize, dataset, log_file):
    """转换一个模型；任何 RKNN API 返回非 0 都立即转成明确异常。"""
    rknn = RKNN(verbose=True, verbose_file=str(log_file))
    try:
        ret = rknn.config(
            mean_values=[[0.0, 0.0, 0.0]],
            std_values=[[255.0, 255.0, 255.0]],
            target_platform="rk3568",
        )
        if ret != 0:
            raise RuntimeError("rknn.config failed: {}".format(ret))

        ret = rknn.load_tflite(model=str(source))
        if ret != 0:
            raise RuntimeError("rknn.load_tflite failed: {}".format(ret))

        ret = rknn.build(
            do_quantization=quantize,
            dataset=str(dataset) if quantize else None,
        )
        if ret != 0:
            raise RuntimeError("rknn.build failed: {}".format(ret))

        ret = rknn.export_rknn(str(output))
        if ret != 0:
            raise RuntimeError("rknn.export_rknn failed: {}".format(ret))
    finally:
        rknn.release()


def main():
    """解析两个模型路径，逐个转换并写出可追溯清单。"""
    parser = argparse.ArgumentParser()
    parser.add_argument("--detector", type=Path, required=True)
    parser.add_argument("--landmark", type=Path, required=True)
    parser.add_argument("--output", type=Path, required=True)
    parser.add_argument("--quantize", action="store_true")
    parser.add_argument("--detector-dataset", type=Path)
    parser.add_argument("--landmark-dataset", type=Path)
    args = parser.parse_args()

    if args.quantize and (not args.detector_dataset or not args.landmark_dataset):
        parser.error("quantized conversion requires both dataset files")

    args.output.mkdir(parents=True, exist_ok=True)
    suffix = "int8" if args.quantize else "fp16"
    models = [
        ("hand_detector", args.detector, args.detector_dataset),
        ("hand_landmarks_detector", args.landmark, args.landmark_dataset),
    ]
    manifest = {
        "toolkit": "1.3.0",
        "target": "rk3568",
        "quantized": args.quantize,
        "preprocess": {
            "color": "RGB",
            "mean": [0, 0, 0],
            "std": [255, 255, 255],
        },
        "models": [],
    }

    for name, source, dataset in models:
        output = args.output / "{}_{}.rknn".format(name, suffix)
        log_file = args.output / "{}_{}_convert.log".format(name, suffix)
        convert(source.resolve(), output, args.quantize, dataset, log_file)
        manifest["models"].append(
            {
                "name": name,
                "source_sha256": sha256(source),
                "output": output.name,
                "output_bytes": output.stat().st_size,
                "output_sha256": sha256(output),
                "dataset": str(dataset) if dataset else None,
                "log": log_file.name,
            }
        )

    (args.output / "conversion_manifest.json").write_text(
        json.dumps(manifest, indent=2, sort_keys=True) + "\n",
        encoding="utf-8",
    )
    print(json.dumps(manifest, sort_keys=True))
    return 0


if __name__ == "__main__":
    raise SystemExit(main())
```

教程中的完整版本只增加了帮助理解的中文注释，没有改变函数名、参数、控制流程和输出合同。工程实际执行仍使用仓库中的原文件。

### FP16 具体输入走读

不带 `--quantize` 时：

1. `args.quantize=False`。
2. `suffix="fp16"`。
3. 两个 `dataset` 都是 `None`。
4. `rknn.build(do_quantization=False, dataset=None)`。
5. 输出名分别为 `hand_detector_fp16.rknn` 和 `hand_landmarks_detector_fp16.rknn`。
6. `conversion_manifest.json` 记录两个输入/输出文件指纹。

历史验收比较了 FP16 与 INT8：FP16 有效/拒绝一致率约 0.9951，并满足全部冻结 P95 误差；INT8 虽更快，但一致率约 0.9182，多项误差超限，所以项目采用 FP16。这是历史实物证据，不是仅凭转换成功作出的决定。

### 第一次运行转换

运行前先进入已经安装 RKNN Toolkit2 1.3.0 的 Python 虚拟环境。Shell 内置命令 `.` 会在当前 Shell 中读取激活脚本，使 `python` 和 Python 包路径指向该环境。

**运行地点：WSL。当前目录：仓库根目录。作用：转换模型，不训练模型。**

```sh
. /home/user123/s7_3_toolkit/bin/activate

python Linux/RK3568/s7_3/convert_models.py \
  --detector /实际模型目录/hand_detector.tflite \
  --landmark /实际模型目录/hand_landmarks_detector.tflite \
  --output /home/user123/s7_3_models_course_fp16
```

必须把“实际模型目录”替换为现有文件的绝对路径。正常输出目录至少包含：

```text
hand_detector_fp16.rknn
hand_detector_fp16_convert.log
hand_landmarks_detector_fp16.rknn
hand_landmarks_detector_fp16_convert.log
conversion_manifest.json
```

失败时第一检查点：

| 现象 | 第一检查点 |
|---|---|
| `ModuleNotFoundError: rknn` | 是否激活了 Toolkit2 环境，Python 版本是否匹配 wheel |
| 找不到 TFLite | 两个绝对路径是否真实存在 |
| `rknn.load_tflite failed` | 转换日志和源模型 SHA-256 |
| build 算子失败 | 转换日志中的具体算子，不要先替换板端 Runtime |

## 为什么项目单独构建最小 OpenCV

> **当前位置：`模型已经转换 → [准备板端程序依赖的图像处理库] → 编译板端程序`**
>
> 本节先解释 CMake 配置和构建脚本，再第一次执行。

完整 OpenCV 包含 GUI、视频编码、网络等大量模块。S7.3 离线程序只需要：

- `core`：矩阵和基本数据；
- `imgproc`：颜色、缩放、仿射变换；
- `imgcodecs`：JPEG 图片读写。

只构建三项能减少旧 Buildroot 环境中的无关依赖问题。

### 首次出现的构建名字

- `CMake`：读取项目构建描述并生成 Makefile。
- `toolchainfile.cmake`：告诉 CMake 使用哪套交叉编译器和目标系统路径。
- `Release`：启用面向交付的优化构建配置。
- `BUILD_SHARED_LIBS=ON`：生成动态库 `.so`。
- `make -j4`：用最多 4 个并行任务执行编译。
- `make install`：把构建结果复制到脚本规定的安装目录；这里不是安装到 Windows 或 RK3568 系统根目录。

### 脚本构思

输入：

- `SDK`：SDK 根目录；
- `BUILD`：本次 OpenCV 构建目录。

输出：

- `$BUILD/install/include`：头文件；
- `$BUILD/install/lib`：AArch64 OpenCV 动态库。

流程：

```text
定位 SDK 内 OpenCV 源码和 host 工具
    ↓
建立独立构建目录
    ↓
CMake 读取源码并使用 Buildroot toolchain
    ↓
只启用 core/imgproc/imgcodecs
    ↓
make 编译
    ↓
make install 放入独立 install 目录
```

### 完整脚本

现有文件：`Linux/RK3568/s7_3/build_opencv.sh`

```sh
#!/bin/sh
set -eu

SDK=${SDK:-/home/user123/rk3568_sdk}
SOURCE="$SDK/buildroot/output/rockchip_rk3568/build/opencv4-4.5.5"
HOST="$SDK/buildroot/output/rockchip_rk3568/host"
BUILD=${BUILD:-/home/user123/s7_3_opencv}

mkdir -p "$BUILD"
cd "$BUILD"

"$HOST/bin/cmake" "$SOURCE" \
  -DCMAKE_TOOLCHAIN_FILE="$HOST/share/buildroot/toolchainfile.cmake" \
  -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_INSTALL_PREFIX="$BUILD/install" \
  -DBUILD_LIST=core,imgproc,imgcodecs \
  -DBUILD_SHARED_LIBS=ON \
  -DBUILD_TESTS=OFF \
  -DBUILD_PERF_TESTS=OFF \
  -DBUILD_EXAMPLES=OFF \
  -DBUILD_opencv_apps=OFF \
  -DBUILD_JPEG=ON \
  -DWITH_JPEG=ON \
  -DWITH_PNG=OFF \
  -DWITH_TIFF=OFF \
  -DWITH_WEBP=OFF \
  -DWITH_OPENJPEG=OFF \
  -DWITH_PROTOBUF=OFF \
  -DWITH_IPP=OFF \
  -DWITH_OPENCL=OFF \
  -DWITH_ITT=OFF

make -j4
make install
```

`mkdir -p` 创建目录；已存在时不报错。这个脚本会复用指定 BUILD 目录中的已有 CMake 状态。若要做完全干净的重建，应选择一个新的空 BUILD 路径，不要删除不确定的旧目录。

### 第一次执行

**运行地点：WSL。当前目录：仓库根目录。作用：编译 AArch64 OpenCV，不运行板端代码。**

```sh
SDK=/home/user123/rk3568_sdk \
BUILD=/home/user123/s7_3_opencv_course \
sh Linux/RK3568/s7_3/build_opencv.sh
```

正常完成后，用已解释过的 `ls` 和 `file` 检查：

```sh

file /home/user123/s7_3_opencv_course/install/lib/libopencv_core.so
```

预期库面向 ARM AArch64。编译成功只证明库已生成，不证明板端动态加载成功。

## 板端推理程序怎样完成交叉编译

> **当前位置：`模型和 OpenCV 已准备 → [把 C++ 源码编译并链接为 AArch64 ELF] → 部署到板端`**
>
> 本节先解释每一组编译参数，再展示完整脚本和第一次调用。

### 编译脚本输入和输出

输入：

- `s7_3_board_infer.cpp`；
- OpenCV 头文件与 AArch64 库；
- RKNN API 头文件与 AArch64 `librknnrt`；
- SDK 交叉编译器。

输出：

- `Linux/RK3568/s7_3/s7_3_board_infer`。

### 编译参数第一次解释

| 参数 | 作用 | 缺失时的具体问题 |
|---|---|---|
| `-std=c++17` | 按 C++17 语法编译 | 源码使用的语言特性可能不被识别 |
| `-O2` | 开启常用优化 | 程序可编译但性能可能明显降低 |
| `-Wall -Wextra` | 打开常见警告 | 潜在类型/未使用问题不易发现 |
| `-I路径` | 增加头文件搜索目录 | 报 `No such file or directory` |
| `-L路径` | 增加库搜索目录 | 链接器找不到目标库 |
| `-lopencv_core` | 链接 `libopencv_core.so` | 出现未定义 OpenCV 符号 |
| `-lrknnrt` | 链接 RKNN Runtime | 出现未定义 RKNN API 符号 |
| `-o 路径` | 指定输出文件 | 使用编译器默认输出名 |
| `-Wl,-rpath,'$ORIGIN/lib'` | 把运行时库相对位置写进 ELF | 板端可能找不到随程序部署的 `lib/` |

`$ORIGIN` 由 Linux 动态加载器在运行时解释为“可执行文件所在目录”。单引号阻止构建时 Shell 把它当普通变量展开。因此板端目录可以组织为：

```text
部署目录/
├── s7_3_board_infer
└── lib/
    ├── libopencv_core.so...
    ├── libopencv_imgproc.so...
    └── libopencv_imgcodecs.so...
```

### 完整脚本

现有文件：`Linux/RK3568/s7_3/build_board.sh`

```sh
#!/bin/sh
set -eu

SCRIPT_DIR=$(CDPATH= cd -- "$(dirname -- "$0")" && pwd)
SDK=${SDK:-/home/user123/rk3568_sdk}
HOST="$SDK/buildroot/output/rockchip_rk3568/host"
RKNN="$SDK/external/rknpu2/runtime/RK356X/Linux/librknn_api"
OPENCV=${OPENCV:-/home/user123/s7_3_opencv/install}

"$HOST/bin/aarch64-buildroot-linux-gnu-g++" \
  -std=c++17 -O2 -Wall -Wextra \
  "$SCRIPT_DIR/s7_3_board_infer.cpp" \
  -I"$OPENCV/include/opencv4" \
  -I"$RKNN/include" \
  -L"$OPENCV/lib" \
  -L"$RKNN/aarch64" \
  -Wl,-rpath,'$ORIGIN/lib' \
  -lopencv_imgcodecs -lopencv_imgproc -lopencv_core -lrknnrt \
  -o "$SCRIPT_DIR/s7_3_board_infer"

file "$SCRIPT_DIR/s7_3_board_infer"
```

### `SCRIPT_DIR` 为什么写得复杂

`$0` 是当前脚本的启动路径。`dirname -- "$0"` 取脚本所在目录。`cd` 进入该目录，`pwd` 再得到绝对路径。`$(...)` 表示把括号内命令的标准输出作为文字使用。

最终 `SCRIPT_DIR` 始终指向脚本自身目录。因此无论你从仓库根目录还是别的目录调用脚本，它都能找到旁边的 `s7_3_board_infer.cpp`。

具体输入：

```text
$0 = Linux/RK3568/s7_3/build_board.sh
dirname = Linux/RK3568/s7_3
cd + pwd = /mnt/e/.../GETFUN_F722_FreeRTOS/Linux/RK3568/s7_3
```

### 第一次执行

如果 OpenCV 使用本篇新构建目录，必须把它通过 `OPENCV` 传入：

**运行地点：WSL。当前目录：仓库根目录。作用：交叉编译，不执行板端程序。**

```sh
SDK=/home/user123/rk3568_sdk \
OPENCV=/home/user123/s7_3_opencv_course/install \
sh Linux/RK3568/s7_3/build_board.sh
```

脚本最后调用 `file`。预期包含 `ELF 64-bit` 和 `ARM aarch64`。若显示 x86-64，说明没有使用目标交叉编译器。

## 产物为什么还要计算 SHA-256

> **当前位置：`WSL 已生成模型和程序 → [固定产物身份] → 复制到 RK3568`**
>
> 本节建立“复制前后是否同一文件”的证据。

SHA-256 根据文件全部字节计算固定长度摘要。它不证明算法正确，但能回答：“板端文件是否与 WSL 这份逐字节相同？”

`sha256sum` 接收一个或多个文件路径，输出摘要和路径。

**运行地点：WSL。**

```sh
sha256sum \
  /home/user123/s7_3_models_course_fp16/hand_detector_fp16.rknn \
  /home/user123/s7_3_models_course_fp16/hand_landmarks_detector_fp16.rknn \
  Linux/RK3568/s7_3/s7_3_board_infer
```

保存这三行。后面在板端对相同文件再执行一次；摘要必须对应相同。

## 安全地建立新的板端部署目录

> **当前位置：`产物身份已固定 → [复制到独立的板端目录] → 下一篇加载并运行`**
>
> 本节只部署文件，不打开摄像头和 NPU。为了不覆盖已有验收环境，使用新的课程目录。

### 先解释 `test` 和 `mkdir`

Shell 内置工具 `test` 检查条件，不打印正常结果，只用退出码表达真假。

`test -e 路径`：

- 路径存在时退出码 0；
- 不存在时退出码 1。

`mkdir` 创建目录。不带 `-p` 时，如果目录已存在会失败，因此不会默默复用旧内容。

在板端选择新目录：

```text
/userdata/gesture_rc_course_run1
```

先检查是否存在：

**运行地点：RK3568 板端。**

```sh
test -e /userdata/gesture_rc_course_run1
printf '目录已存在时为0，不存在时为1：%s\n' "$?"
```

只有输出 1 时，才创建：

```sh
mkdir /userdata/gesture_rc_course_run1
mkdir /userdata/gesture_rc_course_run1/lib
```

若第一条输出 0，换一个新目录名，不删除也不覆盖已有目录。

### `scp` 怎样复制文件

`scp` 是 secure copy 的缩写，通过 SSH 加密通道复制文件。结构是：

```text
scp 本地路径 root@板端IP:远程目录/
```

输入是 WSL 文件，输出是板端副本。它不会执行文件。

假设已经用上一篇方法确认当前板端 IP 是 `169.254.151.86`，执行：

**运行地点：WSL；当前目录：仓库根目录。**

```sh
scp Linux/RK3568/s7_3/s7_3_board_infer \
  root@169.254.151.86:/userdata/gesture_rc_course_run1/

scp /home/user123/s7_3_models_course_fp16/hand_detector_fp16.rknn \
  /home/user123/s7_3_models_course_fp16/hand_landmarks_detector_fp16.rknn \
  root@169.254.151.86:/userdata/gesture_rc_course_run1/
```

OpenCV 动态库有真实文件和符号链接。选项 `-r` 表示递归复制目录。为避免把不相关构建文件复制上板，先在 WSL 用 `ls` 确认 `install/lib` 内容，再只复制三个库族：

```sh
scp /home/user123/s7_3_opencv_course/install/lib/libopencv_core.so* \
  /home/user123/s7_3_opencv_course/install/lib/libopencv_imgproc.so* \
  /home/user123/s7_3_opencv_course/install/lib/libopencv_imgcodecs.so* \
  root@169.254.151.86:/userdata/gesture_rc_course_run1/lib/
```

`*` 是 Shell 通配符，匹配同一库的版本文件和符号链接。执行前必须先用 `ls` 展开检查，避免范围超出预期。

### 板端逐项验证

SSH 登录板端，进入新目录后：

```sh
cd /userdata/gesture_rc_course_run1
ls -l
file s7_3_board_infer
sha256sum s7_3_board_infer hand_detector_fp16.rknn hand_landmarks_detector_fp16.rknn
```

检查：

1. `file` 仍显示 AArch64 ELF；
2. 三个 SHA-256 与 WSL 保存值一致；
3. `lib/` 中存在三类 OpenCV 库；
4. 本篇还没有执行 `./s7_3_board_infer`，所以不能声称 RKNN Runtime 或 NPU 已通过。

## 本篇验证闭环

| 层 | 正常证据 | 失败现象 | 第一检查点 |
|---|---|---|---|
| SDK 路径 | 预检查关键项 `OK` | 大量 `MISSING` | `SDK` 是否指向完整 SDK |
| Toolkit2 | Python 能导入 `rknn.api` | 模块不存在/版本错误 | 虚拟环境与 Python 版本 |
| 模型转换 | 两个 RKNN、两份日志、manifest | 只生成部分文件 | 对应转换日志与退出码 |
| OpenCV | install 下有 AArch64 头/库 | CMake 或 make 失败 | 第一条真实错误，不看最后一串连锁错误 |
| 程序构建 | `file` 显示 AArch64 ELF | x86-64 或链接失败 | 编译器路径、`-I`、`-L` |
| 产物身份 | WSL 和板端 SHA-256 相同 | 摘要不同 | 复制源、目标和文件大小 |
| 部署边界 | 新目录含程序、模型、lib | 复用了旧目录 | 换新目录，不覆盖历史证据 |

本篇确认的是“构建与部署副本完整”。它没有确认板端能加载动态库、模型能初始化、NPU 能推理或摄像头能实时采集。下一篇从板端程序启动时的动态加载开始，接通摄像头与 NPU。

## 只改变一个条件的迁移练习

保持源码、模型和所有编译参数不变，只改变 `OPENCV` 路径为一个不存在目录：

```sh
OPENCV=/tmp/intentionally_missing_opencv \
sh Linux/RK3568/s7_3/build_board.sh
```

预期编译器首先报告找不到 OpenCV 头文件或链接库，退出码非 0。这个练习证明 `-I` 和 `-L` 依赖真实目录，不是装饰参数。

不要为了让练习“通过”而创建假文件。记录第一条错误后，重新使用正确 `OPENCV` 路径构建，并确认 AArch64 ELF 恢复。
