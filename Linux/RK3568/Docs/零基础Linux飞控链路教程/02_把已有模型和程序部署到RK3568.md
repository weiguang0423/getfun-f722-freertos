# 把已有模型和程序部署到 RK3568

> **当前学习位置：** `能够登录 WSL 和 RK3568` → **固定输入、交叉编译并复制部署副本** → `摄像头实时推理`
>
> 本篇解决“模型已经存在时，怎样把能在 RK3568 上运行的程序和模型准备好”。不讨论模型训练，也不会把外部模型、SDK 或生成的二进制文件误当成 Git 源码。

## 先回答：部署到底在部署什么

一个“模型部署结果”至少有四类东西，不是把一个 `.rknn` 文件复制过去就结束：

```text
Git 源码/脚本 ──> WSL 交叉编译 ──> ARM64 可执行程序
外部 TFLite 模型 ──> 固定 Toolkit2 转换 ──> RK3568 FP16 .rknn 模型
OpenCV 运行库 ──> 随部署副本提供 ──> 板端加载
上述副本 ──> 板端运行 ──> 日志与验收结果
```

**部署**是把“已知版本的一组输入”变成“板子上可运行的一组副本”，然后验证副本的行为。模型训练是在部署之前发生的事情，本课程不需要改变模型权重，也不会覆盖训练流程。

## 先分清哪些文件属于 Git，哪些是外部产物

项目的边界在 [Linux/RK3568/README.md](../../README.md) 中已经固定。初学时最容易犯的错误，是在 Windows、WSL 与板端各保存一份不同源码，最后不知道哪个才是真实版本。

| 类别 | 例子 | 正确处理 |
|---|---|---|
| Git 原件 | `s7_4/build_board.sh`、`.cpp`、`.hpp`、测试、README、验收摘要 | 在 Windows 仓库修改并提交；WSL/板端只是使用副本 |
| 外部依赖 | RK3568 SDK、RKNN Toolkit2、TFLite 模型、OpenCV 构建目录 | 记录来源、版本、路径和 SHA-256；不直接塞进普通 Git 提交 |
| 可重建产物 | ARM64 ELF、`.rknn`、部署包、一次运行 JSONL | 可以重新生成；正式交付时同 Git 标签一起归档并校验 |
| 板端临时文件 | `/tmp` 下的测试文件、运行日志、采集结果 | 知道它可能重启后消失；需要保留时主动取回到 PC |

**不要**把“RK3568 板上能运行”理解成“板子就是唯一源代码仓库”。板端常常是部署副本，重刷系统或误删后应当能从 Windows/WSL 重新构建。

## 为什么同一份 C++ 不能直接在 WSL 运行

> **概念说明：CPU 架构与交叉编译**
>
> `x86_64` 是普通 PC 常见的 CPU 指令语言，`aarch64` 是 RK3568 的 ARM64 指令语言。CPU 不能直接执行另一种指令语言。交叉编译器运行在 x86_64 的 WSL 中，但输出 aarch64 程序。

可用下面命令看一个文件是不是给 RK3568 生成的：

**运行地点：WSL。**

```sh
cd /mnt/e/getfun-f722-freertos/GETFUN_F722_FreeRTOS
file Linux/RK3568/s7_3/s7_3_board_infer
```

`file` 不执行程序，只识别文件格式。输出包含 `ELF 64-bit ... aarch64` 时，说明它是 ARM64 程序。把它直接放在 WSL 执行通常会看到 `Exec format error`；这不表示程序坏了，只表示运行地点错了。

## 模型为什么选择 FP16 而不是 INT8

你不需要会训练模型，但需要会理解部署选择。S7.3 使用同一批 2859 帧固定输入，在 PC 参考链与 RK3568 上分别运行，然后比较输出是否还足够接近。

| 模型版本 | 速度特点 | 实测结论 | 项目决定 |
|---|---|---|---|
| FP16 | NPU 推理较慢 | 有效/拒绝一致率 `0.995103`，各冻结 P95 误差合格 | 采用 |
| INT8 | NPU 推理更快 | 有效/拒绝一致率 `0.918153`，多项误差超限 | 拒绝 |

FP16 和 INT8 是模型数值精度形式。INT8 的文件更小、通常更快，但如果手框或关键点偏差太大，后面的手势状态机会基于错误输入工作。因此本项目选择“通过误差门槛的 FP16”，而不是只选速度最快的版本。

已冻结的 FP16 模型是：

```text
hand_detector_fp16.rknn
hand_landmarks_detector_fp16.rknn
```

它们的来源、SHA-256、运行库与验收数据在 [Docs/38_S7.3_RKNN转换与板端NPU推理验收记录.md](../../../../Docs/38_S7.3_RKNN转换与板端NPU推理验收记录.md) 中。模型文件路径是当时验收环境的记录；换电脑时使用自己的存放位置即可，但必须重新核对文件指纹。

## 在 WSL 中先检查，而不是盲目构建

> **当前学习位置：** `知道哪些是部署输入` → **检查 WSL 交叉编译环境** → `生成 ARM64 程序`

本项目给 S7.4 提供了预检查脚本。它只读取 SDK、头文件和库是否存在，不下载软件，也不修改系统。

**运行地点：WSL。**

```sh
cd /mnt/e/getfun-f722-freertos/GETFUN_F722_FreeRTOS
sh Linux/RK3568/s7_4/precheck_wsl.sh
```

脚本会检查 SDK 路径、ARM64 交叉编译器、RKNN API 头文件、OpenCV 和可选 DRM 头文件。输出中的 `OK` 表示当前找到该项；`MISSING` 表示先解决环境或路径，不要跳过检查继续编译。

脚本默认的 SDK 是历史验收环境中的：

```text
/home/user123/rk3568_sdk
```

这不是硬编码的项目接口。你的 SDK 不在这里时，先给当前命令设置变量，而不是修改别人的绝对路径：

```sh
SDK=/你的实际SDK路径 sh Linux/RK3568/s7_4/build_board.sh
```

`SDK=...` 只对紧随其后的这一条命令生效；它告诉脚本去哪找 SDK。

## 交叉编译时，脚本替你连接哪些部件

以 S7.4 为例，下面命令在 WSL 执行：

```sh
cd /mnt/e/getfun-f722-freertos/GETFUN_F722_FreeRTOS
sh Linux/RK3568/s7_4/build_board.sh
file Linux/RK3568/s7_4/s7_4_live
```

`build_board.sh` 没有重新实现手势算法。它把已有模块编译到同一个 ARM64 程序中：

```text
s7_3_board_infer.cpp  ：两级模型的前后处理和 RKNN 推理
s7_4_display.cpp      ：可选 DRM 屏显
s7_4 的构建选项      ：V4L2 实时入口
OpenCV/RKNN Runtime   ：图像处理和 NPU API
```

在构建日志中，最重要的不是“屏幕上没有红字”，而是最后 `file` 的架构确认：生成物必须是 `aarch64`。它证明交叉编译链可用；**它不能证明摄像头、NPU 或串口在实物板上已经工作。**

S7.6 的构建脚本还有一个真实兼容性细节：板端 Buildroot 使用 glibc 2.35，而 SDK host 中的较新编译器可能生成要求 glibc 2.36 以上的程序。因此 `s7_6/build_board.sh` 默认采用 `aarch64-linux-gnu-g++-10`。这不是“哪个编译器更新就选哪个”，而是为了让产物能被当前板端系统加载。若脚本报告找不到交叉编译器，先记录错误和 `file` 输出，再补齐与板端兼容的工具链。

## 复制到板端时，先创建一份明确的部署目录

部署目录是板端运行副本的家。不要把程序直接丢到根目录，也不要覆盖不清楚来源的旧文件。下面使用一个新目录名称作为示例：

**运行地点：RK3568 板端。**

```sh
mkdir -p /userdata/gesture_rc_demo
ls -ld /userdata/gesture_rc_demo
```

`mkdir -p` 会在目录不存在时创建它，已存在时不会报错；`ls -ld` 只显示这个目录本身。确认后从 **WSL** 复制实际需要的文件。账号、IP、模型路径必须按你的板端实际情况替换：

```sh
scp Linux/RK3568/s7_4/s7_4_live root@板端IP:/userdata/gesture_rc_demo/
scp /你的FP16模型目录/hand_detector_fp16.rknn root@板端IP:/userdata/gesture_rc_demo/
scp /你的FP16模型目录/hand_landmarks_detector_fp16.rknn root@板端IP:/userdata/gesture_rc_demo/
```

复制完成后，在 **RK3568 板端** 用下面命令确认副本，而不是默认认为传输成功：

```sh
cd /userdata/gesture_rc_demo
ls -lh
sha256sum s7_4_live hand_detector_fp16.rknn hand_landmarks_detector_fp16.rknn
```

如果你有构建或验收时记录的 SHA-256，逐项对照。`scp` 传输成功只代表网络传输完成；SHA-256 对得上才证明得到同一字节文件。

## 这一步的验证出口

完成本篇时，应当拿到这四类证据：

1. WSL 能找到项目和 SDK 依赖，预检查没有关键 `MISSING`。
2. `file s7_4_live` 明确显示 ARM64/aarch64，而不是 x86-64。
3. 板端部署目录中同时有可执行文件、两份 FP16 `.rknn` 和需要的运行库副本。
4. 板端 `sha256sum` 与你保存的输入/构建记录一致。

常见失败的第一检查点：

| 现象 | 第一检查点 | 含义 |
|---|---|---|
| `command not found` | 当前是不是 WSL；脚本是否以 `sh 路径` 执行 | 不是模型错误 |
| `No such file or directory` 但文件明明在 Windows | 是否把 `E:\...` 改成了 `/mnt/e/...` | 路径体系混用了 |
| 板端报 GLIBC 版本不满足 | 是否使用了与 Buildroot 兼容的 S7.6 工具链 | 不是摄像头故障 |
| WSL 运行 ARM64 程序报 `Exec format error` | `file` 输出和运行地点 | 应把程序复制到 RK3568 运行 |
