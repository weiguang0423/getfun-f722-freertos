# 从零学习 RK3568 Linux 与飞控链路：课程地图

> **文档进度：`[本篇：认识最终目标和学习路线] → Linux基本操作 → 构建与部署 → 摄像头/NPU → 手势 → 虚拟RC → 飞控 → 拆桨验收`**
>
> **真实数据流位置：`摄像头 → RK3568 Linux → 串口 → STM32F722 → 飞控安全链`**
>
> 本篇只解决三个问题：最终要搭成什么、为什么要分阶段、每个阶段会留下什么可检查的结果。本篇不要求你输入任何 Linux 命令，也不假设你知道 Linux 是怎样工作的。

## 先从你真正想完成的事情出发

你已经明确了两个边界：

1. 你不关心开源手部模型是怎样训练出来的。
2. 你关心怎样把已有模型放到 RK3568 上运行，以及怎样把 Linux 的识别结果安全地送进飞控。

因此，这套课程不会从神经网络训练、损失函数或数据标注讲起。我们把两个已经存在的模型文件当成“输入材料”，从它们怎样变成 RK3568 能运行的 `.rknn` 文件开始学习。

最终要亲手理解并能复现的真实链路是：

```text
IMX335 摄像头产生一帧画面
        ↓
RK3568 上的 Linux 从 /dev/video0 取得这一帧
        ↓
RK3568 的 NPU 运行两个已有模型
        ↓
得到手框、21 个手部关键点和置信度
        ↓
Linux 根据关键点判断手势，并等待多帧确认
        ↓
Linux 把确认后的手势变成受限的虚拟 RC 候选帧
        ↓
RK3568 UART 把 44 字节候选帧发给 STM32F722 USART6
        ↓
飞控检查帧、检查人工授权、检查物理遥控器和 Failsafe
        ↓
条件全部满足时，只允许 Linux 临时替换 Roll/Pitch/Yaw
        ↓
飞控已有 setpoint、PID、Mixer、ARM/Failsafe 和 DShot 链继续工作
```

这里有一个贯穿全课程的关键：**Linux 只提出候选动作，飞控决定是否采用。**

这不是措辞区别，而是安全架构。如果 Linux 识别错了一帧、摄像头断开、进程卡住、串口拔掉或系统重启，飞控必须能把 Linux 候选判为无效，并立即回到物理遥控器。Linux 没有权限直接 ARM，也没有权限直接写 PID、Mixer 或 DShot。

## 为什么不能直接从“运行程序”开始

如果现在直接让你用一条尚未解释的命令启动“摄像头识别并向串口发送”的最终程序，即使照着复制后碰巧运行成功，也不能说明你学会了这条链路。你仍然不知道：

- 命令应该在哪台机器上运行；
- `/dev/ttyS9` 是文件、串口还是程序；
- 为什么串口设备要在程序启动前显式指定；
- 为什么 Linux 运行当前目录程序时需要明确路径；
- 程序怎样选择“实时摄像头”而不是“离线图片”入口；
- 输出到了屏幕还是文件；
- 程序失败时怎样看退出码；
- 这条命令是否已经影响飞控。

这些缺口会让后续排错变成反复试命令。因此课程必须先建立 Linux 的最小心智模型，再让命令逐步出现。

本课程使用下面的工程循环。每完成一篇，得到的结果会成为下一篇可以依赖的起点：

```text
现在已经能观察到什么
        ↓
当前还缺什么能力
        ↓
为什么选择这一种设计
        ↓
先解释将出现的名字和数据
        ↓
再展示脚本或代码怎样实现
        ↓
用一个具体输入走完整条路径
        ↓
运行并保存证据
        ↓
把已确认结果交给下一篇
```

## 你实际上会操作三种环境

> **当前位置：`认识最终系统 → [分清三种操作环境] → 建立每篇课程的产物`**
>
> 本节只建立三种环境的角色，不教登录命令。完成后，你应当先问“这条命令在哪个环境运行”，再关心命令本身。

本项目里“Linux”不是一个单独地点。你会接触 Windows、WSL 和 RK3568 板端 Linux。

### Windows：保存项目原件和打开工具

Windows 是你的日常电脑系统。Git 仓库位于：

```text
E:\getfun-f722-freertos\GETFUN_F722_FreeRTOS
```

课程中新建的 Markdown、项目 C/C++ 源码和脚本原件都保存在这个仓库。Windows 是项目文件的主存放位置，不是 RK3568 程序的最终运行环境。

### WSL：在 Windows 电脑里运行的 Linux 构建环境

WSL 是 Windows Subsystem for Linux 的缩写，中文可以理解为“Windows 里的 Linux 子系统”。

本项目使用 WSL 做三类工作：

- 运行 RKNN Toolkit2，把已有 TFLite 模型转换成 RK3568 使用的 RKNN 模型；
- 使用 ARM64 交叉编译器生成 RK3568 可执行程序；
- 在没有摄像头和 NPU 的情况下，先运行纯逻辑测试。

WSL 的 CPU 仍然是电脑的 x86-64 CPU。它只是能够运行 Linux 工具，并不因此变成 RK3568。

### RK3568 板端 Linux：真正连接摄像头和 NPU 的运行环境

ATK-DLRK3568 开发板运行 Buildroot Linux，CPU 架构是 AArch64，也就是 ARM64。摄像头 `/dev/video0`、NPU Runtime、显示屏 DRM 设备和 UART 都在这台板子上。

WSL 生成 ARM64 程序后，要把程序复制到 RK3568，再由 RK3568 执行。这个过程叫作“交叉编译后部署”。

三者的关系可以先记成：

```text
Windows 仓库：保存源码原件
      ↓ WSL 看到 Windows 盘并读取源码
WSL：把源码编译成 ARM64 程序
      ↓ 通过网络或其他方式复制
RK3568：运行 ARM64 程序并连接真实硬件
```

## 课程怎样从零走到项目结果

> **当前位置：`三种环境已经分清 → [确认每篇的输入和输出] → 从第一篇开始实践`**
>
> 本节给出课程依赖关系。后面的篇章不能随意跳读，因为每一篇会使用前文已经解释和验证过的能力。

### 课程 01：先建立 Linux 的最小心智模型

文件：`01_先会操作三台Linux相关机器.md`

开始时你只需要会使用 Windows。课程会从“文件和目录是什么”开始，依次解释：

- Windows 路径与 Linux 路径为什么不同；
- 终端、Shell、命令、参数分别是什么；
- 当前目录和绝对路径是什么；
- 普通文件、目录、设备文件有什么区别；
- 程序怎样成为一个进程；
- 标准输出、错误输出和退出码怎样留下证据；
- 文件权限为什么会导致 `Permission denied`；
- 怎样判断当前是在 WSL 还是 RK3568。

本篇完成时的可观察结果：你能进入 WSL 和 RK3568，能用已经解释过的只读命令定位自己、查看文件，并把命令结果和退出码保存下来。

### 课程 02：把已有模型和源码变成 RK3568 产物

文件：`02_把已有模型和程序部署到RK3568.md`

开始时你已经会操作 Shell、理解路径和退出码。本篇再引入：

- 源码、头文件、库、可执行文件分别是什么；
- x86-64 与 AArch64 为什么不能直接互相运行程序；
- SDK、工具链、头文件路径、库路径解决什么问题；
- 环境变量怎样把实际 SDK 路径交给脚本；
- Shell 脚本中的变量、条件、循环、退出策略；
- `convert_models.py` 怎样转换模型而不是训练模型；
- `build_opencv.sh` 和 `build_board.sh` 每一行怎样组成构建过程。

本篇完成时的可观察结果：WSL 生成 `.rknn` 文件和 AArch64 ELF 可执行程序，`file` 与 SHA-256 给出可保存的产物证据。

### 课程 03：让 RK3568 从摄像头得到实时关键点

文件：`03_摄像头到手部关键点.md`

开始时你已经有 ARM64 程序和模型。本篇会解释：

- Linux 为什么把摄像头表示成 `/dev/video0`；
- V4L2、NV12、MMAP 缓冲分别解决什么问题；
- 为什么消费者落后时必须丢旧帧；
- 两级模型怎样从整帧得到手框，再从手框得到 21 点；
- RKNN Runtime、OpenCV 动态库怎样在程序启动时被加载；
- `precheck_board.sh`、`run_stability.sh` 的变量、后台进程、`trap`、日志重定向和资源采样怎样工作。

本篇完成时的可观察结果：RK3568 产生逐帧 JSONL、运行日志、标注图和资源 CSV；你能从这些证据判断摄像头、NPU、实时性和故障失效是否正常。

### 课程 04：让模型观测变成可靠手势事件

文件：`04_从关键点得到可靠手势.md`

开始时每一帧只有手框、关键点和置信度。本篇会先建立二维点、距离、角度和置信度的含义，再按函数依赖顺序讲清：

- 怎样估计一根手指是伸直还是弯曲；
- 怎样组合成四个手势得分；
- 为什么第一名还必须领先第二名；
- 为什么 5 帧和 150 ms 两个条件都要满足；
- 五个状态怎样阻止单帧误触发和旧动作残留；
- 评估脚本怎样把标签 CSV 与 JSONL 对齐。

本篇完成时的可观察结果：屏幕和 JSONL 中能看到 `CANDIDATE`、`ACTIVE`、`RELEASED` 的真实转换，并能统计混淆、进入延迟和误触发。

### 课程 05：把手势变成有边界的串口候选帧

文件：`05_把手势封装成安全的虚拟RC串口帧.md`

开始时只有经过确认的手势。本篇会先定义虚拟 RC 通道和安全目标，再讲：

- 一次性 1 秒命令为什么比“手一直摆着就一直动作”安全；
- 限幅和变化率限制怎样逐帧产生通道值；
- 44 字节帧为什么需要魔数、版本、长度、序号、心跳、时间戳和 CRC；
- 小端整数怎样放进字节数组；
- POSIX 串口 `open`、`termios`、`write`、`poll`、`tcdrain` 各自解决什么；
- S7.6 构建脚本为什么改用兼容板端 glibc 的 GCC 10。

本篇完成时的可观察结果：纯逻辑测试、文件回环和真实 UART 观测都能证明帧的内容、周期、CRC 和失效行为。

### 课程 06：飞控怎样接收并决定是否采用 Linux

文件：`06_飞控怎样接收并仲裁Linux候选值.md`

开始时 RK3568 已能发送候选帧。本篇从 USART6 收到第一个字节开始，依次讲：

- 中断回调为什么只接收字节，不直接控制飞行；
- `linux_rc_monitor` 怎样重新找帧头并逐项拒绝非法帧；
- 候选快照为什么不等于有效 RC；
- `RcTask` 怎样同时保存物理 CRSF 和 Linux 候选；
- 仲裁器进入虚拟源需要哪些条件；
- AUX3 撤销、物理摇杆接管、超时、重启和 Failsafe 为什么立即退出；
- 为什么物理油门和全部 AUX 永远不交给 Linux。

本篇完成时的可观察结果：UART4 日志可以说明字节是否收到、帧是否有效、候选是否新鲜、飞控选择了哪个 RC 来源以及为何退出。

### 课程 07：用拆桨证据闭合整条链

文件：`07_拆桨端到端验收与故障定位.md`

开始时两端功能各自成立。本篇把同一个摄像头源序号贯穿：

```text
Linux sequence
  = virtual_rc_source_sequence
  = UART 帧 source_sequence
  = 飞控 rc_seq
```

本篇会解释怎样采集两端日志、怎样运行两个验证脚本、怎样逐层注入故障，以及每一种失败应先查哪一层。

本篇完成时的可观察结果：拆桨条件下，摄像头到最终控制链的每一层都有对应日志；正常动作、撤销、接管、断线、重启和非法帧都有唯一可解释结果。

## 怎样区分事实、约定和仍需验证的内容

教程会使用四种证据标签，避免把旧验收结果说成永远成立：

| 标签 | 含义 | 例子 |
|---|---|---|
| **当前源码事实** | 直接从当前 Git HEAD 源码读取 | 帧长度是 44 字节；USART6 是 115200 8N1 |
| **历史实物证据** | 曾在记录的板卡和版本上实际测过 | S7.4 约 20 fps、5 分钟资源观测通过 |
| **文档约定** | 设计要求或验收合同 | Linux 不拥有 ARM/Throttle/AUX |
| **本次待验证** | 换环境后必须重新执行 | 当前板端 IP、UART 设备名、接线和模型 SHA-256 |

例如，项目历史记录里 RK3568 直连 IP 曾是 `169.254.151.86`。这只能证明当时的网络状态，不能证明你下一次开机仍然是这个地址。课程会教你怎样查当前值，而不是让你死记旧值。

## 硬件安全边界先冻结

> **当前位置：`课程路线已经明确 → [冻结不允许跨越的安全边界] → 开始 Linux 基础`**
>
> 本节只规定整个课程的安全条件。后文任何命令都不能绕过这些条件。

- S7.1～S7.8 的记录不等于允许装螺旋桨。
- 本课程的最终实践停在拆桨端到端验收；S7.9 受控飞行不在范围内。
- 接线前必须确认两端逻辑电平、TX/RX 方向、共地、引脚功能和供电极性。
- 3.3 V TTL UART 不能直接连接 RS-232 电平。
- 不允许把 RK3568 TX 与 ELRS/CRSF 发送端并接到同一个 UART RX。
- 逻辑分析仪地线必须接系统地，不能夹到电源正极或未知信号脚。
- 不带电移动未知线缆，不用短接电源的方式制造故障。
- Linux 进程运行成功、串口收到帧、飞控选择虚拟源，三者都不等于允许电机带桨运行。

## 读完本篇，你现在应该能解释什么

你暂时不需要会任何 Linux 命令，但应该能够解释：

1. Windows 保存源码，WSL 负责构建，RK3568 负责运行和连接真实硬件。
2. 交叉编译是“在 x86-64 WSL 上生成 AArch64 程序”，不是“在板子上直接编译”。
3. 模型输出先经过手势状态机，再变成候选 RC；Linux 不直接碰电机链。
4. 飞控只有在物理遥控器 ARM、人工授权和全部安全条件满足时，才可能采用 Linux 的 RPY 候选。
5. 每篇课程必须留下可观察证据，不能以“命令没有报错”代替验收。
