# 先看懂整条 Linux 与飞控链路

这套教程只解决一个问题：**一个完全没有 Linux 基础的人，怎样看懂并复现本项目从摄像头识别手势，到飞控安全采用手势指令的整条链路。**

这里不讲模型是怎样训练出来的。我们把两个开源模型当成已经准备好的零件。真正要学习的是：这些零件怎样在 RK3568 上运行，识别结果怎样一步步变成飞控能够接收的数据，以及飞控为什么不能直接相信 Linux 发来的内容。

项目里的构建脚本、检查脚本和测试工具也不是这套课程的教学重点。它们是工程师为了减少重复操作而写的工具。你需要知道它们在什么时候被使用、产生什么结果，但不需要学习它们的内部语法。

## 先看最终结果

整条链路可以先用一句话概括：

> RK3568 从摄像头取得画面，模型从画面中找出手部关键点，程序根据关键点判断手势，再把手势转换成一个受限制的“虚拟遥控器候选值”；F722 收到候选值后，还要结合物理遥控器、解锁状态和安全条件，决定是否采用。

展开以后是这样：

```text
IMX335 摄像头
  ↓ 图像
RK3568 Linux / V4L2
  ↓ 一帧图像
RKNN 两级推理
  ↓ 21 个手部关键点
几何手势判断
  ↓ 单帧手势结果
时序状态机
  ↓ 已经稳定确认的手势
虚拟 RC 映射
  ↓ 受限制的 Roll / Pitch / Yaw 候选值
44 字节串口帧
  ↓ 3.3 V UART
F722 USART6
  ↓ 通过完整检查的候选快照
物理 / 虚拟 RC 仲裁
  ↓ 唯一有效的 RC 通道
Setpoint → PID → Mixer → DShot
```

现在不用急着记住图里的缩写。后面每一章只讲其中一段，而且新名词都会在真正需要它时解释。

## 为什么链路要分这么多层

最直觉的做法似乎是：模型识别出“向前”，Linux 就直接告诉飞控向前飞。

这个做法在真实无人机上不安全，原因有三个。

第一，模型的一帧结果可能出错。手刚进入画面、光线突然变化或者关键点抖动，都可能让一帧看起来像另一种手势。所以不能看到一帧就立刻动作。

第二，Linux 不是实时飞控。摄像头可能断开，NPU 推理可能卡住，进程可能退出，系统也可能重启。飞控不能在这些情况下继续保持最后一个动作。

第三，操作者必须始终拥有最终控制权。Linux 不应该能够解锁飞机，也不应该能够控制油门和功能开关。只要物理遥控器要求接管，飞控就必须立即回到物理遥控器。

因此，这些层并不是为了把系统写复杂，而是在分别回答不同问题：

| 层 | 它负责回答的问题 |
|---|---|
| 摄像头采集 | 当前真的拿到了一帧新图像吗？ |
| 模型推理 | 图像里有没有手，21 个关键点在哪里？ |
| 几何判断 | 这一帧更像哪一种手势？ |
| 时序状态机 | 这个手势是否连续稳定，足以触发一次动作？ |
| 虚拟 RC 映射 | 这个动作最多能产生多大的姿态变化？ |
| 串口帧 | 数据在传输中是否完整、是否还是新数据？ |
| 飞控接收 | 这帧格式、时间、序号和内容是否可信？ |
| RC 仲裁 | 在当前飞行状态下，是否允许采用 Linux 的三个姿态轴？ |

## 四台“机器”分别做什么

### Windows：保存项目原件

项目仓库保存在 Windows。你平时查看 Markdown、修改源码、管理 Git，都是在这里完成。

Windows 不是 RK3568 程序的运行环境。原因很直接：电脑通常是 x86-64 处理器，而 RK3568 是 ARM64 处理器。两种处理器听不懂同一套机器指令。

### WSL：在电脑上准备 ARM64 产物

WSL 是 Windows 里的 Linux 环境。本项目用它完成两件事：

- 把已有模型转换成 RK3568 使用的 RKNN 模型；
- 把 C++ 源码编译成 ARM64 可执行程序。

WSL 负责“制作”，但一般不负责接摄像头运行最终程序。

### RK3568：真正运行视觉程序

RK3568 连接 IMX335 摄像头，并带有 NPU。NPU 可以先理解为专门加速神经网络计算的硬件。

板端 Linux 负责：

- 从摄像头取图；
- 调用 RKNN 模型；
- 判断稳定手势；
- 生成受限制的虚拟 RC 候选值；
- 通过串口持续发送候选帧。

### F722：掌握最终飞行权限

F722 是飞控 MCU，也就是负责姿态控制、电机输出和安全状态的微控制器。

它接收 Linux 数据，但不会因为“收到了”就立刻使用。它还要检查物理遥控器、是否已经 ARM、安全抑制状态、AUX3 授权、摇杆是否居中以及候选是否新鲜。

最重要的权限边界是：

- Linux 只能提出 Roll、Pitch、Yaw 候选值；
- ARM 永远来自物理遥控器和飞控安全状态；
- Throttle 永远来自物理遥控器；
- 所有 AUX 通道永远来自物理遥控器；
- 物理 Roll、Pitch、Yaw 明显离开中心时，可以立即接管；
- Linux 断线、重启或数据异常时，飞控退出虚拟源，并要求重新授权。

## “候选值”是什么意思

候选值不是最终控制值。

可以把它理解成 Linux 向飞控提出的建议：

> “我现在识别到一个已经稳定的手势，建议 Pitch 使用 -300 的偏移。”

飞控收到后会回答：

- 数据格式不对：拒绝；
- 数据已经过期：拒绝；
- 物理遥控器无效：拒绝；
- 没有 ARM：拒绝；
- AUX3 没有完成低到高授权：拒绝；
- 物理摇杆正在接管：拒绝；
- 所有条件都满足：只采用 Roll、Pitch、Yaw，油门和 AUX 仍用物理遥控器。

这就是整套设计的中心思想：**Linux 负责感知和建议，飞控负责安全判断和执行。**

## 安全边界先说清楚

涉及 F722、电机或遥控器的操作一律先拆桨。

串口接线前要确认：

- 双方都是 3.3 V TTL 电平；
- RK3568 与 F722 共地；
- RK3568 TX 接 F722 PC7，也就是 USART6 RX；
- 不要把同一个输出同时接到两个会主动驱动的引脚；
- 不确认引脚和电压时，不要通电试错。

S7.8 的拆桨验收通过，不等于允许装桨飞行。装桨和受控飞行属于 S7.9，仍有独立的安全前置条件。
