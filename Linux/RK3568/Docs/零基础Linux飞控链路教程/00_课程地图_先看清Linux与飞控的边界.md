# 从零搭建 RK3568 Linux 到飞控链路：课程地图

> **当前学习位置：** `Windows` → **先认识整条链路和安全边界** → `WSL 与 RK3568` → `摄像头/手势/虚拟 RC` → `飞控仲裁与拆桨验收`
>
> 本篇只解决“这套系统由谁负责什么、学习终点是什么”。读完后，你会知道后面的 Linux 命令究竟服务于哪一段功能；本篇不让你编译、接线或转动电机。

## 这套课程要带你完成什么

你不需要学习模型怎样训练，也不需要成为 Linux 管理员。本项目把已经选定的开源手部模型部署到 RK3568 上，最终实现的是下面这条**受安全限制**的链路：

```text
IMX335 摄像头画面
    -> RK3568 Linux 采集画面
    -> RKNN NPU 推理：手框和 21 个手部关键点
    -> 手势状态机：确认“张掌/单指/V 字/握拳”是否真的成立
    -> 有边界的虚拟 RC 候选帧
    -> 串口发送到 STM32F722
    -> 飞控验证、人工授权、物理遥控器仲裁
    -> 既有 RC / setpoint / PID / Mixer / ARM / Failsafe / DShot 链
```

这里的“虚拟 RC”可以先理解为：Linux 像遥控器一样提出一个有限的姿态通道建议，例如“让 Pitch 短暂向前偏一点”。它不是电机命令，更不是解锁命令。

本项目现在已经做出的效果是：在 RK3568 的屏幕上实时显示摄像头画面、手框和 21 个关键点；经过连续帧确认后，四种手势可生成有限的、一次性持续 1 秒的 Roll/Pitch 候选动作；飞控只有在物理遥控器已解锁、人工授权且 Linux 链路健康时才会采用这些候选值。物理遥控器的油门和全部 AUX 开关始终保留控制权。

## 先建立最重要的边界

Linux 板性能强，能运行摄像头和神经网络；飞控实时、且直接连接电机。这两个角色不能混在一起。

| 角色 | 在本项目中负责什么 | 明确不负责什么 |
|---|---|---|
| RK3568 Linux | 摄像头、模型推理、关键点、手势、虚拟 RC 候选帧 | ARM、AUX、PID、Mixer、DShot、电机值 |
| STM32F722 飞控 | 接收并验证候选帧、选择 RC 来源、Failsafe、控制与电机门禁 | 图像处理、模型训练、相信一帧手势就动作 |
| 物理遥控器 | ARM、飞行模式、视觉授权、随时接管、实时油门 | 不负责运行 Linux 或模型 |

所以，下面这种“捷径”在本项目中是错误的：

```text
摄像头 -> 识别到手势 -> Linux 直接写 DShot 电机值
```

它绕过了飞控已有的 ARM、Failsafe 和人工接管。正确链路是前面的长链路：Linux 只交付候选 RC，最后是否采用由飞控决定。

> **安全边界**
>
> S7.1～S7.8 已有项目记录和开发者确认的验收结论，但这不等于允许装螺旋桨或飞行。S7.9 受控飞行尚未开始。学习、复现和端到端检查一律先保持拆桨；能断开电机动力时优先断开。

## 你会在哪三个地方工作

后面每个命令都会标明运行地点。不要把 Linux 命令直接粘到 Windows PowerShell，也不要把 Windows 路径直接粘到 RK3568。

| 地点 | 它是什么 | 本项目用它做什么 | 典型提示符 |
|---|---|---|---|
| Windows PowerShell | 你的 Windows 命令窗口 | 看仓库、启动 WSL、复制文件 | `PS E:\...>` |
| WSL | 运行在 Windows 内的 Ubuntu/Linux 环境 | 保存 SDK、转换模型、交叉编译 ARM64 程序 | `user@pc:~$` |
| RK3568 板端 | 开发板自身的 Buildroot Linux | 接摄像头、运行 ARM64 程序、把候选帧送往飞控 | `root@ATK-DLRK3568:~#` |

**交叉编译**是本项目最早需要理解的 Linux 概念：程序在 WSL 里生成，但目标 CPU 是 RK3568 的 ARM64，而不是你的 Windows PC 常见的 x86-64。WSL 负责“造出给板子吃的程序”，RK3568 负责“真正运行它”。

## 本课程的阅读和实践顺序

不要跳到串口或飞控章节再回头补 Linux。后一个阶段使用前一个阶段的输出。

1. [01_先会操作三台Linux相关机器](01_先会操作三台Linux相关机器.md)：从零认识终端、路径、WSL 和 RK3568 登录方式。
2. [02_把已有模型和程序部署到RK3568](02_把已有模型和程序部署到RK3568.md)：理解 Git 原件、外部模型、交叉编译与复制部署。
3. [03_摄像头到手部关键点](03_摄像头到手部关键点.md)：用 V4L2 取图，再用 RKNN 在 NPU 上得到手部观测。
4. [04_从关键点得到可靠手势](04_从关键点得到可靠手势.md)：理解为什么不能让一帧识别直接触发飞行指令。
5. [05_把手势封装成安全的虚拟RC串口帧](05_把手势封装成安全的虚拟RC串口帧.md)：认识 44 字节协议、限幅、限速和串口部署。
6. [06_飞控怎样接收并仲裁Linux候选值](06_飞控怎样接收并仲裁Linux候选值.md)：看 STM32 怎样验证帧、要求授权并保留物理遥控器。
7. [07_拆桨端到端验收与故障定位](07_拆桨端到端验收与故障定位.md)：把两端日志按同一源序号对齐，逐级证明链路。

## 本课程依据的真实项目状态

这不是一套脱离工程的 Linux 示例。下表列出每篇课程会引用的现有阶段和证据边界。

| 阶段 | 已完成的真实结果 | 课程中的作用 |
|---|---|---|
| S7.1 | RK3568 Buildroot、IMX335 `/dev/video0`、RKNN Runtime 和官方 NPU 冒烟已实测 | 证明板子、摄像头和 NPU 的起点可用 |
| S7.2 | PC 参考链固定了两级手模型的输入输出合同 | 说明模型文件是部署输入，不讨论训练过程 |
| S7.3 | FP16 与 INT8 均实测；FP16 合格，INT8 因误差超限被拒绝 | 说明“能跑更快”不等于“结果能交付” |
| S7.4 | V4L2 实时采集、NPU 推理、5 分钟资源观测和屏显已验收 | 给出 Linux 实时链的实际运行入口 |
| S7.5 | 四类手势和五态安全状态机已验收 | 让单帧模型结果变成可控制的事件 |
| S7.6 | 候选 RC 映射、44 字节帧和串口发送已验收 | 把 Linux 输出限制在可验证的数据契约中 |
| S7.7～S7.8 | 飞控仲裁、人工接管、拆桨端到端验收已确认 | 把 Linux 链放在飞控安全链内部，而不是旁路 |

这些事实来自项目源码和验收文档；“已验收”只表示记录的范围内已完成，并不替代你重新接线、升级环境或改动版本后的实物复测。

## 读完本篇后的自检

请先用自己的话确认下面三句话：

- RK3568 的输出是“受限候选 RC”，不是“电机命令”。
- WSL 是编译地点，RK3568 是运行地点；二者不是同一台 Linux。
- 即使 Linux 运行正常，飞控也只有在物理遥控器 ARM 和授权都满足时才可能使用它。

确认后，继续阅读 [01_先会操作三台Linux相关机器](01_先会操作三台Linux相关机器.md)。
