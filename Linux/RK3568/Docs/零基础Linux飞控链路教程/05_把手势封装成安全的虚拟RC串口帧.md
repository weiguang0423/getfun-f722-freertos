# 把可靠手势封装成安全的虚拟 RC 串口帧

> **文档进度：`关键点 → 可靠手势 → [本篇：有界通道、固定帧、串口发送] → 飞控接收仲裁`**
>
> **真实数据流位置：`GestureSnapshot → Mapper → VirtualRcFrame → 44字节 → RK3568 UART TX`**
>
> 本篇只让 Linux 发送“候选姿态值”。Linux 不能解锁，不能决定油门，不能占有 AUX，也不能直接调用飞控 PID、Mixer 或 DShot。

## 为什么可靠手势仍不能直接发送给飞控

上一篇最后得到 `GestureSnapshot`。其中只有 `state=ACTIVE` 才表示手势已经跨多帧确认。但飞控接收的是连续字节，不知道：

- 这条手势是哪一帧摄像头产生的；
- 发送时是否已经过期；
- 中间有没有字节损坏或错位；
- 同一动作应该持续多久；
- 通信健康但当前没有动作，和通信已经断开，有什么区别；
- Linux 是否偷偷提出了油门或解锁要求。

因此还缺三层：

```text
ACTIVE手势
  ↓ Mapper：决定小幅目标、限速、1秒脉冲、健康中立/失效释放
VirtualRcFrame：带序号、心跳、时间戳和通道
  ↓ encode：固定成44字节并计算CRC
字节数组
  ↓ SerialLink：115200 8N1，完整写出
RK3568 TX引脚
```

本篇使用这些现有文件：

| 文件 | 作用 |
|---|---|
| `s7_6_virtual_rc.hpp/.cpp` | 定义通道、候选帧、映射、编码、解码和纯逻辑自检 |
| `s7_6_serial.hpp/.cpp` | 打开串口、配置 115200 8N1、完整写出一帧 |
| `s7_6_virtual_rc_test.cpp` | 不碰设备的映射和协议测试 |
| `s7_6_serial_test.cpp` | 用临时文件验证真实写出路径和两帧解码 |
| `build_board.sh` | 生成能在当前 Buildroot/glibc 上运行的 AArch64 程序 |

仓库记录 S7.6 在 2026-08-22 被确认验收通过。本轮重写没有重新给 UART 接线、没有重新抓逻辑分析仪波形，也没有重新连接飞控，因此下面的硬件结果仍要在你当前实物上重验。

## 先冻结安全合同：Linux 有什么权、没有什么权

> **当前位置：`可靠手势已经得到 → [规定Linux候选值边界] → 定义Channels`**
>
> 本节还不写字节，也不打开串口。

Linux 只被允许影响 Roll、Pitch、Yaw 三个姿态候选，而且幅度限制在 `-300～+300`。这个整数尺度中，1000 才代表归一化 1.0；所以 300 代表 0.30。

Throttle 和 AUX 在 Linux 帧里永远为 0。这里的 0 不是“电机最低油门的某个微秒值”，而是“Linux 对这两个通道没有所有权”。飞控后面始终从物理 CRSF 遥控器取油门和 AUX。

首版事件映射：

| ACTIVE 边沿 | Roll | Pitch | Yaw | Throttle | AUX | 含义 |
|---|---:|---:|---:|---:|---:|---|
| OPEN_PALM | 0 | -300 | 0 | 0 | 0 | 一次向前/低头候选脉冲 |
| POINT | 0 | +300 | 0 | 0 | 0 | 一次向后/抬头候选脉冲 |
| V_SIGN | -300 | 0 | 0 | 0 | 0 | 一次向左候选脉冲 |
| FIST | 0 | 0 | 0 | 0 | 0 | 明确无效释放 |

这些只是有界姿态脉冲，没有位置或速度反馈，因此不能承诺无人机会精确移动多少厘米。

## `Channels` 和 `VirtualRcFrame` 分别保存什么

> **当前位置：`安全合同已明确 → [定义内存中的候选帧] → 设计Mapper`**

### 五个通道先完整定义

```cpp
struct Channels {
    int16_t roll{};
    int16_t pitch{};
    int16_t yaw{};
    int16_t throttle{};
    int16_t aux{};
};
```

- `int16_t` 是 16 位有符号整数，范围 -32768～32767；协议实际范围更窄。
- `{}` 让默认值为 0，所以 `Channels{}` 天然是全中立。
- 一个 `Channels` 只保存某一时刻的五个数，不包含新旧、是否可信等信息。

### 候选帧再加上“为什么可信”的证据

```cpp
struct VirtualRcFrame {
    bool valid{};
    s7_5::GestureId gesture_id{s7_5::GestureId::UNKNOWN};
    uint8_t confidence_percent{};
    uint32_t source_sequence{};
    uint32_t heartbeat{};
    uint64_t source_timestamp_us{};
    uint64_t send_timestamp_us{};
    Channels channels{};
};
```

字段逐个解释：

- `valid`：本候选是否健康。`true + 全零` 是“通信健康、当前中立”；`false + 全零` 是“立即释放候选”。
- `gesture_id`：产生当前脉冲的手势；中立时 UNKNOWN。
- `confidence_percent`：0～100 的整数置信度，便于协议检查。
- `source_sequence`：摄像头源帧序号。最新帧策略允许跳号，但有效帧必须向前。
- `heartbeat`：每发送一帧加 1，接收端用它发现重复或倒退。
- `source_timestamp_us`：源画面时间。
- `send_timestamp_us`：Linux 准备发送候选帧的时间。
- `channels`：五个候选通道。

`source_sequence` 回答“来自哪帧”，`heartbeat` 回答“这是第几次发送”。同一源结果理论上也可能对应多次发送，所以二者不能合并。

## Mapper 为什么要限速、锁存边沿和自动回中

> **当前位置：`内存帧已定义 → [手势事件变成随时间变化的候选值] → 固定字节布局`**

### `approach()` 先定义每次最多走多远

目标从 0 跳到 -300 会形成阶跃。项目把姿态轴最大变化率限制为每秒 600。输入是当前值、目标值、每秒最大变化量和本次经过的微秒数；输出是向目标靠近一步后的值；它不保存状态。

```cpp
int16_t approach(int16_t current, int16_t target,
                 int32_t rate_per_second, uint64_t elapsed_us) {
    if (current == target) return current;
    const int64_t scaled = static_cast<int64_t>(rate_per_second) * elapsed_us;
    const int32_t step = static_cast<int32_t>(
        std::max<int64_t>(1, scaled / 1000000));
    if (target > current)
        return static_cast<int16_t>(std::min<int32_t>(target, current + step));
    return static_cast<int16_t>(std::max<int32_t>(target, current - step));
}
```

- `elapsed_us/1000000` 把微秒换成秒。
- 先转 `int64_t` 是为了让乘法不容易溢出。
- `max(1,...)` 保证时间很短时也至少移动 1 个整数单位。
- `min/max` 防止跨过目标。

具体走读：当前 Pitch=0，目标=-300，速率 600/s，经过 50000 us=0.05 s，最大步长 `600×0.05=30`，输出 -30。下一次相同间隔输出 -60；到 -300 后不再越过。

### Mapper 调用前先定义目标表和全零判断

`target_for()` 输入一个已定义手势 ID，输出该手势的五通道目标；FIST 和 UNKNOWN 都返回默认全零。`channels_are_zero()` 只判断五个通道是否全部回中，不修改状态。

```cpp
Channels target_for(s7_5::GestureId id) {
    switch (id) {
    case s7_5::GestureId::OPEN_PALM:
        return {0, -300, 0, 0, 0};
    case s7_5::GestureId::POINT:
        return {0, 300, 0, 0, 0};
    case s7_5::GestureId::V_SIGN:
        return {-300, 0, 0, 0, 0};
    default:
        return {};
    }
}

bool channels_are_zero(const Channels& value) {
    return value.roll == 0 && value.pitch == 0 && value.yaw == 0 &&
           value.throttle == 0 && value.aux == 0;
}
```

具体输入 `V_SIGN` 返回 Roll=-300、其余为0；输入 FIST 进入 `default`，返回全零。现在这两个内部函数已完整定义，`Mapper::update()` 才能调用它们。

### 手势只在 ACTIVE 边沿触发一次 1 秒脉冲

`Mapper` 要长期保存：当前通道、上一次触发手势、上次置信度、是否已经锁存当前 ACTIVE、心跳、脉冲截止时间和上次发送时间。

```cpp
class Mapper {
public:
    VirtualRcFrame update(const s7_5::GestureSnapshot& gesture,
                          uint32_t source_sequence,
                          uint64_t source_timestamp_us,
                          uint64_t send_timestamp_us);

private:
    Channels current_{};
    s7_5::GestureId command_gesture_{s7_5::GestureId::UNKNOWN};
    uint8_t last_confidence_percent_{};
    bool active_latched_{};
    uint32_t heartbeat_{};
    uint64_t pulse_until_us_{};
    uint64_t last_send_us_{};
};
```

`active_latched_` 解决“手一直保持张掌会不会每帧重新开始 1 秒”的问题：同一个 ACTIVE 持续出现时，只第一次设置截止时间；必须先离开 ACTIVE，之后再次进入才是新边沿。

### 健康中立和无效释放必须分开

这是本篇最容易误解的地方：

- 摄像头/推理健康，只是当前 `NO_HAND/UNKNOWN/CANDIDATE/RELEASED`：继续发送 `valid=true`。若之前 1 秒脉冲尚未结束，它按原计划完成；结束后缓慢回中并成为 UNKNOWN 全零。
- FIST、源时间为 0、源超过 250 ms、发送时间倒退、采集/推理/延迟门禁失败：立即清零并 `valid=false`。

健康空档不等于断线；真正故障也不能伪装成健康中立。

### `Mapper::update()` 的决策骨架和完整定义

```text
心跳加1，填写序号和时间
  ↓
检查源时间新鲜且发送时间不倒退
  ├─ 失败或FIST → current清零，valid=false，立即返回
  ↓
检测新的ACTIVE边沿
  └─ 新边沿 → current清零，记录手势，pulse_until=发送时间+1秒
  ↓
valid=true
  ↓
脉冲未结束？目标=手势目标：目标=全零
  ↓
用approach按实际时间间隔更新五通道
  ↓
非零时保留触发手势；全零时改UNKNOWN/0置信度
```

项目完整实现如下；依赖的 `approach()` 和目标合同已经先定义：

```cpp
VirtualRcFrame Mapper::update(const s7_5::GestureSnapshot& gesture,
                              uint32_t source_sequence,
                              uint64_t source_timestamp_us,
                              uint64_t send_timestamp_us) {
    VirtualRcFrame frame;
    frame.confidence_percent = std::isfinite(gesture.observed_confidence)
        ? static_cast<uint8_t>(std::clamp(
              std::lround(gesture.observed_confidence * 100.0f), 0l, 100l))
        : 0;
    frame.source_sequence = source_sequence;
    frame.heartbeat = ++heartbeat_;
    frame.source_timestamp_us = source_timestamp_us;
    frame.send_timestamp_us = send_timestamp_us;

    const bool fresh = source_timestamp_us &&
        send_timestamp_us >= source_timestamp_us &&
        send_timestamp_us - source_timestamp_us <= 250000;
    const bool ordered = !last_send_us_ || send_timestamp_us >= last_send_us_;
    const bool active = gesture.state == s7_5::GestureState::ACTIVE &&
        gesture.active_id != s7_5::GestureId::UNKNOWN &&
        gesture.observed_id == gesture.active_id &&
        std::isfinite(gesture.observed_confidence) &&
        gesture.observed_confidence >= .75f;
    const bool release = active && gesture.active_id == s7_5::GestureId::FIST;

    if (!fresh || !ordered || release) {
        current_ = {};
        command_gesture_ = s7_5::GestureId::UNKNOWN;
        last_confidence_percent_ = 0;
        active_latched_ = false;
        pulse_until_us_ = 0;
        frame.confidence_percent = 0;
        frame.channels = current_;
        last_send_us_ = send_timestamp_us;
        return frame;
    }

    if (active) {
        last_confidence_percent_ = frame.confidence_percent;
        if (!active_latched_ || command_gesture_ != gesture.active_id) {
            current_ = {};
            command_gesture_ = gesture.active_id;
            pulse_until_us_ = send_timestamp_us + 1000000;
        }
        active_latched_ = true;
    } else {
        active_latched_ = false;
    }

    frame.valid = true;
    const Channels target = send_timestamp_us < pulse_until_us_
        ? target_for(command_gesture_) : Channels{};
    const uint64_t elapsed = last_send_us_ && send_timestamp_us >= last_send_us_
        ? std::min<uint64_t>(send_timestamp_us - last_send_us_, 250000)
        : 50000;
    current_.roll = approach(current_.roll, target.roll, 600, elapsed);
    current_.pitch = approach(current_.pitch, target.pitch, 600, elapsed);
    current_.yaw = approach(current_.yaw, target.yaw, 600, elapsed);
    current_.throttle = approach(current_.throttle, target.throttle, 400, elapsed);
    current_.aux = approach(current_.aux, target.aux, 1000, elapsed);

    if (!channels_are_zero(current_)) {
        frame.gesture_id = command_gesture_;
        frame.confidence_percent = last_confidence_percent_;
    } else {
        frame.gesture_id = s7_5::GestureId::UNKNOWN;
        frame.confidence_percent = 0;
    }
    frame.channels = current_;
    last_send_us_ = send_timestamp_us;
    return frame;
}
```

具体时间线：在 1.00 s 首次 ACTIVE 张掌，首帧 Pitch 从 0 到 -30；每 50 ms 再减 30，0.5 s 后到 -300；目标保持期在 2.00 s 结束，随后每帧加 30 回到 0。持续张掌不会把截止时间向后续期。过程中健康的短暂 RELEASED 不会截断已经触发的脉冲；FIST 或源时间异常会当帧全零无效。

## 44 字节为什么这样排列

> **当前位置：`内存中的VirtualRcFrame已得到 → [变成固定线上的字节] → CRC`**

串口只传字节，不认识 C++ 结构体。不能直接把结构体内存原样发送，因为编译器可能插入填充，CPU 的整数存储顺序也需要明确。协议固定为：

| 偏移 | 长度 | 字段 | 例子/规则 |
|---:|---:|---|---|
| 0 | 1 | magic0 | ASCII `G` = `0x47` |
| 1 | 1 | magic1 | ASCII `R` = `0x52` |
| 2 | 1 | version | 1 |
| 3 | 1 | length | 44 |
| 4 | 1 | valid | 0 或 1 |
| 5 | 1 | gesture_id | 0～4 |
| 6 | 1 | confidence_percent | 0～100 |
| 7 | 1 | reserved | 必须为 0 |
| 8 | 4 | source_sequence | 小端 uint32 |
| 12 | 4 | heartbeat | 小端 uint32 |
| 16 | 8 | source_timestamp_us | 小端 uint64 |
| 24 | 8 | send_timestamp_us | 小端 uint64 |
| 32 | 2 | roll | 小端 int16 |
| 34 | 2 | pitch | 小端 int16 |
| 36 | 2 | yaw | 小端 int16 |
| 38 | 2 | throttle | 小端 int16 |
| 40 | 2 | aux | 小端 int16 |
| 42 | 2 | CRC16 | 对 0～41 字节计算，小端保存 |

魔数 `GR` 让接收端在连续流里重新找帧头；版本和长度阻止不同协议误解同一字节；保留字节必须为 0，未来扩展前旧接收端会拒绝未知格式。

## 小端整数怎样放进字节数组

> **当前位置：`字段布局已冻结 → [定义整数编码辅助函数] → 计算CRC`**

小端 little-endian 表示最低有效字节放在低地址。数字 `0x12345678` 写成四字节是：

```text
偏移+0: 0x78
偏移+1: 0x56
偏移+2: 0x34
偏移+3: 0x12
```

完整辅助函数：

```cpp
void put_u16(uint8_t* out, uint16_t value) {
    out[0] = static_cast<uint8_t>(value);
    out[1] = static_cast<uint8_t>(value >> 8);
}

void put_u32(uint8_t* out, uint32_t value) {
    for (int i = 0; i < 4; ++i)
        out[i] = static_cast<uint8_t>(value >> (8 * i));
}

void put_u64(uint8_t* out, uint64_t value) {
    for (int i = 0; i < 8; ++i)
        out[i] = static_cast<uint8_t>(value >> (8 * i));
}

uint16_t get_u16(const uint8_t* in) {
    return static_cast<uint16_t>(in[0]) |
           static_cast<uint16_t>(in[1]) << 8;
}

uint32_t get_u32(const uint8_t* in) {
    uint32_t value{};
    for (int i = 0; i < 4; ++i)
        value |= static_cast<uint32_t>(in[i]) << (8 * i);
    return value;
}

uint64_t get_u64(const uint8_t* in) {
    uint64_t value{};
    for (int i = 0; i < 8; ++i)
        value |= static_cast<uint64_t>(in[i]) << (8 * i);
    return value;
}
```

`>>` 右移把高位移到最低 8 位；转为 `uint8_t` 只留下一个字节。`|` 是按位或，把各字节放回整数对应位置。负的 `int16_t` 通道先转成同宽 `uint16_t`，保留二进制补码位型；接收时再转回 `int16_t`。

例：Pitch=-30 的 16 位补码是 `0xFFE2`，线上小端两个字节为 `E2 FF`。

## CRC16 怎样发现字节损坏

> **当前位置：`42字节主体可编码 → [定义CRC16] → 完整encode`**

CRC 是 cyclic redundancy check，循环冗余校验。它不是加密，也不能阻止恶意伪造；它用固定多项式让常见传输位错误很容易被发现。

本项目使用 CRC16-CCITT-FALSE：初值 `0xFFFF`，多项式 `0x1021`，逐字节从高位处理。完整定义：

```cpp
uint16_t crc16(const uint8_t* bytes, std::size_t size) {
    uint16_t crc = 0xffffu;
    for (std::size_t i = 0; i < size; ++i) {
        crc ^= static_cast<uint16_t>(bytes[i]) << 8;
        for (int bit = 0; bit < 8; ++bit) {
            crc = static_cast<uint16_t>(
                (crc & 0x8000u) ? (crc << 1) ^ 0x1021u : crc << 1);
        }
    }
    return crc;
}
```

- `^` 是按位异或：相同位得 0，不同位得 1。
- `& 0x8000` 检查 16 位 CRC 的最高位。
- 每个输入字节都要进行 8 次位迭代。
- 转回 `uint16_t` 自动只保留低 16 位。

可复算的小例子：初值 `FFFF` 处理第一个字节 `G=47` 后得到 `D9D3`；继续处理 `R=52` 后得到 `F3E3`。真实帧还会继续处理版本到 AUX 共 42 字节，最后把结果以小端写在偏移 42～43。若线路把任意主体字节翻转，接收端重算结果通常不再等于帧尾。

## `encode()` 完整定义后才第一次编码

> **当前位置：`所有字段和辅助函数已定义 → [构造44字节] → decode拒绝错误`**

输入是 `VirtualRcFrame`，输出固定长度 `std::array<uint8_t,44>`，不修改 Mapper 状态。完整实现：

```cpp
std::array<uint8_t, 44> encode(const VirtualRcFrame& frame) {
    std::array<uint8_t, 44> out{};
    out[0] = 'G';
    out[1] = 'R';
    out[2] = 1;
    out[3] = 44;
    out[4] = frame.valid ? 1u : 0u;
    out[5] = static_cast<uint8_t>(frame.gesture_id);
    out[6] = frame.confidence_percent;
    put_u32(out.data() + 8, frame.source_sequence);
    put_u32(out.data() + 12, frame.heartbeat);
    put_u64(out.data() + 16, frame.source_timestamp_us);
    put_u64(out.data() + 24, frame.send_timestamp_us);
    put_u16(out.data() + 32, static_cast<uint16_t>(frame.channels.roll));
    put_u16(out.data() + 34, static_cast<uint16_t>(frame.channels.pitch));
    put_u16(out.data() + 36, static_cast<uint16_t>(frame.channels.yaw));
    put_u16(out.data() + 38, static_cast<uint16_t>(frame.channels.throttle));
    put_u16(out.data() + 40, static_cast<uint16_t>(frame.channels.aux));
    put_u16(out.data() + 42, crc16(out.data(), 42));
    return out;
}
```

数组初始化为全零，所以保留字节 7 自然为 0。具体输入：有效 UNKNOWN 中立、序号 1、心跳 1、全通道 0，编码后前四字节固定 `47 52 01 2C`，其中 `2C` 是十进制 44；偏移 4 是 01；偏移 5、6、7 是 00；最后两字节由前 42 字节共同决定。

现在才第一次概念调用：

```cpp
const auto bytes = encode(frame);
```

## `decode()` 为什么按层拒绝，而不是先信字段

> **当前位置：`发送端能编码 → [接收参考先验结构再验语义] → 串口写出`**

`decode()` 输入字节指针、大小、接收时刻、上一有效源序号和上一心跳；只有全部检查通过才覆盖输出 `frame`。失败返回 `false`，原输出对象不应被当作新候选。

拒绝顺序：

```text
空指针/长度/魔数/版本/valid位/ID/置信度/保留位/CRC
  ↓
解出整数和通道
  ↓
通道范围/心跳前进/发送时间不在未来/链路年龄<=150ms
  ↓ 若valid=true
源序号前进/源时间非0/时间顺序/源年龄<=250ms/手势与通道匹配
  ↓ 若valid=false
五通道必须全零
  ↓
才把decoded赋给frame并返回true
```

为什么 CRC 在解字段之前？损坏的字节不能先被当成可信长度、时间或通道。为什么结构合法后还要语义检查？CRC 只能说明“发送和接收看见的位大概率相同”，不能说明发送内容符合项目安全合同。

`decode()` 将调用三个内部检查，所以先完整定义它们：

```cpp
bool newer(uint32_t value, uint32_t previous) {
    return value != previous &&
           static_cast<int32_t>(value - previous) > 0;
}

bool channels_in_range(const Channels& value) {
    return std::abs(static_cast<int>(value.roll)) <= 300 &&
           std::abs(static_cast<int>(value.pitch)) <= 300 &&
           std::abs(static_cast<int>(value.yaw)) <= 300 &&
           value.throttle >= 0 && value.throttle <= 250 &&
           value.aux >= 0 && value.aux <= 1000;
}

bool channels_match_gesture(const VirtualRcFrame& frame) {
    if (frame.channels.yaw != 0 || frame.channels.throttle != 0 ||
        frame.channels.aux != 0) return false;

    switch (frame.gesture_id) {
    case s7_5::GestureId::UNKNOWN:
        return frame.confidence_percent == 0 &&
               channels_are_zero(frame.channels);
    case s7_5::GestureId::OPEN_PALM:
        return frame.confidence_percent >= 75 &&
               frame.channels.roll == 0 &&
               frame.channels.pitch >= -300 && frame.channels.pitch <= 0;
    case s7_5::GestureId::POINT:
        return frame.confidence_percent >= 75 &&
               frame.channels.roll == 0 &&
               frame.channels.pitch >= 0 && frame.channels.pitch <= 300;
    case s7_5::GestureId::V_SIGN:
        return frame.confidence_percent >= 75 &&
               frame.channels.pitch == 0 &&
               frame.channels.roll >= -300 && frame.channels.roll <= 0;
    default:
        return false;
    }
}
```

`newer()` 先拒绝相同值，再用 32 位有符号差判断前进方向，允许无符号计数器正常回绕。`std::abs` 取绝对值。`channels_match_gesture()` 在范围检查之外，再验证哪个轴允许非零以及置信度。

现在 `get_u32/get_u64/newer/channels_in_range/channels_match_gesture` 都已定义，才能给出完整 `decode()`：

```cpp
bool decode(const uint8_t* bytes, std::size_t size,
            uint64_t receive_timestamp_us,
            uint32_t previous_source_sequence,
            uint32_t previous_heartbeat,
            VirtualRcFrame& frame) {
    if (!bytes || size != 44 || bytes[0] != 'G' || bytes[1] != 'R' ||
        bytes[2] != 1 || bytes[3] != 44 || (bytes[4] & ~1u) ||
        bytes[5] > 4 || bytes[6] > 100 || bytes[7] ||
        get_u16(bytes + 42) != crc16(bytes, 42))
        return false;

    VirtualRcFrame decoded;
    decoded.valid = bytes[4] != 0;
    decoded.gesture_id = static_cast<s7_5::GestureId>(bytes[5]);
    decoded.confidence_percent = bytes[6];
    decoded.source_sequence = get_u32(bytes + 8);
    decoded.heartbeat = get_u32(bytes + 12);
    decoded.source_timestamp_us = get_u64(bytes + 16);
    decoded.send_timestamp_us = get_u64(bytes + 24);
    decoded.channels = {
        static_cast<int16_t>(get_u16(bytes + 32)),
        static_cast<int16_t>(get_u16(bytes + 34)),
        static_cast<int16_t>(get_u16(bytes + 36)),
        static_cast<int16_t>(get_u16(bytes + 38)),
        static_cast<int16_t>(get_u16(bytes + 40)),
    };

    if (!channels_in_range(decoded.channels) ||
        !newer(decoded.heartbeat, previous_heartbeat) ||
        decoded.send_timestamp_us > receive_timestamp_us ||
        receive_timestamp_us - decoded.send_timestamp_us > 150000)
        return false;

    if (decoded.valid &&
        (!newer(decoded.source_sequence, previous_source_sequence) ||
         !decoded.source_timestamp_us ||
         decoded.send_timestamp_us < decoded.source_timestamp_us ||
         decoded.send_timestamp_us - decoded.source_timestamp_us > 250000 ||
         !channels_match_gesture(decoded)))
        return false;

    if (!decoded.valid &&
        (decoded.channels.roll || decoded.channels.pitch || decoded.channels.yaw ||
         decoded.channels.throttle || decoded.channels.aux))
        return false;

    frame = decoded;
    return true;
}
```

具体故障：编码后的 Pitch 字节 `E2 FF` 被翻成 `E3 FF`，但帧尾 CRC 没变，第一层就拒绝；攻击者若同时重算 CRC，却发送有效 UNKNOWN 和非零 Roll，结构层通过，语义层仍拒绝。

## Linux 串口仍然是设备文件

> **当前位置：`44字节已经可靠构造 → [打开并配置UART设备] → 完整写出`**

例如 `/dev/ttyS9` 是 UART 的设备文件。设备名必须来自 RK3568 原理图、设备树、丝印和板端枚举，不能靠教程猜测。

**termios** 是 POSIX 串口配置结构。115200 8N1 表示：每秒 115200 bit、8 个数据位、无校验、1 个停止位。

### 完整串口实现

现有逻辑源码通过 `git show HEAD:Linux/RK3568/s7_6/s7_6_serial.cpp` 可读；工作树文件受外部透明加密层包装，但 Git 逻辑内容与 HEAD 一致。本轮不修改该源文件。完整实现：

```cpp
#include "s7_6_serial.hpp"

#include <cerrno>
#include <cstring>
#include <fcntl.h>
#include <poll.h>
#include <stdexcept>
#include <string>
#include <termios.h>
#include <unistd.h>

namespace s7_6 {

SerialLink::SerialLink(const char* device) {
    if (!device || !*device)
        throw std::runtime_error("S7_6_RC_OUTPUT is empty");

    fd_ = open(device, O_WRONLY | O_NOCTTY | O_NONBLOCK);
    if (fd_ < 0)
        throw std::runtime_error(
            "open RC output failed: " + std::string(std::strerror(errno)));

    termios options{};
    if (tcgetattr(fd_, &options) == 0) {
        cfmakeraw(&options);
        cfsetispeed(&options, B115200);
        cfsetospeed(&options, B115200);
        options.c_cflag =
            (options.c_cflag & ~(CSIZE | CSTOPB | PARENB | CRTSCTS)) |
            CS8 | CLOCAL;
        if (tcsetattr(fd_, TCSANOW, &options) != 0) {
            close(fd_);
            fd_ = -1;
            throw std::runtime_error(
                "configure RC output failed: " +
                std::string(std::strerror(errno)));
        }
    } else if (errno != ENOTTY) {
        close(fd_);
        fd_ = -1;
        throw std::runtime_error(
            "inspect RC output failed: " +
            std::string(std::strerror(errno)));
    }
}

SerialLink::~SerialLink() {
    if (fd_ >= 0) close(fd_);
}

VirtualRcFrame SerialLink::send(const s7_5::GestureSnapshot& gesture,
                                uint32_t source_sequence,
                                uint64_t source_timestamp_us,
                                uint64_t send_timestamp_us) {
    const auto frame = mapper_.update(gesture, source_sequence,
                                      source_timestamp_us, send_timestamp_us);
    const auto bytes = encode(frame);
    std::size_t written{};

    while (written < bytes.size()) {
        const ssize_t count = write(fd_, bytes.data() + written,
                                    bytes.size() - written);
        if (count > 0) {
            written += static_cast<std::size_t>(count);
            continue;
        }
        if (count < 0 && errno == EINTR) continue;
        if (count < 0 && (errno == EAGAIN || errno == EWOULDBLOCK)) {
            pollfd output{fd_, POLLOUT, 0};
            if (poll(&output, 1, 50) > 0) continue;
        }
        throw std::runtime_error(
            "write RC frame failed: " + std::string(std::strerror(errno)));
    }

    if (tcdrain(fd_) != 0 && errno != ENOTTY)
        throw std::runtime_error(
            "drain RC frame failed: " + std::string(std::strerror(errno)));
    return frame;
}

}  // namespace s7_6
```

首次出现的串口符号：

- `O_WRONLY`：只写；本阶段 Linux 单向发给飞控。
- `O_NOCTTY`：不要把该串口变成进程的控制终端。
- `cfmakeraw`：关闭行编辑、回显、换行转换等终端文本行为，让字节原样传输。
- `B115200`：termios 中的 115200 波特率常量。
- `CS8`：8 数据位；清 `CSTOPB` 得 1 停止位；清 `PARENB` 得无校验；清 `CRTSCTS` 得无硬件流控。
- `CLOCAL`：忽略调制解调器载波控制线。
- `TCSANOW`：立即应用设置。
- `write()`：返回实际写入的字节数；一次调用可能小于 44，所以必须循环。
- `EINTR`：被信号打断，重试。
- `EAGAIN/EWOULDBLOCK`：暂时写不进去，用 `poll(POLLOUT)` 最多等 50 ms。
- `tcdrain()`：等待已经交给串口驱动的字节真正发送完成；普通文件返回 ENOTTY 时允许，用于文件回环测试。

具体走读：第一次 `write()` 只写 20 字节，`written=20`；第二次从 `bytes+20` 写剩余 24 字节。若把部分写误当成功，飞控会收到断帧。若 50 ms 内始终不可写，函数抛异常，实时进程终止；它不会自动重连后恢复旧动作。

## 构建脚本为什么特意选择 GCC 10

> **当前位置：`串口逻辑已完整 → [生成与板端glibc兼容的AArch64 ELF] → 软件自检`**

当前板端 Buildroot 用户空间使用 glibc 2.35。项目记录发现 SDK host 符号链接后来指向 GCC 13，生成的 ELF 可能要求 `GLIBC_2.36+`，板上启动会报找不到新版本符号。因此脚本默认使用 `aarch64-linux-gnu-g++-10`，并静态带入 libstdc++/libgcc；这不是“编译器越旧越好”，而是目标系统兼容性选择。

## 接线前的电气安全边界

> **当前位置：`AArch64程序已生成 → [确认物理UART] → 真实发送`**

全程先拆下所有螺旋桨。断电接线，通电前用万用表和原理图核对。不要用“接上试试”判断未知引脚。

1. RK3568 UART 必须是 **3.3 V TTL**。PC 的 RS-232 使用正负高电压，不能直接接 STM32 UART。
2. 两块板必须共地：RK3568 GND ↔ 飞控 GND。没有共同参考，逻辑高低电平无意义。
3. 单向发送：RK3568 **TX → F722 PC7 / USART6_RX**。TX 必须接 RX，不能 TX 对 TX。
4. 若做双向诊断，F722 PC6 / USART6_TX 才接 RK3568 RX；本协议主数据只要求 Linux→飞控。
5. 不能把 RK3568 TX 并到 UART2/CRSF 接收机的发送线上。两个推挽 TX 同时驱动相反电平会形成大电流和逻辑冲突。
6. 避免 5 V、VBAT、电源极性接错和裸线短路；逻辑分析仪地夹只能接系统 GND，不能夹信号脚。

项目历史记录使用 RK3568 JP11 的 `UART9_TX_M1` 到飞控 PC7，Linux 设备 `/dev/ttyS9`。换板、换设备树或改复用后必须重新核对，不能把这个名称当通用值。

```cpp
        const s7_5::GestureSnapshot point{
            s7_5::GestureState::ACTIVE, s7_5::GestureId::POINT,
            .90f, s7_5::GestureId::POINT, 5};
        link.send(point, 2, 1050000, 1060000);
    }

    std::array<uint8_t, s7_6::kWireFrameSize * 2> bytes{};
    const int input = open(path, O_RDONLY);
    const ssize_t count = input >= 0
        ? read(input, bytes.data(), bytes.size()) : -1;
    if (input >= 0) close(input);
    unlink(path);
    if (count != static_cast<ssize_t>(bytes.size())) return 1;

    s7_6::VirtualRcFrame first, second;
    if (!s7_6::decode(bytes.data(), s7_6::kWireFrameSize,
                      1070000, 0, 0, first) ||
        !first.valid || first.gesture_id != s7_5::GestureId::UNKNOWN ||
        first.channels.roll != 0 || first.channels.pitch != 0 ||
        first.heartbeat != 1) return 1;
    if (!s7_6::decode(bytes.data() + s7_6::kWireFrameSize,
                      s7_6::kWireFrameSize, 1070000,
                      first.source_sequence, first.heartbeat, second) ||
        !second.valid || second.channels.pitch != 30 ||
        second.heartbeat != 2) return 1;
    std::cout << "s7.6 serial loopback self-test ok\n";
    return 0;
}
```

`mkstemp` 用模板创建唯一临时文件；花括号让 `SerialLink` 在读回前析构并关闭输出 fd；`unlink` 删除临时文件。第一帧应是健康中立，第二帧 POINT 首步 Pitch=30，总长度恰好 88 字节。现在才运行：

```sh
g++ -std=c++17 -O2 -Wall -Wextra -pedantic \
  Linux/RK3568/s7_5/s7_5_gesture.cpp \
  Linux/RK3568/s7_6/s7_6_virtual_rc.cpp \
  Linux/RK3568/s7_6/s7_6_serial.cpp \
  Linux/RK3568/s7_6/s7_6_serial_test.cpp \
  -o /tmp/s7_6_serial_test
/tmp/s7_6_serial_test
```

正常输出 `s7.6 serial loopback self-test ok`。测试创建临时文件，`SerialLink` 写两帧，再读取 88 字节并逐帧 decode。它证明循环处理部分写和编码写出路径，不能证明 UART 电平。

### RK3568 板端自检和显式设备选择

部署后先运行：

```sh
./s7_6_live --self-test
```

然后在确认 `/dev/ttyS9` 确实对应已接好的 TX 后，做不使用摄像头的 20 帧测试：

```sh
./s7_6_live --uart-test /dev/ttyS9 20 cycle
```

`20` 是帧数，`cycle` 表示循环测试手势。逻辑分析仪设置为 UART、115200、8N1，期望约每 50 ms 一帧、每帧 44 字节、前两字节 `47 52`、心跳递增、CRC可重算。

完整摄像头链必须显式设置环境变量：

```sh
S7_6_RC_OUTPUT=/dev/ttyS9 \
./s7_6_live --camera \
  ./models/hand_detector_fp16.rknn \
  ./models/hand_landmarks_detector_fp16.rknn \
  /dev/video0 800 600 20 0 200 4776
```

没有 `S7_6_RC_OUTPUT` 时程序拒绝启动，防止源码猜串口。纯视觉测试可明确设 `/dev/null`，但 `/dev/null` 只丢弃字节，不能算串口验收。

### 故障注入不能省

| 注入 | 正常安全结果 | 第一证据 | 第一检查点 |
|---|---|---|---|
| 翻转主体一位 | decode 因 CRC 拒绝 | CRC错误计数 | 抓到的44字节与离线重算 |
| 重复同一心跳 | 拒绝 | heartbeat错误计数 | 上一值与当前值 |
| 有效源序号不前进 | 拒绝 | sequence错误计数 | 是否误把发送心跳当源序号 |
| 接收比发送晚>150 ms | 拒绝/候选超时 | age/link错误 | 两端使用的单调时间合同 |
| 源到发送>250 ms | 发送端无效或接收拒绝 | source age | 摄像头/推理延迟 |
| 无效帧携带非零通道 | 拒绝 | format/range错误 | Mapper是否真正清零 |
| 断开TX线 | 150 ms内飞控候选失效 | 飞控 `rx_age` | 物理线、波特率、地线 |
| 杀死Linux进程 | 150 ms内候选失效 | 心跳停止 | 进程PID和飞控超时 |
| 重启Linux进程 | 不自动恢复旧动作 | 新会话/需重新授权 | 下一篇的session与AUX3门禁 |

## 验证闭环

| 层级 | 正常 | 失败 | 能证明什么 |
|---|---|---|---|
| Mapper | 50 ms 首步30，1秒后回中，Throttle/AUX恒0 | 突跳、重复续期、旧值残留 | 手势到候选的逻辑边界 |
| encode/decode | 44字节往返一致 | CRC/格式/语义被拒绝 | 软件协议一致 |
| 文件回环 | 两帧共88字节均可解 | 少字节或第二帧错位 | SerialLink完整写出路径 |
| ELF兼容 | ARM aarch64，无GLIBC_2.36需求 | 板端 loader 版本错误 | 静态兼容检查，不证明硬件 |
| UART波形 | 3.3V、115200 8N1、44字节、约20Hz | 无波形/乱码/幅值错误 | 引脚、电平和串口参数 |
| 飞控观察 | 心跳/序号前进，CRC通过，断线超时 | 候选不更新或错误计数涨 | Linux→F722接收链；还不证明仲裁 |

## 迁移练习：只改变脉冲持续时间

在实验分支把 `kCommandPulseUs` 从 1,000,000 改为 500,000，其他映射、速率和帧周期不变，更新纯逻辑测试的时间预期后重跑。预测：达到 -300 后更早开始回中；峰值可能仍能到 -300，因为 600/s 从 0 到 300 需要 0.5 s。不要同时改变化率，否则无法判断差异来自持续时间还是斜率。新协议行为必须重新做台架验收。

## 文字复盘和最终结构图

你现在知道“虚拟 RC”不是 Linux 冒充完整遥控器，而是一个受限候选协议。Mapper 把 ACTIVE 边沿变成一次 1 秒小幅脉冲，按实际时间限制变化率，结束后回中；Throttle/AUX 永远为 0。健康中立与故障释放用 `valid` 明确区分。

固定 44 字节使用小端整数、魔数、版本、长度、序号、心跳、双时间戳和 CRC。CRC 先挡传输损坏，语义检查再挡过期、倒退、越界或手势/通道不匹配。SerialLink 用 termios 配置 115200 8N1，并处理部分写和暂时不可写。

```text
GestureSnapshot
  ↓ Mapper
  ├─ 新ACTIVE边沿 → 1秒有界目标
  ├─ approach → 600/s姿态限速
  ├─ 健康空档 → valid=1中立/完成已有脉冲
  └─ FIST/时间故障 → valid=0全零
VirtualRcFrame
  ↓ 小端encode + CRC16
44字节
  ↓ SerialLink：termios 115200 8N1，完整write
RK3568 3.3V TX
  ↓ 共地，TX→PC7/USART6_RX
下一篇：F722从第一个字节开始同步、校验、保存候选，再与物理RC仲裁
```
