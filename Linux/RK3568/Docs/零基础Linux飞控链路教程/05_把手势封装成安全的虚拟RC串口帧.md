# 手势怎样变成安全的虚拟 RC 候选帧

上一章得到的是已经确认的手势事件。飞控不能直接理解 `OPEN_PALM` 或 `V_SIGN` 这些名字，它接收的是遥控通道形式的数据。

这一章要解决三个问题：

1. 每种手势对应多大的姿态变化；
2. 怎样避免命令跳变、重复触发或永久保持；
3. 怎样把候选值放进一个能检查完整性和新鲜度的串口帧。

## 先说清 Linux 有什么权限

当前项目只允许 Linux 提出三个姿态轴的候选：

- Roll：横滚，控制机体左右倾斜；
- Pitch：俯仰，控制机体前后倾斜；
- Yaw：偏航，控制机头左右旋转。

Linux 不拥有：

- ARM；
- Throttle；
- 任何 AUX 通道；
- PID、Mixer 或 DShot 的直接控制权。

实际上当前三个动作只使用 Roll 和 Pitch，Yaw 候选保持 0。Throttle 和 AUX 字段也始终为 0。

这些 0 不是让油门归零。它们表示 Linux 根本不提供这些通道。真正的油门和 AUX 在飞控仲裁时一直从物理遥控器取得。

## 当前手势映射是什么

| 已确认手势 | Linux 候选 | 直观含义 |
|---|---|---|
| 张掌 `OPEN_PALM` | Pitch = -300 | 一次 Pitch 负向目标 |
| 单指 `POINT` | Pitch = +300 | 一次 Pitch 正向目标 |
| V 字 `V_SIGN` | Roll = -300 | 一次 Roll 负向目标 |
| 握拳 `FIST` | 无效释放 | 立即撤销 Linux 候选资格 |

这里的 ±300 是相对 RC 中心的偏移量，不是角度，也不是电机值。

飞控把中心看作大约 1500 us，所以 Pitch=-300 对应的目标大约是 1200 us，Pitch=+300 对应大约 1800 us。

## 为什么动作只持续 1 秒

如果手一直保持张掌，而 Linux 一直输出 Pitch=-300，飞机会持续接收同一个姿态要求。使用者必须再做另一个手势才能停止，这不够保守。

当前设计把新的 `ACTIVE` 当作一次按钮事件：

```text
新的ACTIVE边沿
  ↓
启动1秒目标
  ↓
1秒结束
  ↓
自动回到中立
```

手一直不动不会重复启动。只有状态先离开 ACTIVE，之后再次完成确认，才会产生下一次事件。

## 为什么变化不能一步跳到 ±300

即使目标被限制在 ±300，从 0 一帧跳到 -300 仍然是突变。

Linux 侧把姿态候选变化速度限制为 600 单位每秒。目标帧率是 20 Hz，也就是约每 50 ms 发一帧。

理想情况下，一帧最多变化：

```text
600 × 0.05 = 30
```

所以张掌刚触发时，Pitch 大致经历：

```text
0 → -30 → -60 → -90 → ... → -300
```

1 秒目标结束后，它也按同样速度回到 0，而不是突然回中。

飞控侧还有第二层限速。两层同时存在，是为了避免 Linux 实现错误或异常时间间隔直接造成大跳变。

## “有效中立”和“无效释放”不是一回事

这是整条链路里最容易混淆的地方。

### 有效中立

有效中立表示：

> Linux 进程、摄像头和推理链仍然健康，只是现在没有新的活动动作，三个姿态候选都在中间位置。

正常无手、手势切换过程或 1 秒动作结束后，Linux 可以继续发送有效中立。

这样做的原因是，正常识别空档不应该让飞控反复退出虚拟源，再要求操作者重新拨 AUX3。

### 无效释放

无效释放表示：

> Linux 当前不再具备提供候选值的资格，飞控必须退出虚拟源。

以下情况会产生无效释放：

- 握拳被稳定确认为 ACTIVE；
- 数据源时间已经过期；
- 时间顺序倒退；
- 视觉管线发生真实故障；
- 发送进程停止后，飞控等待候选超时。

无效不是“姿态轴等于 0”。它是一个独立的资格状态。

## 正常无手为什么不打断已经触发的 1 秒动作

假设张掌刚刚触发动作，随后手自然离开画面。

如果无手立即把目标截断，使用者每次收手的速度都会改变动作持续时间，控制会很难预测。

所以当前设计在视觉链仍健康时，让已经开始的 1 秒动作继续完成。无手只表示没有新事件，不会自动续期，也不会重新触发。

握拳不同。握拳是明确的人工释放手势，因此立即清空当前动作并让帧无效。

## 为什么每一帧还需要序号、心跳和时间

只发送五个通道不够。飞控还需要判断这是不是新数据。

### 源序号

`source_sequence` 表示动作源的前进顺序。有效动作数据不能倒退或重复使用旧序号。

### 心跳

`heartbeat` 每发送一帧都会增加。即使当前是中立，心跳仍应前进。飞控据此判断发送进程是否持续工作。

### 源时间

`source_timestamp_us` 表示产生这份视觉/手势信息的时间。

### 发送时间

`send_timestamp_us` 表示帧真正准备发送的时间。

发送时间不能早于源时间。有效源数据从产生到发送最多允许 250 ms，否则说明程序正在发送过旧结果。

飞控还会用自己的本地时钟记录收到帧的时刻。若 150 ms 内没有新的有效候选，它会退出虚拟源。

为什么需要两种时间检查？

- 250 ms 检查 Linux 内部结果是否已经老化；
- 150 ms 检查帧到达 F722 后，链路是否还在持续更新。

两块芯片的开机时刻不同，所以飞控不会直接把 Linux 的绝对时间与自己的绝对时间相减。

## 44 字节帧里放了什么

串口只传字节，不知道哪里是一条完整消息。项目规定每帧固定 44 字节：

| 偏移 | 长度 | 内容 | 用途 |
|---:|---:|---|---|
| 0 | 2 | `G`、`R` | 帮接收端找到帧起点 |
| 2 | 1 | 版本 1 | 防止双方误用不同协议 |
| 3 | 1 | 长度 44 | 确认完整布局 |
| 4 | 1 | valid 标志 | 区分有效候选和无效释放 |
| 5 | 1 | 手势 ID | 说明候选来自哪种手势 |
| 6 | 1 | 置信度百分比 | 0～100 |
| 7 | 1 | 保留字节 | 当前必须为 0 |
| 8 | 4 | 源序号 | 检查有效动作是否前进 |
| 12 | 4 | 心跳 | 检查发送进程是否持续工作 |
| 16 | 8 | 源时间 | 判断视觉结果年龄 |
| 24 | 8 | 发送时间 | 判断 Linux 内部延迟和顺序 |
| 32 | 2 | Roll | 有符号候选偏移 |
| 34 | 2 | Pitch | 有符号候选偏移 |
| 36 | 2 | Yaw | 当前保持 0 |
| 38 | 2 | Throttle | 必须为 0 |
| 40 | 2 | AUX | 必须为 0 |
| 42 | 2 | CRC16 | 检查前 42 字节是否损坏 |

多字节整数按小端顺序存放。小端的意思是低位字节先发送。发送端和接收端必须采用同一种顺序，否则同样的两个字节会被解释成不同数字。

## CRC 能证明什么

CRC16-CCITT-FALSE 根据前 42 个字节计算出一个 16 位结果，并放在帧尾。

飞控收到后重新计算。两边结果不同，说明帧在传输中损坏、丢字节、错位，或者双方协议实现不一致。

CRC 能发现常见传输错误，但它不能证明发送者是谁，也不能证明内容本身合理。因此飞控还要继续检查版本、范围、时间、序号，以及手势名称和通道值是否互相匹配。

例如一帧 CRC 完全正确，却声称 `FIST` 同时带有 Pitch=-300，这仍然违反当前手势映射，飞控会拒绝。

## Linux 怎样把 44 字节交给 UART

板端 Linux 把串口也表示为 `/dev/tty*` 设备。

程序打开正确的设备，配置为：

- 115200 波特率；
- 8 个数据位；
- 无校验；
- 1 个停止位；
- 无硬件流控。

这通常简称为 115200 8N1。

一次写入不保证操作系统必定接受全部 44 字节，所以发送逻辑会继续写剩余部分，直到整帧交出或出现错误。

这里真正需要你关心的不是串口 API 细节，而是三个条件：

1. 设备名必须对应实际引脚；
2. 串口参数必须与 F722 USART6 完全一致；
3. 任何写入错误都不能假装成功并继续沿用旧动作。

## 接线为什么必须先确认电气条件

当前链路是：

```text
RK3568 UART TX
  ↓
F722 PC7 / USART6 RX

RK3568 GND
  ─────────
F722 GND
```

要求：

- 使用 3.3 V TTL；
- 两块板共地；
- TX 接 RX；
- 不把 RK3568 TX 接到 F722 的 TX；
- 不把这根线并到已有 UART2 CRSF 接收链路；
- 所有飞控联调先拆桨。

共地让双方对“高电平和低电平”有共同参考。没有共地时，即使串口参数完全正确，接收也可能出现随机字节或完全没有数据。

## 用一次张掌走完整章

假设张掌在 1200 ms 进入 ACTIVE：

1. 映射器发现这是新的 ACTIVE 边沿，启动 1 秒动作。
2. 目标设为 Pitch=-300，其他候选轴为 0。
3. 当前 Pitch 从 0 开始按 600/s 逐帧接近 -300。
4. 每约 50 ms 生成一帧，心跳持续增加。
5. 每帧带上源序号、源时间、发送时间和当前限速后的通道。
6. 前 42 字节计算 CRC，形成完整 44 字节。
7. 串口把字节从 RK3568 TX 送到 F722 PC7。
8. 到 2200 ms 后目标回中，Pitch 再按限速逐步回到 0。
9. 手一直保持张掌不会再次触发；必须离开 ACTIVE 后重新确认。

## 这一章的故障应该从哪里查

| 现象 | 先看哪一层 |
|---|---|
| ACTIVE 有了但通道一直为 0 | 手势映射和新边沿是否成立 |
| 通道直接从 0 跳到 -300 | 变化率限制是否生效 |
| 动作一直不结束 | 1 秒结束时间和回中逻辑 |
| 同一手势不停重复动作 | ACTIVE 是否被当成持续电平而不是新事件 |
| 无手导致飞控不停退出 | 有效中立与无效释放是否混淆 |
| 握拳后仍保持有效 | 明确释放路径错误 |
| UART 有字节但飞控 CRC 错误 | 帧边界、字节顺序、长度或电气质量 |
| F722 完全收不到字节 | 串口设备、TX/RX、共地、电压和参数 |

## 这一章交给飞控的仍然只是候选

现在 Linux 已经能产生完整、有限幅、有时间信息的 44 字节帧。

但串口线有数据，不代表飞控已经使用它。下一章从 F722 的第一个接收字节开始，说明它怎样找到完整帧、怎样逐项拒绝不可信内容，以及 RC 仲裁器怎样保证物理遥控器始终拥有最终权限。
