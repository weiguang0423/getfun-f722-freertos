# 把手势封装成安全的虚拟 RC 串口帧

> **当前学习位置：** `手势已经经过连续帧确认` → **把 ACTIVE 事件限制为可验证的串口候选帧** → `飞控接收、仲裁和人工授权`
>
> 本篇对应 S7.6。它只构造并发送候选 RC 帧；Linux 仍然没有 ARM、AUX、Failsafe、PID、Mixer 或 DShot 权限。

## 为什么不能直接把“张掌”写成一个遥控器数值

手势识别的输出是一个事件，例如 `OPEN_PALM`。飞控输入需要的是有范围、有时间、有完整性校验的数据。若 Linux 只写“张掌”几个字符给飞控，就会缺少：这条消息是否损坏、是不是旧消息、还能不能用、该影响哪个通道、持续多久。

S7.6 因此在两者之间放入一个固定协议：

```text
S7.5 ACTIVE 快照
    -> Mapper：限幅、限速、1 秒事件脉冲、正常中立
    -> 44 字节二进制帧 + CRC
    -> RK3568 串口 115200 8N1
    -> STM32 USART6 只读验证器
```

**CRC** 是循环冗余校验。你可以把它理解为根据前 42 个字节计算出的“错误检测码”。接收端用同一算法重算并比较；数据在传输中只要有一位变化，大概率就会发现不一致并拒绝该帧。

## 首版手势到虚拟 RC 的冻结含义

线上通道采用整数尺度：`1000` 表示归一化幅度 `1.0`，中立值是 `0`。目前只允许很小的姿态命令：

| 首次进入 ACTIVE 的手势 | Roll | Pitch | Yaw | Throttle | AUX | 语义 |
|---|---:|---:|---:|---:|---:|---|
| `OPEN_PALM` | 0 | -300 | 0 | 0 | 0 | 短暂向前/低头 Pitch |
| `POINT` | 0 | +300 | 0 | 0 | 0 | 短暂向后/抬头 Pitch |
| `V_SIGN` | -300 | 0 | 0 | 0 | 0 | 短暂向左 Roll |
| `FIST` | 0 | 0 | 0 | 0 | 0 | 当帧无效释放 |

三条轴限制为 `-300` 到 `+300`，最大变化率 `600/s`。这意味着数值不会从 0 突然跳到 -300，而是按最大每秒 600 的斜率靠近目标。同一 ACTIVE 手势只触发一次目标保持 `1 s`，随后自动按同一速率回中；一直摆着同一个手势不会连续发送多个动作。

没有手、未知、候选、正常手势切换等“链路仍健康”的状态，持续发送 `valid=1` 的全零中立帧。这样已经开始的 1 秒命令不会被中间的一帧无手过早截断，也不会让飞控误以为通信断开。握拳、采集/推理失败、超过延迟门槛、源时间异常才立即发送 `valid=0` 的全零释放帧。

`Throttle` 和 `AUX` 目标永远为 0。这里的 0 不是飞控的微秒脉宽，而是 Linux 候选协议中的“我不提出油门/AUX 请求”。飞控之后会把物理遥控器油门和 AUX 保留下来。

## 44 字节帧里有什么，接收端如何拒绝错误

| 字节偏移 | 字段 | 为什么需要它 |
|---:|---|---|
| 0～1 | 魔数 `G`、`R` | 在连续字节流里重新找到一帧起点 |
| 2～3 | 协议版本、固定长度 44 | 新旧协议或错位帧不混用 |
| 4 | `valid` 位 | 明确告诉飞控：这是健康候选还是立即释放 |
| 5～6 | 手势 ID、置信度 | 留下“为何产生该通道”的可诊断证据 |
| 8～11 | `source_sequence` | 对齐摄像头帧；允许因丢旧帧跳号，但必须前进 |
| 12～15 | `heartbeat` | 每一次发送递增，发现重复/倒退帧 |
| 16～31 | 源和发送单调时间戳 | 拒绝旧结果、未来时间和错误时间顺序 |
| 32～41 | 五个 `int16` 通道 | 有限的 Roll/Pitch/Yaw 与固定释放的 Throttle/AUX |
| 42～43 | CRC16 | 发现传输损坏 |

接收契约拒绝以下任何情况：CRC、版本、长度或保留字节错误；通道越界；心跳未前进；有效帧源序号未前进；收包距发送超过 150 ms；源结果距发送超过 250 ms；有效 `UNKNOWN` 帧并非全零；或 `FIST`/低置信度帧冒充有效动作。

这不是为了让协议复杂，而是为了让“接收一串字节”不等于“允许影响飞控”。

## 接串口前必须核对的电气边界

本项目已经把 CRSF 接收机保留在 UART2；Linux 链路使用飞控 `USART6`，配置为 `115200 8N1`。F722 源码确认：`PC6=USART6_TX`、`PC7=USART6_RX`。

接线前要逐项确认：

1. RK3568 选定 UART 是 **3.3 V TTL** 电平，而不是 PC 的 RS-232 电平。RS-232 不能直接接 MCU UART。
2. RK3568 的 TX 接飞控 `PC7/USART6_RX`；若需要双向测试，RK3568 的 RX 接飞控 `PC6/USART6_TX`。
3. 两块板的 GND 必须相连，且只在断电状态下确认导线和引脚。
4. 先查 RK3568 原理图/排针丝印和 `ls -l /dev/ttyS*`，确认实际 Linux 设备名；不能猜一个 `/dev/ttyS?`。
5. 不能把 RK3568 TX 与 ELRS/CRSF 的 UART2 发送端并接，也不能带电试探未知引脚。

项目历史接线记录使用 RK3568 JP11 的 `UART9_TX_M1`（3.3 V）到飞控 PC7，板端设备为 `/dev/ttyS9`。这是一份现有项目事实，重新布线或换板后仍必须按照上面五项重核，而不是照抄一个设备名。

## 构建、板端自检和可观察的串口测试

先在 **WSL** 交叉构建：

```sh
cd /mnt/e/getfun-f722-freertos/GETFUN_F722_FreeRTOS
sh Linux/RK3568/s7_6/build_board.sh
```

将新生成的 `s7_6_live` 与所需模型/运行库复制到 RK3568 后，在 **板端** 执行：

```sh
cd /userdata/gesture_rc_demo
./s7_6_live --self-test

# 只在已核对的实际 UART 上运行；此示例的 /dev/ttyS9 不是通用占位符
./s7_6_live --uart-test /dev/ttyS9 20 cycle
```

`--uart-test` 不打开摄像头。它先发送一帧释放，再每 50 ms 发送一帧，终端打印每帧的字节数、心跳、有效位与十六进制内容。它适合用逻辑分析仪或飞控 UART4 诊断日志核对 115200 8N1、44 字节、心跳和 CRC。

完整实时链需要给程序显式指定输出设备；禁止不经确认默认发送：

```sh
S7_6_RC_OUTPUT=/已核对的串口设备 \
./s7_6_live --camera 检测模型.rknn 关键点模型.rknn \
  /dev/video0 800 600 20 0 200 4776
```

环境变量 `S7_6_RC_OUTPUT` 的存在就是一个安全门：没有它，程序拒绝启动。做纯视觉显示而不接飞控时，可以明确设为 `/dev/null`；这会丢弃帧，不能算作串口验收。

## 本篇完成判据

完成本篇时，你应该能拿到：

- WSL 中两个自检均通过的输出。
- 板端 `--self-test` 的退出码为 0。
- 逻辑分析仪或飞控 UART4 日志证明收到 44 字节、20 Hz 左右、心跳递增的帧。
- 断开/杀死发送进程后，接收端在 150 ms 超时内把候选判为无效。
