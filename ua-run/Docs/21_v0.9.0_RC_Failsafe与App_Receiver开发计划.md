# v0.9.0 RC Failsafe与App Receiver开发计划

> 所属里程碑：S3.8  
> 合并目标标签：`v0.9.0-flight-input-baseline`（S3.8与S3.9共同验收）  
> 基线：`v0.8.0-crsf-rc-baseline` / `5bce889`

## 1. 问题与证据

S3.7实物验收确认CRSF数据已能在UART4摘要中稳定观察，但
Betaflight App 2025.12.2的Receiver页面没有显示通道。原因不在CRSF链路，
而在MSP页面初始化契约不完整。

Betaflight App官方标签 `2025.12.2`（commit `a2d0f506`）的
`src/js/tabs/receiver.js` 依次请求：

```text
MSP_FEATURE_CONFIG
MSP_RC
MSP_RSSI_CONFIG
MSP_RC_TUNING
MSP_RX_MAP
MSP_RC_DEADBAND
MSP_RX_CONFIG
MSP_MIXER_CONFIG
```

v0.8.0只实现了其中的 `MSP_FEATURE_CONFIG`和 `MSP_MIXER_CONFIG`，且前者返回
空Feature掩码。因此不能只增加 `MSP_RC=105`，必须同时补齐Receiver页面的
完整只读依赖链。

## 2. 通道契约

CRSF `0x16`解码后的 `channel_us[]`保留发射机线序，不覆写S3.7原始证据。
S3.8新增 `mapped_channel_us[]`，按Betaflight默认 `AETR1234`映射为
Receiver页面要求的内部顺序：

| App逻辑通道 | CRSF线序索引 |
|---|---:|
| Roll / Aileron | 0 |
| Pitch / Elevator | 1 |
| Yaw / Rudder | 3 |
| Throttle | 2 |
| AUX1～AUX4 | 4～7 |

`MSP_RX_MAP=64` 固定返回8字节：

```text
[0, 1, 3, 2, 4, 5, 6, 7]
```

`MSP_RC=105` 固定返回16路小端 `uint16_t`微秒值，顺序为
Roll、Pitch、Yaw、Throttle、AUX1～AUX12。本阶段不做端点标定、Deadband、
Rates、Expo或归一化；这些仍属于S4.4。

## 3. Failsafe与恢复契约

### 3.1 状态

| 值 | 状态 | 含义 |
|---:|---|---|
| 0 | `WAITING_FOR_SIGNAL` | 启动后尚未建立可信RC链路 |
| 1 | `RECOVERING` | 已重新收到帧，但恢复观察窗口未关闭 |
| 2 | `HEALTHY` | RC可供飞行消费者使用 |
| 3 | `LOST` | 通道超时，Failsafe激活 |

### 3.2 阈值

- 最后一帧合法 `0x16` 通道帧超过300 ms未更新，进入 `LOST`。
- 启动或断链后恢复必须同时满足：连续观察至少100 ms，且至少收到5帧。
- 二者任一未满足时，`channels_valid=false`且 `failsafe_active=true`。
- Link Statistics超过1000 ms未更新时单独撤销 `link_statistics_valid`，不用它代替
  通道帧超时判定。
- 全部时间差使用无符号32位减法，覆盖tick回绕。

### 3.3 安全输出

RC无效时，`MSP_RC`不返回可被误解为有效控制的陈旧值，而是返回：

```text
Roll=1500, Pitch=1500, Yaw=1500, Throttle=1000, AUX1～AUX12=1000
```

原始通道和最后一次映射值仍保留在 `app_state.rc`供诊断。任何后续
FlightTask/ARM消费者必须同时检查 `channels_valid=true`且
`failsafe_active=false`，不得只读通道数组。

`APP_ARMING_INHIBIT_RC_NOT_READY` 使用bit 6。`MSP_STATUS_EX`在RC无效时同时报告
Betaflight标准 `ARMING_DISABLED_RX_FAILSAFE` bit 2，使App能显示 `RXLOSS`。

## 4. Receiver页面MSP响应

| 命令 | ID | 长度 | S3.8语义 |
|---|---:|---:|---|
| `MSP_FEATURE_CONFIG` | 36 | 4 | 仅声明 `FEATURE_RX_SERIAL` bit 3 |
| `MSP_RC` | 105 | 32 | 16路已映射微秒值；Failsafe时返回安全值 |
| `MSP_RSSI_CONFIG` | 50 | 1 | RSSI AUX通道关闭，Link Statistics仍保留在快照 |
| `MSP_RC_TUNING` | 111 | 24 | API 1.48可解析的Betaflight默认Rates只读值 |
| `MSP_RX_MAP` | 64 | 8 | `AETR1234` / `[0,1,3,2,4,5,6,7]` |
| `MSP_RC_DEADBAND` | 125 | 5 | Deadband 0，3D throttle deadband 50，只读 |
| `MSP_RX_CONFIG` | 44 | 39 | CRSF provider 9、mid 1500、min/max校验边界与API 1.48尾部 |
| `MSP_MIXER_CONFIG` | 42 | 2 | 保持Quad X |
| `MSP_FAILSAFE_CONFIG` | 75 | 8 | 300 ms、DROP、Throttle 1000的只读投影 |

本阶段不承诺Receiver页面的Save按钮。`MSP_SET_RX_MAP`、`MSP_SET_RX_CONFIG`、
`MSP_SET_RC_DEADBAND`、`MSP_SET_RSSI_CONFIG`和 `MSP_SET_FEATURE_CONFIG` 不会伪造“已持久化”。
可写参数将在参数系统扩展时单独实现。

## 5. GETFUN MSP2诊断

`MSP2 0x4003` 固定64字节，小端：

| 偏移 | 长度 | 字段 |
|---:|---:|---|
| 0 | 1 | 版本1 |
| 1 | 1 | flags：bit0收到过帧，bit1 valid，bit2 failsafe，bit3 recovering，bit4 link valid |
| 2 | 1 | phase |
| 3 | 1 | map id，0=AETR |
| 4 | 2 | timeout ms |
| 6 | 2 | recovery ms |
| 8 | 2 | recovery minimum frames |
| 10 | 2 | 保留 |
| 12 | 4 | channel sequence |
| 16 | 4 | channel age ms，未收到时 `0xFFFFFFFF` |
| 20 | 4 | failsafe count |
| 24 | 4 | recovery count |
| 28 | 2 | 当前recovery frame count |
| 30 | 2 | 保留 |
| 32 | 32 | 16路最新映射通道 |

## 6. 完成条件

- 纯算法回归覆盖映射、安全值、299/300 ms边界、恢复双门限和32位回绕。
- Betaflight App 2025.12.2 Receiver页面可打开，16路通道连续更新。
- Roll/Pitch/Yaw/Throttle标签与实际操作一致，不靠改CRSF解析器掩盖映射错误。
- 断链300 ms内进入Failsafe，App显示安全值且 `MSP_STATUS_EX` 报告 `RXLOSS`。
- 恢复必须经过100 ms且至少5帧，快速闪断不会瞬时重新放行。
- Debug/Release构建、既有CRSF/姿态/时间/滤波回归、`git diff --check`全部通过。
- 文档24的S3.8/S3.9合并实物验收通过前不创建
  `v0.9.0-flight-input-baseline` 标签。
