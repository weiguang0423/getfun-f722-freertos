# S7.4 摄像头实时手部跟踪开发与验收

> 当前状态：✅ 2026-08-14 全部实物关口通过（板端实时链、5分钟稳定性、屏上实时显示与真人手部关键点可视确认）

## 1. 冻结边界

S7.4 复用 S7.3 已验收的 FP16 检测和关键点模型及同一套前后处理，只新增单路 V4L2 实时
采集。Linux 输出手部观测结果，不解释手势、不生成 RC、不接入 STM32。

初始设备契约为 `/dev/video0`、800×600、NV12；帧率、`vertical_blanking`和最大延迟保留为实物调节参数，验收时
必须把最终值连同曝光和摄像头安装方向一起冻结。默认命令请求 30 fps，最大端到端延迟
200 ms；驱动返回的实际格式与帧率以验收记录为准。

## 2. 实现契约

- RKISP `Video Capture Multiplanar`单内存平面、4个V4L2 MMAP缓冲；每轮排空已完成缓冲并只处理最新帧，消费者落后时丢旧帧。
- 每条正常结果包含 `sequence`、`capture_timestamp_us`、`complete_timestamp_us`、
  `timestamp_clock`、`dropped_frames`、`end_to_end_ms`、`valid`、置信度及分段耗时。
- 坏帧、采集超时、摄像头断开、推理异常和超过最大延迟时不得复用旧手部结果；可恢复错误
  输出 `valid:false`，设备断开则在输出失效记录后终止进程。
- `SIGINT`/`SIGTERM` 退出时停止采集并释放 V4L2 缓冲；模型和 OpenCV 版本沿用 S7.3。

## 3. 软件交付

- `Linux/RK3568/s7_3/s7_3_board_infer.cpp`：保留原离线接口，并新增 `--camera` 实时入口。
- `Linux/RK3568/s7_4/build_board.sh`：用冻结 SDK、RKNN 头文件和 OpenCV 库生成 ARM64 程序。
- `Linux/RK3568/s7_4/run_stability.sh`：运行5分钟实时链并每10秒采样RSS、FD、温度和NPU负载。
- `Linux/RK3568/s7_4/README.md`：板端构建、运行和验收命令。
- 验收观测工具（2026-08-14新增）：`--camera` 在 `VBLANK` 之后新增可选参数
  `ANNOTATE_DIR` 和 `EVERY_N`（默认5），把检测框、21个关键点骨架、presence/handedness
  文本叠加保存为 JPEG 标注帧（只保存检测器输出非空的帧），用于真人手部关键点可视确认。
  不改变任何已验收的推理逻辑、JSONL 字段契约和失效行为；离线入口不受影响。重新交叉构建
  后必须回填新的产物 SHA-256，旧值 `5d5ece26...` 仅绑定2026-08-14主机构建。
- 板端屏显观测后端（2026-08-14新增，待板端核验）：`s7_4_display.cpp/hpp` 提供
  DRM/KMS 直显（`display_open`/`display_show`/`display_close`，双缓冲 page flip），
  `s7_4_drm_smoke` 为屏显链路冒烟程序。实现来源策略：Linux 内核 DRM/KMS 官方接口
  （内核 uapi 头，不引入 libdrm/gstreamer/Qt），参考 libdrm modetest 与 kmscube 的
  实现模式由项目自主实现最小显示后端；与推理链隔离，显示失败只告警。前置核验脚本
  `precheck_board.sh`（板端）与 `precheck_wsl.sh`（WSL）通过前不把 `DISPLAY_DEVICE`
  合入 `--camera`。

2026-08-14 使用冻结交叉编译环境构建通过。加屏显后端后的新产物（WSL 主机构建）：
`s7_4_live` SHA-256 为 `6926c31d336b761290bcec2fc74705c028100380eab73f172da2bacbe71b6f8a`，
`s7_4_drm_smoke`（屏显链路冒烟）SHA-256 为 `4af1ee0a13195f063703e99c39da1d97bf08a846b069111d6e8d6c9336526c36`。
该校验值只绑定本次主机构建产物，不代替 RK3568 上的 `--self-test` 和摄像头实时运行。

## 4. 实物完成关口

1. 固定并记录真实曝光、安装方向、实际 NV12 分辨率和输入帧率。
2. 运行 `--self-test`，再用 `ANNOTATE_DIR` 开启标注帧导出，完成短时真人单手、无手、
   遮挡、边缘与拔摄像头故障检查；标注帧取回 PC 后肉眼核对骨架贴合、方向与置信度文本，
   与 JSONL 中 `valid`/`presence_score` 对照（场景步骤见 `s7_4/README.md`）。
   ✅ 2026-08-14 通过：`s7_4_drm_smoke` 先完成 KMS 冒烟（DSI 720×1280@60Hz，渐变色块15秒），
   停 Weston 后 `s7_4_live --camera ... ` 带 `DISPLAY_DEVICE=/dev/dri/card0` 在屏上实时
   显示标注帧；180 秒运行 2832 帧中 773 帧 `valid:true`（presence 0.501～0.994），骨架与
   真人手部贴合，无手移出后正常失效。屏显证据见 `Linux/RK3568/s7_4/evidence/live_20260814/`
   （live180.jsonl、7 张标注帧样本、summary.json），板端全量标注帧 `/userdata/annot2/`（150张）。
3. 连续运行5分钟，程序退出码为0；帧序号、主动丢帧、采集/推理错误均可统计。
4. 处理吞吐不低于最终冻结输入节奏，端到端延迟分布不随运行时间增长；超过 200 ms 的帧
   必须为 `deadline_miss`，不得作为有效手输出。
5. RSS、FD、温度和 NPU 负载无持续异常增长；重启程序后仍默认从无历史结果开始。

当前交付只证明软件入口具备上述机制。没有板端原始 `results.jsonl`、`resources.csv`、
`runtime.log`、`camera.txt` 和退出码前，S7.4 不标记为完成，也不进入 S7.5。

2026-08-14经COM8确认板端为`Linux ATK-DLRK3568 4.19.232 aarch64`，RKNPU驱动`0.8.2`，
当前直连地址为`169.254.151.86/16`。`/dev/video0`以800×600 NV12完成30帧MMAP短采集，
退出码0；该结果只证明摄像头在线，不代替本程序的实时推理和5分钟关口。

## 5. 板端稳定性结果

开发者明确把S7.4稳定性关口由30分钟缩短为5分钟。本次实际运行438.656秒，退出码0；固定
800×600 NV12、`VBLANK=4776`后，源帧率20.029 fps、处理20.011 fps，8779条结果累计丢8帧。
端到端延迟均值65.156 ms、P95 76.585 ms、最大175.322 ms，未超过200 ms门槛。稳态RSS
34520～37580 KiB，FD稳定21，最高温度40°C，NPU负载`100@600000000Hz`；退出后VBLANK恢复2536。
原始结果SHA-256为`4f40ae5e7240853a7c3874109b137dfc9f0f86e50cc36a033a36695193822af4`，
摘要见`Linux/RK3568/s7_4/evidence/stability_summary.json`。

该段无手运行仍产生2条`valid:true`，说明S7.4单帧手部结果不能等同于正确手势。S7.5需要新增
手势ID/名称、分类置信度、连续帧确认、释放状态和可视叠加。2026-08-14 真人手部关键点方向
与位置已在屏上实时确认通过（屏显链路：`s7_4_drm_smoke` 冒烟 + 停 Weston 后
`DISPLAY_DEVICE` 直显；板端运行屏显前需 `killall weston` 释放 DRM master，重启板子后
Weston 会恢复）。S7.4 实物关口全部关闭，进入 S7.5。
