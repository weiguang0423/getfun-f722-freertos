# GETFUN F722 V3 v0.3.0 IMU DMA与DRDY开发计划

> 基线：`v0.2.0-imu-polling-baseline`  
> 目标里程碑：`v0.3.0-imu-dma-drdy-baseline`  
> MCU：STM32F722RET6  
> 日期：2026-07-27

## 1. 本轮开发定位

`v0.2.0-imu-polling-baseline` 已完成并通过实物验收：

- SPI1 Mode 0、1.6875 MHz 与 PA4 软件片选。
- ICM42688P 识别、配置回读和 1 kHz 连续采样。
- SI 单位、`CW90_DEG` 机体坐标和 Betaflight App 原始数据。
- IMU 离线重试、USB/UART 保活和 Motor 1～8 安全低电平。

v0.2.0 每帧使用阻塞式 `HAL_SPI_TransmitReceive()`。14 字节样本加地址共
15 字节，在 1.6875 MHz 下理论占用约 71 μs；CPU 在这段时间内不能执行同优先级以下
的有效工作。本轮把样本事务改为 DMA，并让 DMA 完成中断唤醒 ImuTask。

本轮不改变传感器量程、ODR、单位、坐标方向和 MSP 缩放，v0.2.0 是全部结果的回归基准。

## 2. 硬件事实与DRDY边界

当前硬件事实来源：

```text
E:\betaflight\src\config\configs\GETFUNF722V3\config.h
Docs/01_GETFUN_F722_V3_硬件基线_构建烧录与恢复.md
```

已确认目标文件定义：

```c
#define GYRO_1_SPI_INSTANCE SPI1
#define GYRO_1_CS_PIN        PA4
#define PINIO1_PIN           PC4
```

目标文件没有定义 `GYRO_1_EXTI_PIN`，现有硬件基线也没有冻结 ICM42688P INT1/INT2
到 STM32 的连接。PC4 已明确属于 PINIO1，禁止参考其他 F722 板卡把 PC4 猜测为
GYRO EXTI。

因此本版的 DRDY 方案固定为：

```text
ImuTask 1 kHz绝对周期
    ↓
SPI阻塞读取 INT_STATUS.DATA_RDY_INT
    ↓ ready
SPI1 DMA读取 TEMP_DATA1起始的14字节样本
```

本轮不配置 GPIO EXTI，也不修改 ICM42688P INT1/INT2 输出寄存器。只有取得原理图、
PCB 连通性或实际测量证据后，才能增加 GPIO DRDY 中断。

## 3. 预期达成目标

1. SPI1 RX 使用 DMA2 Stream 0、Channel 3。
2. SPI1 TX 使用 DMA2 Stream 3、Channel 3。
3. 采样读取使用两个静态、Cache line 对齐的 TX/RX 槽位交替工作。
4. DMA 完成中断只结束 CS、记录状态并通过任务通知唤醒 ImuTask。
5. ImuTask 保持唯一的 SPI/IMU 策略拥有者。
6. 初始化、WHO_AM_I、配置写入和回读继续使用阻塞式 SPI，降低启动复杂度。
7. 每帧先检查 `INT_STATUS.DATA_RDY_INT`，未就绪时不启动 DMA。
8. DMA 启动失败、完成错误或超时均恢复 CS 高电平并进入现有三次失败恢复策略。
9. MSP、SI 单位、轴向和 Betaflight App结果与 v0.2.0 一致。
10. 全过程不启用电机输出。

## 4. 设计思路

### 4.1 为什么只把样本突发读取改为DMA

启动初始化只发生在上电或故障恢复阶段，寄存器事务很短，不影响稳定运行时CPU预算。
如果初始化阶段也异步化，会引入额外状态机，却不能明显改善1 kHz运行性能。

因此：

- 初始化和DRDY状态读取：阻塞式、短事务。
- 14字节连续样本读取：DMA异步事务。

这使问题可以限制在稳定运行的单一路径，也保留 v0.2.0 的可靠初始化基线。

### 4.2 为什么使用软件双缓冲

HAL DMA `NORMAL` 模式一次只完成一个SPI事务。总线层准备两个固定槽位：

```text
slot 0：TX[64] + RX[64]
slot 1：TX[64] + RX[64]
```

每次启动交替选择槽位。DMA完成后，已完成槽位保持不变，任务可以复制和解析；下次事务
使用另一个槽位。这样未来扩展流水处理时不需要改变接口，也不会让DMA覆盖任务正在解析
的数据。

本轮不使用DMA硬件Double Buffer Mode，因为SPI事务需要每帧显式控制CS，HAL普通模式
更容易处理错误和恢复。

### 4.3 为什么用任务通知

系统中只有ImuTask等待SPI1 DMA完成，属于单生产者、单等待者事件。FreeRTOS直接任务
通知不需要创建队列或信号量：

```text
DMA IRQ
  → HAL_DMA_IRQHandler()
  → HAL_SPI_TxRxCpltCallback()
  → imu_bus完成回调
  → vTaskNotifyGiveFromISR(ImuTask)
```

ISR不解析传感器数据、不做浮点换算、不发布app_state、不输出日志。

### 4.4 Cache与内存策略

当前 `main.c` 只启用 I-Cache，没有启用 D-Cache。DMA静态缓冲仍按32字节Cache line
对齐，并在总线层实现条件式Clean/Invalidate：

- D-Cache关闭时操作为空。
- 将来启用D-Cache后，TX在DMA前Clean，RX在DMA前后Invalidate。

缓冲区不得位于任务栈，生命周期必须覆盖整个DMA事务。构建后通过MAP文件确认缓冲区
位于STM32F722 DMA可访问的内部RAM。

### 4.5 为什么DMA中断优先级为5

DMA完成ISR需要调用 `vTaskNotifyGiveFromISR()`。当前
`configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY=5`，因此DMA2 Stream 0/3抢占优先级
固定为5，不能配置为0～4。

### 4.6 错误状态机

```text
DMA start
 ├─ HAL_OK → 等待通知（2 ms上限）
 ├─ HAL_BUSY/ERROR → CS高、记录启动错误
 └─ 通知超时 → 标记非活动、HAL_SPI_Abort、CS高

DMA IRQ
 ├─ complete → CS高、保存完成槽位、通知任务
 └─ error    → CS高、保存HAL错误、通知任务
```

任一DMA错误都计入 `read_error_count` 和 `consecutive_error_count`。连续三次失败后
`present=false`，再执行完整初始化；不能进入平台Fault Halt。

## 5. 固定资源配置

| 项目 | 固定配置 |
|---|---|
| SPI1 RX DMA | DMA2 Stream 0 / Channel 3 |
| SPI1 TX DMA | DMA2 Stream 3 / Channel 3 |
| 方向 | RX Peripheral-to-Memory；TX Memory-to-Peripheral |
| 数据宽度 | Byte / Byte |
| 地址递增 | 外设关闭、内存开启 |
| 模式 | Normal |
| 优先级 | High |
| FIFO | Disable |
| DMA IRQ抢占优先级 | 5 |
| DMA IRQ子优先级 | 0 |

| 每槽TX/RX容量 | 64字节、32字节对齐 |
| GPIO DRDY | 不启用，硬件引脚未冻结 |

## 6. 接口设计

### 6.1 imu_bus

保留现有阻塞接口，新增：

```c
typedef void (*imu_bus_dma_callback_t)(void *context);

void imu_bus_set_dma_callback(imu_bus_dma_callback_t callback, void *context);
imu_bus_status_t imu_bus_read_dma_start(uint8_t register_address,
                                         size_t length);
imu_bus_status_t imu_bus_read_dma_finish(uint8_t *data, size_t length);
imu_bus_status_t imu_bus_dma_abort(void);
bool imu_bus_dma_busy(void);
```

约束：

- 只允许一个在途事务。
- `start()`拉低CS；成功完成、错误和abort都拉高CS。
- `finish()`只能由收到DMA通知后的ImuTask调用。
- 回调运行在ISR上下文，只负责通知。

### 6.2 icm42688p

新增：

```c
icm42688p_status_t icm42688p_start_sample_dma(
    imu_bus_status_t *bus_status);
icm42688p_status_t icm42688p_finish_sample_dma(
    icm42688p_raw_sample_t *sample,
    imu_bus_status_t *bus_status);
```

器件层继续负责14字节大端解析，ImuTask不得直接解释DMA字节。

### 6.3 app_state统计

在 `app_imu_sample_t` 增加：

```c
uint32_t drdy_poll_count;
uint32_t dma_transfer_count;
uint32_t dma_start_error_count;
uint32_t dma_completion_error_count;
uint32_t dma_timeout_count;
uint32_t dma_abort_count;
```

这些计数只由ImuTask更新，诊断与MSP只读快照。

## 7. ImuTask执行流程

每个1 kHz周期：

1. `vTaskDelayUntil()`等待绝对周期点。
2. 读取并累计DRDY轮询次数。
3. DRDY未就绪时累计 `data_not_ready_count`，不启动DMA。
4. 清除可能残留的任务通知。
5. 调用 `icm42688p_start_sample_dma()`。
6. 最多等待2 ms DMA通知。
7. 超时时调用 `imu_bus_dma_abort()`并记录错误。
8. 通知到达后调用 `icm42688p_finish_sample_dma()`。
9. 完成大端解析、SI换算和`CW90_DEG`轴变换。
10. 发布完整快照。

## 10. 本轮不包含

- GPIO DRDY/EXTI：当前硬件没有冻结连接证据。
- ICM42688P FIFO和硬件DMA Double Buffer Mode。
- 提高SPI频率或更改1 kHz ODR。
- 陀螺零偏、加速度校准和参数持久化。
- 软件滤波、姿态解算、CRSF、PID或DShot。
- 任何有效电机波形。
