# S7 RK3568 Linux摄像头手势RC控制总体开发计划

> 当前状态：✅ S7.1～S7.8 已验收并冻结为 `v1.6.0-s7.8-gesture-rc-baseline`
> 当前关口：S7.9 尚未开始；必须先满足 S5.6、装桨和受控飞行安全前置条件
> 最终目标：不同手势稳定生成有界RC指令，经人工授权和飞控既有安全链驱动四旋翼完成对应动作

## 1. 目标、范围与不包含内容

系统使用RK3568 Linux板连接摄像头，识别手部和已冻结手势，把识别结果转换为虚拟RC通道，
再交给飞控已有RC输入、setpoint、PID、Mixer、ARM/Failsafe和DShot链路。Linux不是第二套飞控，
也不直接生成电机值。

本阶段包含：

- Linux板、摄像头、模型转换环境和板端RKNN运行环境基线。
- 手部检测、关键点、手势判定、置信度和连续帧状态机。
- 手势到 Roll/Pitch/Yaw 候选 RC 的范围、变化率和超时语义；Throttle/AUX 在线上保持释放。
- Linux到飞控的物理链路、协议、心跳、序号和故障检测。
- 物理RC优先的输入源仲裁、总授权、立即接管和安全失效。
- PC、板端、链路、拆桨和受控飞行的分级验收。

本阶段不包含：

- 环境建图、自主航线、目标跟踪、自动返航或自主起降。
- 用视觉结果直接ARM、直接写PID/Mixer、直接提交DShot或替代FlightTask。
- 在没有实测资源证据时假定Linux与现有ELRS接收机可以共用同一UART。
- 为未来多摄像头、多机型或多飞控板预先建立通用框架。

## 2. 系统边界

```text
摄像头
  -> Linux采集与时间戳
  -> 手部检测/关键点RKNN推理
  -> 手势置信度与时序状态机
  -> 有界虚拟RC候选值 + 心跳/序号/时间戳
  -> 经实物确认的通信链路
  -> 飞控RC源仲裁（物理RC优先）
  -> 既有rc_input / rc_setpoint
  -> PID / Quad-X Mixer
  -> ARM/PREARM/Failsafe门禁
  -> DShot600
```

必须保持四条所有权边界：

1. Linux拥有图像、推理、手势和虚拟RC候选值，不拥有ARM与电机输出。
2. 物理RC拥有ARM、手势模式总授权和紧急接管；初版不允许视觉生成ARM请求。
3. 飞控拥有输入源选择、RC有效性、setpoint、控制、Failsafe和最终电机授权。
4. 任一异常都使虚拟RC源失效，不得继续发送或保持最后一个动作。

## 4. 分阶段目标

### S7.1 RK3568、Linux、摄像头与RKNN环境基线

交付：

- 板卡/系统/内核、存储、网络、温度和NPU设备信息。
- 摄像头枚举、格式、分辨率、帧率、时间戳和连续采集方法。
- `librknnrt`、RKNPU驱动、转换工具候选版本和恢复方法。
- 一段固定输入到固定输出的最小NPU样例及原始日志。

完成关口：摄像头和NPU各自连续运行30分钟；无进程挂死或不可恢复设备错误；版本、命令、
日志和温度/内存数据可复现。该关口只证明平台可用，不证明手势模型可用。

2026-08-13按文档37完成实物基线。开发者明确免除本阶段摄像头/NPU各30分钟稳定性验收，
因此S7.1按项目例外关闭：摄像头以300帧短采集、NPU以10秒1391次一致输出作为本次证据。
该豁免不延伸到S7.4的摄像头实时推理链，最终曝光和安装方向也在S7.4开始前冻结。

### S7.2 手部检测与关键点模型基线

先在PC固定完整感知链。若使用掌部检测加手部关键点两级模型，必须分别记录ROI、坐标、缩放、
归一化和输出含义；若使用其他方案，也必须提供等价的可重复接口，不能只保存最终手势文本。

交付：

- 模型文件、上游地址、精确版本/校验值、许可证和获取日期。
- 输入尺寸、颜色顺序、量化/归一化、输出张量、关键点坐标系和左右手语义。
- 覆盖无手、单手、遮挡、边缘、不同距离/角度/光照的固定图片/短视频集。
- PC参考输出和可视化证据。

完成关口：相同输入重复得到一致结果；错误输入被拒绝；模型前后处理已有独立可运行检查。

精确提交、四个模型SHA-256、输入输出契约、独立LiteRT CPU参考程序和三次全测试集结果见文档36。
2026-08-13按开发者指定不把许可证作为关口后关闭S7.2；已登记无手误检和手性误差边界，后续由
S7.5时序门禁隔离。上游现成`.rknn`仅作对照，不代替S7.3面向本板环境的重新转换和误差验收。

### S7.3 RKNN转换与板端NPU推理

使用与板端Runtime兼容的固定RKNN-Toolkit2转换模型。转换参数、量化数据集、生成日志、模型
校验值和所有算子告警必须归档，禁止构建时自动下载“最新版”。

完成关口：

- 固定测试集在PC参考模型和RK3568 `.rknn`上的关键点/置信度误差落入冻结范围。
- 记录预处理、推理、后处理各段平均值和高分位延迟、内存峰值、NPU占用及温度。
- 量化前后误差、失败样本和降级条件可追踪。
- 开发者于2026-08-14明确免除S7.3的30分钟稳定性验收；S7.4另于同日明确采用5分钟稳定性关口。

2026-08-13已完成主机侧转换与验收工具，具体模型校验值、同字节PC基线和冻结误差范围见文档38。
2026-08-14在ATK-DLRK3568上完成FP16和INT8各2859帧实测。FP16有效性一致率0.995103且全部P95
误差满足冻结门槛；INT8有效性一致率0.918153且多项误差超限，因此拒绝INT8并选择FP16。两次运行
均退出码0，最高温度41.25°C，S7.3关闭为✅；完整证据见文档38。

### S7.4 摄像头实时手部跟踪

把S7.1采集和S7.3推理串成单路实时管线。只保留完成目标必需的缓冲，消费者落后时优先丢旧帧，
不能堆积历史画面后继续输出过期动作。

完成关口：

- 每个结果带采集时间、完成时间、帧序号、手部有效性和置信度。
- 采集断开、坏帧、推理失败和超时均进入无有效手状态。
- 目标分辨率下处理速度不低于冻结输入节奏，端到端延迟不随运行时间增长。
- 连续5分钟记录帧数、丢帧、推理错误、延迟、内存和温度。

### S7.5 手势集合、置信度与时序状态机

实际手势形状和RC含义在该阶段根据摄像头实测冻结，不在总体计划中提前猜测。每个手势必须有：

| 字段 | 必须冻结的内容 |
|---|---|
| 手势ID与名称 | 唯一机器ID和用户可理解名称 |
| 几何定义 | 使用哪些关键点、角度、距离或左右手信息 |
| 进入条件 | 最低置信度、连续确认帧数/时间和允许的前一状态 |
| 退出条件 | 松开、切换、低置信度和超时门槛 |
| RC语义 | 影响哪些通道、目标范围和最大变化率 |
| 冲突处理 | 多手、多手势或无法判定时的唯一结果 |

状态机至少区分`NO_HAND`、`UNKNOWN`、`CANDIDATE`、`ACTIVE`和`RELEASED`。无手、未知、
低置信度和超时不得沿用上次`ACTIVE`动作。固定视频集与真人重复测试都必须输出混淆统计、
进入延迟和误触发记录。

### S7.6 手势到虚拟RC映射与发送链路

先冻结“手势意图 -> 归一化虚拟RC”，再选择传输协议，避免协议细节反向污染手势逻辑。

虚拟RC契约必须包含：

- Roll/Pitch/Yaw 的中立值、最小/最大值、变化率和释放值，以及线上 Throttle/AUX 固定释放值。
- 有效位、手势ID、置信度、帧序号、源时间戳、发送时间戳和心跳。
- 启动默认无效、连接恢复不自动启用、旧序号/过期帧/非法范围全部拒绝。
- 物理RC的ARM与总授权通道不由Linux生成。

协议和端口只有在核对`01`硬件资源、Linux电平、现有ELRS接收机保留方式和拔线故障后才能冻结。
如复用CRSF通道语义，也必须先证明物理链路与源仲裁可行，不能把两个发送端直接并接到UART。

完成关口：逻辑分析仪/串口回环下，帧率、CRC或等价完整性、序号、范围、超时和断线恢复全部
可重复；杀死Linux发送进程后，飞控侧在冻结超时内只得到“虚拟源无效”。

### S7.7 飞控RC源仲裁、人工授权与Failsafe

该阶段才允许修改飞控。新增逻辑必须位于RC输入边界，输出与现有`rc_input`一致的安全快照，
不得在setpoint、PID、Mixer或DShot旁路注入动作。

初版仲裁规则：

- 上电默认使用物理RC，Linux源默认无效。
- 物理RC完成ARM并通过专用AUX显式授权后，虚拟RC才可控制 Roll/Pitch/Yaw；物理 Throttle 和全部 AUX 始终保留所有权。
- 撤销AUX、物理 Roll/Pitch/Yaw 接管、Linux超时/非法帧或任一现有inhibit出现时，立即退出虚拟源；物理油门变化不退出。
- 切换过程必须有确定的中立/斜坡策略，不能产生姿态通道跳变；Throttle 始终实时采用物理值。
- Linux源恢复后仍需新的人工授权，禁止自动恢复动作或自动重解锁。

完成关口：既有S3/S4回归全部通过，并新增源选择、授权、接管、超时、非法帧、重启和Failsafe
的最小独立回归；Debug/Release构建通过后仍只标记软件完成，不能声称实物安全。

### S7.8 拆桨端到端联合验收

保持拆桨并断开或严格控制Motor动力，逐级观察：

```text
图像帧 -> 手/关键点 -> 手势状态 -> 虚拟RC -> 飞控RC快照
       -> setpoint -> PID/Mixer诊断 -> ARM/Failsafe门禁 -> 实际DShot值
```

必须覆盖每个冻结手势，以及无手、未知、多手、遮挡、低光、拔摄像头、NPU错误、杀进程、
通信断线、乱序/旧帧、Linux重启、飞控重启、物理RC撤销授权和摇杆接管。任一步失败都不得保持
旧动作、自动ARM或绕过停机门禁。连续运行30分钟，记录两端计数、延迟、栈/内存和温度。

S7.8的首个软件切片使用同一源序号连接两端日志：Linux JSONL的
`virtual_rc_source_sequence` 必须等于该摄像头帧 `sequence`；飞控UART4的`e2e`行以
`rc_seq`回显已接收序号，并同时给出RC来源、setpoint、PID、Mixer、ARM/Failsafe与DShot摘要。
详细执行方法、通过条件和记录表见文档43。

### S7.9 受控飞行与整项目冻结

只有S5基础飞行已冻结、S7.8全部通过且恢复/急停手段就绪后，才安装螺旋桨。先限制虚拟RC幅度
和变化率，在低风险场地逐个验证动作；人工操作者始终持有ARM、模式总授权和接管控制。

完成关口：

- 每个冻结手势可重复触发对应动作，释放后按合同恢复，不出现持续旧指令。
- 手势切换、短暂丢手和人工接管没有危险跳变或反向动作。
- 故障注入和恢复行为与拆桨验收一致，不因真实负载改变安全语义。
- 重复完成启动、人工ARM、授权、手势动作、人工接管、降落和DISARM全流程。
- 形成Linux侧、飞控侧和整机联合验收文档后，才能创建整项目冻结标签。

## 5. 文档、版本与验收规则

1. 每个S7.x开始前，先写对应开发计划，冻结输入输出、实现来源、资源和不包含内容。
2. Linux项目与飞控仓库分别记录提交和构建产物；整机验收文档同时引用两端精确版本。
3. 外部模型、Toolkit、Runtime和驱动登记来源、版本、许可证、校验值、本地修改和回退方法。
4. PC转换成功不等于板端推理通过；板端推理通过不等于摄像头实时链通过；拆桨通过不等于飞行通过。
5. 软件完成标记为🟠，只有开发者确认真实硬件关口通过后才能标记✅和创建标签。
6. 任一阶段发现需要改动既有ARM/Failsafe边界时，必须先单独更新设计和回归，不允许顺手绕过。

## 6. 当前下一步

S4已按文档35完成并冻结，S7.1～S7.8 已由开发者确认关闭。下一目标为 S7.9，但不得因
S7.8 通过而直接安装螺旋桨；飞控基础飞行与 S7.9 的其余安全前置条件仍按路线图单独关闭。
